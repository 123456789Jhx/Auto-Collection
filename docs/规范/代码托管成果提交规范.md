# GitHub 成果提交规范

本规范用于让开发人员只维护 GitHub 仓库材料，系统自动采集事实、生成老板看板和负责人行动清单。

## 必备材料

每个项目至少补齐以下必备材料：

| 材料 | 提交位置 | 系统识别方式 |
|---|---|---|
| GitHub 仓库 | GitHub 组织仓库 | 仓库属于组织 |
| 项目简介 | GitHub 仓库 description 字段 | description 不为空 |
| 本期 Commit | GitHub Commit 记录 | 统计周期内有有效提交 |
| README 说明 | `README.md` | README 写清项目目标、成果入口、运行方式和验收口径 |
| 线上地址 | GitHub homepage 字段或 README | 识别公网 HTTP/HTTPS URL |
| 截图证据 | `docs/截图证据/`、`截图/` 或 README 图片/路径 | 文件树、Markdown 图片或纯文本路径；logo、icon、favicon 不算功能截图 |
| 项目文档 | `README.md`、`docs/项目开发/验收口径.md`、`docs/项目开发/部署说明.md`、`文档/验收标准.md` 等 | 文件树、Markdown 链接、项目事实字段 |
| 开发排期计划 | `docs/排期计划/一周开发排期计划.md`、`docs/plans/一周开发排期计划.md` 或 `排期/开发排期.md` | 按功能拆解任务、预计工时、负责人、产出物、验收口径和风险 |
| 阶段评分 | README 的 `## 阶段评分` | 目标、调研、开发、验证、验收等阶段填写 0-100 分；排期节点不评分 |
| 人员日报 | `docs/研发日报/YYYY-MM-DD-姓名.md`、`日报/YYYY-MM-DD-姓名.md` 或 README 今日日报 | 解析日期、成员、工作项、思考性工作、AI 协作、重复工作和改进建议 |
| 效率改进标准 | `docs/规范/{项目名}-efficiency.md` 或 `文档/执行标准.md` | 日报出现重复劳动或改进建议后，提交标准文档即可消除重复提醒 |

录屏和设计稿不是硬性必备，但复杂流程类成果建议补充：

| 材料 | 推荐位置 |
|---|---|
| 演示录屏 | `docs/演示录屏/`、`录屏/` 或 README 链接 |
| 设计稿 | `docs/design/`、`设计稿/` 或 README 链接 |

## 开发排期计划模板

开发排期计划是开发人员提交给技术负责人的计划依据，用来说明“准备怎么做、需要多少工时、有哪些风险”。正式起止日期仍由技术负责人在看板页面确认，开发人员不要把这个文档当成最终排期审批结果。

推荐路径：

```text
docs/排期计划/一周开发排期计划.md
docs/plans/一周开发排期计划.md
排期/开发排期.md
计划/开发计划.md
```

推荐内容：

```md
# 开发排期计划

- 项目：项目名称
- 仓库：dafengchan/project-name
- 计划提交人：张三
- 计划提交日期：2026-06-11
- 期望开发周期：2026-06-12 至 2026-06-18
- 计划总工时：32h
- 需要技术负责人确认的问题：是否优先做导出功能、是否接入登录权限

## 目标和范围

说明本次开发要解决什么问题，本次包含哪些功能，不包含哪些功能。

## 功能拆解和工时

| 功能模块 | 任务 | 负责人 | 预计工时 | 产出物 | 验收口径 | 依赖/风险 |
|---|---|---|---:|---|---|---|
| 项目列表 | 增加筛选条件和状态展示 | 张三 | 3h | 页面和接口 | 可按状态筛选项目 | 依赖项目状态字段 |
| 项目详情 | 展示阶段评分和证据入口 | 张三 | 4h | 页面组件 | 点击阶段可查看详情 | 依赖阶段评分文档 |
| 数据采集 | 解析 README 和 docs 文档 | 李四 | 5h | 采集逻辑和测试 | 能识别线上地址、截图、文档 | 私有仓库权限 |
| 联调验收 | 自测并补截图/录屏 | 张三 | 2h | 截图、录屏、验收说明 | 负责人可按证据复核 | 需要部署地址 |

## 每日计划

| 日期 | 计划工作 | 预计工时 | 当日可验收结果 |
|---|---|---:|---|
| 2026-06-12 | 完成接口字段和数据结构 | 6h | 接口返回项目阶段数据 |
| 2026-06-13 | 完成项目列表和详情 UI | 6h | 页面可查看项目进度 |
| 2026-06-14 | 联调 GitHub 文档识别 | 5h | README/docs 可被采集 |
| 2026-06-15 | 自测、补证据、修复问题 | 5h | 提交截图和验收说明 |

## 工时汇总

| 类型 | 工时 |
|---|---:|
| 前端开发 | 10h |
| 后端开发 | 8h |
| 联调测试 | 6h |
| 文档和证据 | 4h |
| 预留风险 | 4h |
| 合计 | 32h |

## 风险和需要确认

- 风险：线上地址部署可能受服务器资源影响。
- 风险：GitHub 私有仓库读取需要 Token 权限。
- 需要确认：是否必须本期完成录屏。
- 需要确认：哪些页面必须给老板展示。

## 提交和验收材料

- README：README.md
- 项目文档：README.md
- 截图：docs/截图证据/homepage.png
- 录屏：docs/演示录屏/demo.mp4
- 阶段评分：README.md 的“阶段评分”
```

填写要求：

- 按功能模块拆解，不只写一个笼统周期。
- 每项任务写预计工时，建议 0.5h 或 1h 颗粒度。
- 标明负责人、依赖、产出物和验收口径。
- 写清风险和需要技术负责人确认的问题。
- 正式起止日期由技术负责人在看板页面确认。

## 每日日报模板

推荐每位成员每天在项目仓库提交一份独立日报，路径格式如下：

```text
docs/研发日报/2026-06-06-张三.md
日报/2026-06-06-张三.md
工作日志/张三-2026-06-06.md
```

日报内容模板：

```md
# 研发日报

- 日期：2026-06-06
- 成员：张三
- 工作项：完成项目全景流程线评分展示；补充 GitHub 提交规范
- 思考性工作：拆解评分口径，确认 GitHub 事实优先、LLM 只做总结
- AI 协作：用 AI 梳理评分口径并生成测试用例
- 提示词方向：让 AI 对比流程线评分、证据完整度和日报过程质量三种口径
- 人工采纳结果：采纳 GitHub 事实优先方案，放弃不可复核的效率结论
- 重复工作：反复整理截图命名
- 改进建议：沉淀截图目录模板
- 过程质量口径：不按提示词数量评分，只看脱敏方向、人工采纳和 GitHub 交付结果
```

如果文件名已经包含日期和成员，例如 `docs/研发日报/2026-06-06-张三.md` 或 `工作日志/张三-2026-06-06.md`，正文可以不重复填写日期和成员，但必须填写工作项。

系统也兼容分段标题写法，例如 `## 工作项`、`## 思考性工作`、`## AI 协作`、`## 提示词方向`、`## 人工采纳结果`、`## 重复工作`、`## 改进建议` 下分别写列表；但字段行模板更适合复制和快速填写。

为了降低填写成本，系统也兼容少量字段别名，例如 `完成结果`、`关键思考`、`AI复核`、`AI 使用`、`提示方向`、`提问方向`、`采纳情况`、`采纳建议`、`低效重复`、`效率改进`。这些别名只用于结构化摘要识别，不会改变“不提交完整敏感提示词”的边界。

## AI 协作过程质量口径

系统不会采集个人完整提示词，也不会用提示词数量评价工作质量。人员日报只根据开发人员主动提交到 GitHub 的结构化日报评分。

管理口径：不要用提示词数量评价个人。系统只看脱敏提示词方向、人工采纳结果、思考性工作、重复工作、改进建议和 GitHub 交付结果。

| 维度 | 系统看什么 | 建议写法 |
|---|---|---|
| 思考拆解 | 是否明确记录方案判断、问题拆解和取舍 | 写清为什么这样做、如何判断、最终取舍是什么 |
| AI 协作 | AI 是否参与方案对比、生成、验证或复核 | 写清 AI 用在什么环节，最终人工采纳了什么 |
| 提示词方向 | 是否能说明向 AI 提问的目标、约束和方向 | 写清提示方向，不粘贴完整提示词原文 |
| 人工采纳 | 是否记录人工最终采纳、放弃和复核结果 | 写清采纳了什么、放弃了什么、由谁判断 |
| 重复识别 | 是否能识别低价值重复劳动 | 写清哪些工作反复发生、耗时在哪里 |
| 改进沉淀 | 是否提出模板化、自动化或流程优化建议 | 写清下一步可落地的改进动作 |
| 来源追溯 | 日报是否来自 README、`docs/研发日报/` 或中文日报目录文件 | 优先提交 `docs/研发日报/YYYY-MM-DD-姓名.md` |

日报建议写“提示词方向”和“协作结果”，不要提交以下内容：

- API Key、账号密码、Cookie、Token。
- 客户隐私、合同金额、手机号、身份证号等敏感数据。
- 未脱敏的完整业务聊天记录或完整提示词长文。
- 无法复核的夸张结论，例如“效率提升 100%”但没有 GitHub 事实或业务口径支撑。

系统会过滤明显包含密钥、Token、Cookie、完整提示词或客户聊天记录的日报条目；被过滤内容不会进入人员日报评分和老板看板。

## 效率改进标准沉淀

当日报里出现“重复工作”或“改进建议”时，系统会在开发提交清单里生成标准沉淀待办。开发人员提交对应标准文档后，系统会把它作为 GitHub 事实采集，并不再重复催办同一个项目。

推荐路径：

```text
docs/规范/project-name-efficiency.md
文档/执行标准.md
```

推荐内容：

```md
# 效率改进与执行标准

- 项目：dafengchan/project-name
- 负责人：张三
- 来源成员：张三、李四

## 建议沉淀方向
- 重复整理截图路径
- 沉淀截图目录模板

## 标准化方案
- 适用场景：哪些任务需要使用这个标准。
- 输入材料：需要提前准备的文档、截图、接口或数据。
- 操作步骤：可复用的步骤、模板、脚本或检查清单。
- 输出结果：完成后应提交到 GitHub 的代码、文档或证据。
- 验收口径：负责人如何判断该标准有效。

## AI 协作边界
- 可以记录提示词方向、约束、人工采纳结果和效率改进结论。
- 不保存完整敏感提示词、密钥、客户隐私、Cookie、Token 或内部账号信息。
```

## 项目文档模板

README 可以作为项目事实入口；如果项目还需要更细的事实文档，也可以放到 `docs/` 目录。系统兼容中文目录，以下文件会被自动采集为项目事实：

```text
README.md
docs/项目开发/验收口径.md
docs/项目开发/部署说明.md
docs/api.md
docs/business.md
docs/项目说明.md
docs/验收标准.md
docs/业务口径.md
文档/项目说明.md
需求/需求说明.md
接口/接口文档.md
验收/验收口径.md
部署/部署说明.md
```

项目说明文档推荐内容：

```md
# 项目说明

- 负责人：张三
- 项目状态：进行中
- 开发周期：2026-06-10 至 2026-06-20
- 线上地址：https://example.com
- 页面截图：截图/首页.png
- 演示录屏：录屏/演示.mp4

## 项目目标
说明这个项目解决什么业务问题，以及为什么值得展示给领导。

## 业务价值
说明这个成果能减少什么成本、提升什么效率，或者帮助老板做出什么判断。

## 成功指标
- 老板可以打开线上地址查看成果。
- 每个重点页面有截图或录屏证据。

## 本期成果
- 完成项目列表和详情页，支持领导查看项目状态。
- 补充部署说明和验收口径，方便负责人复核。

## 阶段评分
- 目标定义：85
- 调研：82
- 试用：80
- 指标：78
- 复用：90
- 开发：72
- 验证：0
- 验收：0
- 沉淀：0
```

`## 项目目标` 会作为老板看板项目说明的事实来源；`## 业务价值` 和 `## 成功指标` 会作为老板看板业务价值与可验证指标的事实来源。当 GitHub description 或 README 摘要不足时，系统会用项目文档补充项目摘要。

`文档/项目说明.md`、`需求/需求说明.md`、`接口/接口文档.md`、`验收/验收口径.md`、`部署/部署说明.md` 也可以写同样字段；系统会读取负责人、项目状态、开发周期、项目目标、业务价值、成功指标、本期成果和验收口径。

项目事实文档里也可以直接写成果入口，例如 `线上地址：https://example.com`、`页面截图：截图/首页.png`、`演示录屏：录屏/演示.mp4`；系统会把这些链接加入老板看板证据墙，不要求在 README 和证据清单里重复填写。

`docs/项目开发/验收口径.md` 推荐内容：

```md
# 验收口径

负责人能通过项目全景查看流程、证据和线上地址。
老板能查看每天的人员日报和成果证明。
```

## 成果证据清单模板

如果项目缺截图、录屏、项目文档或设计稿，开发人员可以新增：

```text
docs/成果证据/成果证据清单.md
evidence/README.md
证据/README.md
成果证据/README.md
```

推荐内容：

```md
# 成果证据清单

项目：dafengchan/project-name
负责人：张三

## README 成果入口
- 线上地址：https://example.com
- 截图：docs/截图证据/homepage.png
- 演示录屏：docs/演示录屏/demo.mp4
- 项目文档：README.md
- 设计稿：docs/design/homepage.fig

## 截图证据
- docs/截图证据/homepage.png：展示首页或核心操作入口。
- docs/截图证据/project-detail.png：展示关键流程、状态或结果。

## 演示录屏
- docs/演示录屏/demo.mp4：展示完整业务流程。

## 文档与设计
- README.md：项目目标、成果、运行方式、文档入口和验收口径。
```

系统会从 README 链接和 GitHub 文件树自动采集这些材料。截图和录屏必须展示真实功能，不要只放占位图。

截图证据建议使用真实页面或流程文件名，例如 `docs/截图证据/homepage.png`、`docs/media/project-overview.webp`。不要用 `logo.png`、`icon.png`、`favicon.png` 等装饰资源冒充截图证据，系统会把它们排除。

## Commit 要求

- 提交信息写功能结果，不只写 `fix`、`update`、`改一下`。
- 推荐格式：`feat: 完成项目列表和详情页`、`docs: 补充验收口径`。
- `fix`、`update`、`fix bug`、`修改代码`、`改一下` 这类空泛提交不会算作有效成果证据。
- 统计周期内没有 Commit 的项目会被判定为需要跟进。

## README 要求

- README 不能只写 `TODO`、`后续补充` 或项目名称。
- 必须能看出项目目标或业务价值。
- 建议写明负责人，例如 `负责人：张三` 或 `Owner: zhang`，系统会优先用它生成负责人提醒。
- 负责人字段也兼容 `产品负责人`、`技术负责人`、`业务负责人`、`对接人`，系统会取第一个姓名作为项目负责人。
- 建议写明项目状态，例如 `项目状态：进行中`、`项目状态：测试中`、`项目状态：待验收`、`项目状态：已验收`、`项目状态：阻断`、`Status: blocked`，系统会优先用它生成项目流程状态。
- `待补材料` 和 `待确认` 会作为继续推进但需要补证据的状态；`阻断`、`禁止继续`、`暂停`、`停滞` 才会进入红色阻断。
- 开发排期计划请单独提交到 `docs/排期计划/一周开发排期计划.md`、`docs/plans/一周开发排期计划.md` 或 `排期/开发排期.md`。
- 正式起止日期不在 Markdown 中审批，由技术负责人在看板页面选择并保存。
- 建议写明阶段评分，例如 `## 阶段评分` 下填写 `目标定义：85`、`调研：82`、`开发：72`、`验收：0`，系统会用这些分数展示流程线。排期节点不需要评分，由技术负责人在看板页面确认。
- 建议写明本期成果，例如 `## 本期成果` 或 `## 本期进展` 下列出可展示结果，系统会优先用它生成周进展。
- 如果 README 较简洁，可以把负责人、项目状态、开发周期、本期成果和验收口径写入 `docs/项目开发/验收口径.md`、`docs/项目说明.md`、`docs/验收标准.md` 或 `docs/业务口径.md`，系统会作为项目文档事实采集。
- 项目事实文档里的线上地址、截图、录屏、文档和设计稿链接也会被系统采集为成果证据。
- README 或项目事实文档里的项目目标可以补充看板项目说明，但不能替代 GitHub description；description 仍用于 GitHub 组织列表和项目基础信息自查。
- 建议提交每日日报，例如 `docs/研发日报/2026-06-06-张三.md`；可以用字段行，也可以用 `## 工作项` 等分段标题；也可以在 README 的 `## 今日日报` 或 `## 工作日志` 下填写日期、成员、工作项、思考性工作、AI 协作、重复工作和改进建议，系统会把它计入人员日报。
- 系统兼容中文日报目录，例如 `日报/2026-06-06-张三.md`、`工作日志/张三-2026-06-06.md`、`docs/日报/2026_06_06_张三.md`；推荐团队逐步统一到 `docs/研发日报/`。
- 必须提供成果入口，例如线上地址、截图、录屏或项目文档链接。
- 线上入口可以写成 `线上地址`、`线上网址`、`访问地址`、`演示地址`、`预览地址`、`体验地址` 或 `部署地址`，但必须是老板可访问的公网 HTTP/HTTPS 地址。
- 必须写清运行方式、部署方式或使用方式。
- 建议写清验收口径，例如 `验收口径：负责人能通过项目全景查看流程、证据和线上地址。`，系统会把它展示到项目详情和报告数据。
- README 支持三种材料写法：`截图：docs/截图证据/homepage.png`、`页面截图：截图/首页.png`、`![首页截图](docs/截图证据/homepage.png)`、`[验收文档](docs/项目开发/验收口径.md)`。
- `./docs/项目开发/验收口径.md` 和 `docs/项目开发/验收口径.md` 都可以，系统会统一识别为 GitHub 仓库文件链接。
- 系统兼容中文证据目录，例如 `截图/`、`图片/`、`录屏/`、`视频/`、`文档/`、`需求/`、`验收/`、`设计稿/`、`原型/`；推荐团队逐步统一到 `docs/` 目录，方便长期管理。

## GitHub 仓库基础信息

- 仓库 `description` 必须用一句话说明项目用途。
- 避免只写 `demo`、`test`、`前端项目` 这类无法判断业务价值的描述。
- 推荐格式：`用于展示研发成果、线上地址、截图证据和人员日报的老板看板`。

## 线上地址要求

- 线上地址必须是负责人和老板可以直接访问的公网 HTTP/HTTPS 地址。
- `localhost`、`127.0.0.1`、`192.168.x.x`、`10.x.x.x`、`172.16-31.x.x`、`file://` 不会算作线上成果。
- GitHub 仓库 homepage 和 README 成果入口建议填写同一个公网地址。

## 展示前自查

- README 是否写清项目目标、成果入口、运行方式和验收口径。
- GitHub 仓库 description 是否能让老板快速看懂项目用途。
- GitHub homepage 或 README 是否有可访问的线上地址。
- 截图是否能体现真实功能页面。
- 文档是否能说明需求、部署、接口或验收口径。
- 本期是否有能说明功能结果的 Commit。
