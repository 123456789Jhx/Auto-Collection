# 开发变更与编码规范总则

## 1. 目的

本文件是项目统一变更入口。

任何接口、数据库、手机脚本、后台页面、部署脚本或文档变更，都先写方案，再确认，再落地。

## 2. 生效范围

适用于：

1. 后端接口。
2. 数据库表结构。
3. 手机自动化脚本。
4. 后台管理页面。
5. 部署脚本与环境变量。
6. 文档、规范、项目记录。

## 3. 变更流程

1. 先写方案。
2. 方案要说明现状、目标、变更范围、不变范围、风险和落地顺序。
3. 发给我确认后再改代码。
4. 落地后补验证结果。
5. 如果本次只是维护既有规范或项目文档，必须先确认来源材料和目标文件，再只修改指定文档。
6. 遇到已存在的未提交改动，默认认为是用户或其他协作者的工作，不得回滚；如影响当前变更，先说明影响再继续处理。
7. 所有功能更新、功能修复、交互调整、接口调整、脚本调整、配置调整、打包部署调整和文档规范调整，落地后必须同步维护到 `docs/项目开发/项目记录.md` 或 `docs/项目开发/` 下对应专题记录。
8. 所有已确认卡点、Bug、异常现象和阻断问题，必须新增或更新到 `docs/项目开发/卡点与问题记录.md`；可以先记录为“待定位、定位中、待修复”，修复后必须在同一条目回填根因、解决方式、验证结果和剩余风险。

## 4. 编码要求

1. 先读现有代码和文档，再改。
2. 优先复用现有模型、表、接口和页面。
3. 数据结构变更必须同步 migration。
4. 接口变更必须同步类型定义。
5. 手机脚本改动必须保留可审计日志。

## 5. 文档要求

1. 项目介绍、当前范围、运行入口和文档入口维护在根目录 `README.md`。
2. 当前有效方案放 `docs/方案设计/`，且只分为 `功能方案/` 和 `架构方案/`。
3. 项目开发记录、部署说明、验收口径和卡点问题放 `docs/项目开发/`。
4. 过程、会议、联调和历史材料放 `docs/项目开发/` 的对应子目录。
5. 废弃或明确不使用的方案不保留为当前入口。
6. 功能更新记录必须写清变更日期、变更模块、变更内容、影响范围、验证结果和后续注意事项；不能只在对话或提交说明里描述。
7. 有效改动的项目记录至少包含：日期、模块、结果、主要文件或文档；如果是修复类改动，还要能追溯到卡点记录或专题修复记录。
8. 卡点记录必须写清：现象、影响、证据来源、当前判断、处理方案、验证口径和状态；修复完成后在原条目追加解决结果，不用新条目掩盖旧问题。

## 6. 设备与安全

1. 设备对外统一使用 `deviceCode`。
2. 手机本地 token 统一使用 `deviceToken`。
3. 设备注册必须唯一。
4. 真实互动能力必须有独立开关、范围和审计。

## 7. 部署与清理

1. schema 变更和应用部署分开看。
2. 高风险清理必须明确保留范围。
3. 生产部署脚本和本地脚本都要保留。

## 8. AI 与 Codex 协作规范

1. 使用 Codex 处理项目任务时，先判断是否存在适用的技能或项目规范；如存在，先读取当前版本的技能说明，再执行任务。
2. Superpowers 插件已可在 Codex 环境中使用，涉及方案、调试、测试、计划、验证、代码审查或并行代理时，按对应技能要求执行。
3. Codex 环境不依赖 Claude Code 的 `Skill` 工具；需要使用技能时，读取本地技能说明文件并按 Codex 的工具能力完成等价操作。
4. 重要开发任务必须保留“上下文读取、方案判断、执行变更、验证结果”的过程记录，不能只给出结论。
5. AI 可以协助生成方案、拆解任务、修改代码和整理文档，但最终采纳结果必须由开发人员确认，并以仓库文件和验证结果为准。
6. 不得把密钥、账号密码、Cookie、Token、客户隐私、完整敏感提示词或未脱敏聊天记录写入代码、日志、日报或规范文档。

## 9. Superpowers 使用规范

1. 新会话或新任务开始时，先检查任务是否命中 Superpowers 技能，例如 `using-superpowers`、`brainstorming`、`systematic-debugging`、`test-driven-development`、`writing-plans`、`verification-before-completion`。
2. 方案类、功能类、行为变更类任务，先做意图和边界确认，再进入实现；不能在目标、范围和验收口径不清时直接改代码。
3. Bug、测试失败或异常行为必须按系统化调试流程处理：先复现和定位，再提出修复，不凭猜测直接改。
4. 需要声明完成、修复或通过时，必须先运行与变更范围匹配的验证命令，并记录验证结果。
5. 涉及多文件、多模块或可并行拆分的任务，可以使用子代理协作；但必须明确每个代理的职责和文件范围，避免多人改同一位置。
6. 子代理只在用户明确允许或任务确实需要并行代理时使用；代理返回后，主执行人必须复核结果并整合到当前工作区。

## 10. 工具与文件修改规范

1. 搜索文件和文本优先使用 `rg` 或等价快速搜索工具。
2. 手工修改文件优先使用补丁方式，保持 diff 清晰；不要为了小改动重写整份文件。
3. 修改前先读取目标文件的现有结构，延续已有标题、编号、目录和表达方式。
4. 文档维护必须写清“新增了什么、保留了什么、禁止做什么、如何验证”。
5. 不做与任务无关的格式化、重命名、移动文件或大范围重构。
6. 不使用 `git reset --hard`、强制 checkout 或批量删除等破坏性操作，除非用户明确要求。

## 11. 交付与验证规范

1. 交付前必须核对本次实际修改范围，确认没有夹带无关文件。
2. 代码变更按风险运行单元测试、类型检查、构建、接口联调或页面验证。
3. 文档变更至少检查目标文件内容、目录位置和 Markdown 可读性。
4. 最终说明必须包含修改位置、核心变更和已执行的验证；未能验证的内容要明确说明原因。
5. 涉及有效改动的交付，最终说明必须同时写明项目记录维护位置；如果本次发现或处理了卡点、Bug、异常现象，最终说明必须写明卡点记录维护位置。
6. 如果本次没有维护项目记录或卡点记录，最终说明必须明确原因；不能只因为“对话里已经说明”而跳过仓库记录。

## 12. 对话需求承接规范

1. 用户明确要求“先出方案”时，只输出或维护方案文档，不直接改代码；用户确认“可以”或“按照方案修复”后再进入实现。
2. 用户给出参考文件、H5 页面、截图或线上地址时，先读取并确认参考依据，再设计或实现；不能只按记忆或主观判断改。
3. 用户要求“按照 H5 一比一”“保留之前逻辑”时，视觉重构必须服从既有业务链路，不能把原有点击、跳转、筛选、详情展示逻辑删掉或替换成不可用的新交互。
4. 多次连续对话中，最新用户指令优先；在长时间任务、恢复上下文或中断后，最终答复前必须复核当前最新诉求。
5. 对话中出现账号、密码、Token、注册秘钥、服务器地址等敏感信息时，只用于必要操作，不写入规范、提交说明、日志明文或公开文档。

## 13. UI 重构与交互保留规范

1. UI 重构前必须识别页面原有核心工作流，例如设备卡片、日期卡片、日志记录、采集记录、详情抽屉和任务操作按钮之间的关系。
2. 后台管理页面是操作型系统，不做营销式落地页；布局优先清晰、稳定、可扫描，避免只改样式不保留功能。
3. 任务调度、工作台、设备运行、直播评论、采集记录和日志中心等模块涉及同一设备状态时，视觉语言和状态口径要统一。
4. 卡片、列表、详情抽屉、筛选区和操作区必须支持用户继续完成原流程；点击卡片、切换任务、查看日期、查看日志或记录等路径要实际验证。
5. 中文后台页面默认使用中文文案；除技术字段、日志原文或接口字段外，不在用户可见操作文案中混入英文。
6. 完成 UI 变更后，应通过浏览器或截图检查主要页面、关键点击路径、响应式布局、文本溢出和组件遮挡问题。

## 14. 手机 Agent 调试与修复规范

1. 手机端 Bug 先看日志再改代码；至少对齐后台命令、手机 ACK、心跳、runtime log、当前页面 UI 树和实际安装版本。
2. 判断“功能不能执行”时，要区分命令未下发、命令未 ACK、任务未切换、页面未进入、弹窗阻塞、搜索失败、输入失败和发送失败。
3. 修改任务切换逻辑时，视频、直播、直播评论必须互斥；切换任务要中断旧循环，清理旧任务控制状态，避免旧任务继续滑动或发送。
4. 手机端页面恢复和弹窗处理要放在运行时关键路径，不能只在启动时处理一次。
5. 遇到抖音业务弹窗时，优先点击“暂不”“取消”“以后再说”“我知道了”等关闭按钮；不能误点“去设置”“开启”等会改变系统状态或跳出任务流的按钮。
6. 搜索结果不能只凭全屏文本包含目标词就复用，必须校验顶部搜索框或当前搜索状态确实等于目标关键词。
7. 账号名同步、配置刷新、版本检查等辅助能力不得抢占前台 UI 自动化流程；涉及打开抖音或点击页面的动作必须串行。
8. 新增自动化分支必须补充可审计日志，日志至少说明阶段、目标词、当前页面摘要、失败原因和恢复动作。

## 15. APK 版本与打包发布规范

1. 手机端代码变更必须同步提升 `versionName` 和 `versionCode`，避免设备装包后无法区分版本。
2. 打包时注册秘钥只允许通过环境变量、受控配置或既有安全来源注入，禁止在命令输出、文档或提交中明文展示。
3. APK 交付前必须做基础验证：脚本语法检查、`git diff --check`、构建成功、签名验证、包名验证、版本号验证和包内配置验证。
4. APK 产物统一放入 `dist/apk`，最终说明应包含文件路径、版本号和 SHA256。
5. 现场排障时必须核对手机实际安装版本；不能把未安装的新包能力当成当前手机已经具备的能力。

## 16. 日志定位与问题闭环规范

1. 问题定位优先形成时间线：用户操作时间、后台命令 issued/fetched/ack 时间、手机日志时间、心跳状态和页面状态。
2. 结论必须来自日志、代码或现场 UI 树；不能只凭“应该是”判断。
3. 修复后必须说明根因、修改点、验证结果和剩余前提，例如“需要安装新 APK 后才生效”。
4. 卡点或 Bug 一旦进入排查，先登记到 `docs/项目开发/卡点与问题记录.md`；修复成功后回填解决方式和验证结果，未修复则保持待处理状态并写明下一步。
5. 如果 CI 或构建失败，先修复失败项并重新验证，再说明已经推送或交付。
6. 提交前只纳入本次相关文件；工作区存在其他窗口或用户的未提交改动时，不得回滚、覆盖或顺手整理。

## 17. 近期联调沉淀规范

1. 用户明确要求“先设计方案，动代码前确认”时，只能先输出方案、范围、风险和验收口径；未经确认不得改代码、部署或打包。
2. 用户明确要求“开始执行代码”“一次性做完”“重新打包”等执行动作时，可以进入实现和验证，但仍必须先读取现有代码、文档和当前运行状态。
3. 涉及后台任务调度、直播评论、视频任务、直播任务分配等模块时，设计数据库或接口前必须先审查现有表字段、接口字段和页面表单字段，不能基于旧印象直接设计。
4. UI 调整必须以当前仓库实际页面或用户指定的最新线框稿为准；如果旧方案、旧截图和当前 H5 实现不一致，以当前实现和用户最新指示为准。
5. 手机端自动化问题必须结合后台结构化日志、手机端运行日志和代码分支一起判断；不能只凭现象改等待时间或坐标。
6. 手机端修复优先保持主流程不变，先修状态识别、日志、匹配规则、等待策略等低侵入点；只有用户确认后才调整任务主流程或调度策略。
7. 直播间、搜索词、账号名等文本匹配必须考虑全角/半角、空格、标点、括号、页面展示别名和搜索建议差异，不能只做原文字符串包含判断。
8. 对“进入正确页面后又退出重试”的问题，必须先检查状态识别和目标匹配是否误判，再考虑点击坐标、网络或设备性能。
9. 自动化等待策略优先使用“命中即继续、超时才兜底”的短轮询；避免在常规路径上使用不可提前结束的固定长等待。
10. 手机连接 USB 时，除非用户明确授权，不得操作手机、执行 ADB 控制、启动脚本或点击页面；可以读取已有后台日志、修改代码和打包 APK。
11. APK 打包前必须确认版本号、输出路径、注册密钥注入来源、脚本排除目录和构建结果；打包后必须验证版本、包名、签名和 SHA256。
12. 发布和部署必须区分生产环境与测试环境。生产域名或同事正在使用的环境不得擅自部署；用户指定测试服务器时，只能对该测试环境操作。
13. 每次涉及可回退版本时，必须明确当前基线、保留旧 APK 或旧部署产物，不得覆盖唯一可回退包。
14. `docs/项目开发/error`、临时日志、临时截图、验证用 APK、服务器账号密码、Token、Cookie 等敏感或过程文件不得提交，不得写入规范正文。
15. 多窗口或多人同时维护同一文档时，修改前必须检查文件是否被锁、hash 和修改时间是否稳定；如发现正在写入或锁定，等待稳定后再做局部补丁，不得整文件重写。

## 18. 代码审查常态化规范

1. 涉及手机 Agent、后台命令、任务调度、直播评论、权限检查、打包发布的改动，必须进行代码审查并维护到 `docs/项目开发/代码审查风险记录.md`。
2. 代码审查风险记录按审查日期倒序追加，同一天记录合并到一个日期块内，只保留 `风险等级`、`审查结果`、`处理结果` 三类信息；同一天按 P0/P1/P2 等级分层记录，避免写成难维护的长报告。
3. P0/P1 风险的详细证据、根因、修复方式、验证结果和剩余风险必须同步维护到 `docs/项目开发/卡点与问题记录.md`。
4. 审查不能只看当前改动文件；涉及跨层链路时必须同时看后台命令创建、手机拉取/压缩/ACK、runner 状态、采样器 stopReason、心跳和日志。
5. 涉及 STOP/PAUSE/START、任务切换、版本打包、权限检查、目标直播间识别的改动，必须补充至少一个跨状态或跨模块回归测试。
6. 审查结论不能只写在聊天或提交说明中；最终交付说明必须指出风险记录文档是否已更新。
