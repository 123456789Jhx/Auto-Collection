# 部门统一技术架构规范 V1.0

状态：建议标准  
适用范围：企业后台、业务中台、AI 应用、RAG 知识库、工作流系统、多租户 SaaS、内部运营工具  
文档日期：2026-05-18

---

## 一、总览与技术底座

### 1. 总体原则

本规范用于统一部门后续系统开发的技术选型、工程结构、接口标准、数据库标准、前端 UI 标准、AI/RAG 接入方式、部署方式和协作流程。

核心目标：

1. 所有新项目默认从统一工程模板开始，不重复搭建基础设施。
2. 前端、后端、数据库、AI、任务队列、部署方式保持一致。
3. 业务模块可以裁剪，基础规范不能随意变更。
4. 所有系统默认支持多租户、权限、审计、日志、异步任务和后续 SaaS 化。
5. AI 能力作为统一基础能力接入，不能散落在业务代码中。
6. UI 统一使用 Ant Design 和部门业务组件库，保证交互和视觉一致。

统一架构不是要求所有项目功能一样，而是要求所有项目使用同一套底座、同一套规则、同一套交付标准。

### 2. 标准技术栈

#### 2.1 运行时与工程管理

| 构建工具 | Vite |

| 服务端状态 | TanStack Query |
| UI 组件库 | Ant Design |
| 图表 | ECharts 或 Ant Design Charts |
| 表单 | Ant Design Form + Zod 校验 |

#### 2.3 后端

| 用途 | 标准选型 |
|---|---|
| API 服务 | Bun runtime + Hono |
| API 风格 | REST 优先 |
| 数据校验 | Zod |
| ORM | Drizzle ORM |
| 主数据库 | PostgreSQL |
| 缓存/队列 | Redis |

| 文件存储 | 本地开发用本地目录，生产用对象存储 |

| 场景 | 标准 |

| 后端部署 | Hono 同时提供 API 和前端静态页面 |

### 4. 分层架构

#### 4.1 总体分层

```text
用户界面层 Web
    ↓
接口层 API Routes
    ↓
业务服务层 Services
    ↓
数据访问层 Repositories
    ↓
基础设施层 DB / Redis / Qdrant / Object Storage / External APIs
```

#### 4.2 前端分层规则

前端只负责页面展示、交互、状态管理和调用 API，不直接处理后端业务规则。

规则：

1. 路由文件只做页面组装，不写复杂业务逻辑。
2. 业务功能放在 `features/[domain]` 下。
3. 可复用业务组件沉淀到 `packages/ui`。
4. API 调用统一放在 feature 内的 `api.ts` 或统一 client。
5. 服务端数据统一使用 TanStack Query 管理。
6. 页面状态和表单状态不要混入全局状态。
7. 禁止前端直接拼接不受控 SQL、调用数据库、绕过 API 访问后端资源。

推荐结构：

```text
features/example/
├─ api.ts
├─ hooks.ts
├─ types.ts
├─ components/
├─ pages/
└─ utils.ts
```

#### 4.3 后端分层规则

后端按 route、service、repository、integration 分层。

| 层级 | 职责 | 禁止事项 |
|---|---|---|
| routes | HTTP 入参、权限、调用 service、返回响应 | 禁止写复杂业务逻辑 |
| services | 业务规则、事务编排、状态流转 | 禁止直接依赖 HTTP 对象 |
| repositories | 数据查询、数据写入 | 禁止写业务策略 |
| integrations | 第三方系统适配 | 禁止把第三方返回值直接暴露给业务层 |
| workers | 异步任务处理 | 禁止承担实时 API 的同步职责 |

路由示例：

```ts
app.get('/api/v1/resources', authRequired, async (c) => {
  const query = ListResourceQuerySchema.parse(c.req.query())
  const result = await resourceService.list(c.get('auth'), query)
  return c.json(result)
})
```

Service 示例：

```ts
export async function list(auth: AuthContext, query: ListResourceQuery) {
  await permissionService.ensure(auth, 'resource:read')
  return resourceRepository.listByTenant(auth.tenantId, query)
}
```

## 二、接口、数据与权限

### 6. API 规范

#### 6.1 路径规范

统一使用 REST 风格。

```text
GET    /api/v1/resources
POST   /api/v1/resources
GET    /api/v1/resources/:id
PATCH  /api/v1/resources/:id
DELETE /api/v1/resources/:id
```

子资源：

```text
GET  /api/v1/resources/:id/logs
POST /api/v1/resources/:id/actions/approve
POST /api/v1/resources/:id/actions/archive
```

规范：

1. 路径使用复数名词。
2. 常规 CRUD 不在路径中写动词。
3. 非 CRUD 行为统一放在 `/actions/[actionName]`。
4. API 版本写在路径中：`/api/v1`。
5. 管理后台和客户端 API 不混用权限上下文。

#### 6.2 请求参数规范

列表接口统一支持：

```text
page
pageSize
sortBy
sortOrder
keyword
status
createdFrom
createdTo
```

示例：

```text
GET /api/v1/resources?page=1&pageSize=20&sortBy=createdAt&sortOrder=desc
```

#### 6.3 响应规范

单对象：

```json
{
  "id": "res_001",
  "name": "示例",
  "createdAt": "2026-05-18T10:00:00.000Z"
}
```

列表：

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalItems": 0,
    "totalPages": 0
  }
}
```

错误：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "参数不合法",
    "details": {}
  }
}
```

#### 6.4 HTTP 状态码

| 状态码 | 含义 |
|---|---|
| 200 | 查询或更新成功 |
| 201 | 创建成功 |
| 204 | 删除成功且无响应体 |
| 400 | 请求格式错误 |
| 401 | 未登录 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 409 | 资源冲突 |
| 422 | 参数校验失败 |
| 429 | 请求过于频繁 |
| 500 | 服务端错误 |

#### 6.5 类型和校验

所有 API 入参必须使用 Zod schema。

```ts
export const CreateResourceSchema = z.object({
  name: z.string().min(1).max(100),
  description: z.string().max(500).optional(),
})

export type CreateResourceInput = z.infer<typeof CreateResourceSchema>
```

规则：

1. 外部输入必须校验。
2. 第三方接口响应必须校验。
3. AI 输出必须校验。
4. 数据库返回值不重复校验，但要保证 schema 类型正确。
5. 前后端共享 DTO 放在 `packages/types`。

### 7. 数据库规范

#### 7.1 基础原则

1. PostgreSQL 是唯一业务主数据源。
2. Redis 只能做缓存、队列、锁和临时状态。
3. Qdrant 只保存向量、检索字段和业务引用 ID。
4. 文件存储只保存文件本体，数据库保存文件元数据。
5. 数据库 schema 由 Drizzle 统一管理，禁止手工直接改生产库结构。

#### 7.2 通用字段

所有业务表默认包含：

```text
id
tenantId
createdAt
updatedAt
createdBy
updatedBy
deletedAt
```

说明：

| 字段 | 要求 |
|---|---|
| id | 推荐使用 UUID、ULID 或统一 ID 生成器 |
| tenantId | 多租户隔离字段，必须建立索引 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |
| createdBy | 创建人 |
| updatedBy | 最后更新人 |
| deletedAt | 软删除字段，重要业务表必备 |

#### 7.3 命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| 表名 | snake_case 复数 | `users`, `audit_logs` |
| 字段名 | snake_case | `tenant_id`, `created_at` |
| TypeScript 属性 | camelCase | `tenantId`, `createdAt` |
| 枚举值 | UPPER_SNAKE | `PENDING_REVIEW` |
| 索引名 | idx_table_field | `idx_users_tenant_id` |
| 唯一索引 | uniq_table_field | `uniq_users_email` |

#### 7.4 多租户规则

1. 所有租户级数据必须带 `tenantId`。
2. 查询必须默认带 `tenantId` 条件。
3. 禁止前端传入 `tenantId` 后后端直接信任。
4. 当前租户必须来自认证上下文。
5. 跨租户查询必须有平台级权限。
6. 批量任务也必须带租户上下文。

#### 7.5 迁移规则

1. 每次 schema 变更必须生成 migration。
2. migration 文件进入代码审查。
3. 禁止在生产环境自动执行未审核 migration。
4. 删除字段前必须先完成兼容期。
5. 枚举值只允许新增，删除或改名必须写迁移方案。

### 8. 权限与认证规范

#### 8.1 权限模型

统一使用 RBAC + 资源范围。

```text
User
  ↓
Role
  ↓
Permission
  ↓
Resource Scope
```

权限点命名：

```text
resource:read
resource:create
resource:update
resource:delete
resource:approve
resource:export
```

示例：

```text
user:read
user:update
knowledge:create
knowledge:delete
ai:invoke
audit:read
```

#### 8.2 后端鉴权规则

1. 所有非公开 API 必须经过认证中间件。
2. 所有业务操作必须检查权限点。
3. 权限检查必须在后端完成。
4. 前端隐藏按钮只是体验优化，不是安全措施。
5. 导出、删除、审批、模型调用属于高风险权限。

#### 8.3 会话规则

1. 登录态统一由后端签发。
2. Token、Cookie、Session 策略由基础框架统一封装。
3. 敏感操作需要二次确认或操作日志。
4. 管理员重置密码、修改权限必须记录审计日志。

## 三、AI、RAG 与异步任务

### 9. AI 与 RAG 规范

#### 9.1 AI 接入原则

所有模型调用必须通过 `packages/ai`，业务模块不得直接调用模型供应商 SDK。

统一封装：

```text
AIProvider
ModelConfig
PromptTemplate
PromptVersion
AIInvocation
AIResult
RAGPipeline
EmbeddingService
VectorStore
```

#### 9.2 模型调用记录

每次 AI 调用必须记录：

| 字段 | 说明 |
|---|---|
| tenantId | 租户 |
| userId | 触发用户 |
| feature | 业务功能 |
| provider | 模型供应商 |
| model | 模型名称 |
| promptVersion | Prompt 版本 |
| inputHash | 输入摘要 |
| output | 输出内容或引用 |
| tokenUsage | token 消耗 |
| latencyMs | 耗时 |
| status | 成功或失败 |
| error | 错误信息 |
| traceId | 链路 ID |

#### 9.3 AI 输出规则

1. AI 输出默认是草稿，不直接改变关键业务状态。
2. AI 输出必须可追溯到输入、模型、Prompt 版本。
3. AI 输出必须经过 schema 校验。
4. 高风险内容必须人工审核。
5. 对外展示 AI 生成内容时必须保留标识和审核状态。

#### 9.4 Prompt 管理

Prompt 必须版本化。

```text
prompts/
├─ feature-name/
│  ├─ v1.md
│  ├─ v2.md
│  └─ tests.json
```

规则：

1. 修改 Prompt 必须升级版本。
2. 重要 Prompt 必须有测试样例。
3. 禁止在业务代码里硬编码长 Prompt。
4. Prompt 输入和输出字段必须明确。

#### 9.5 RAG 流程

标准流程：

```text
文件上传
  ↓
文本抽取
  ↓
切片 chunk
  ↓
元数据清洗
  ↓
embedding
  ↓
写入 Qdrant
  ↓
检索
  ↓
rerank 可选
  ↓
生成回答
  ↓
引用来源
```

RAG 数据要求：

| 字段 | 说明 |
|---|---|
| documentId | 文档 ID |
| chunkId | 切片 ID |
| tenantId | 租户 |
| sourceType | 来源类型 |
| sourceUri | 来源地址 |
| title | 标题 |
| content | 切片内容 |
| metadata | 业务元数据 |
| embeddingModel | 向量模型 |
| createdAt | 创建时间 |

RAG 回答要求：

1. 必须返回引用来源。
2. 检索不到资料时不能编造。
3. 不同租户的知识库必须隔离。
4. 删除文档时必须同步删除向量。
5. 重要知识库需要重建索引任务。

### 10. 异步任务与工作流规范

#### 10.1 适合异步化的任务

以下任务不得阻塞 API 请求：

1. AI 生成。
2. RAG 入库。
3. 文件解析。
4. 图片、音频、视频处理。
5. 批量导入导出。
6. 群发、通知、消息同步。
7. 第三方接口批量拉取。
8. 定时报表和统计。

#### 10.2 任务结构

```ts
type JobPayload = {
  tenantId: string
  userId?: string
  traceId: string
  type: string
  data: unknown
}
```

规则：

1. 任务必须可重试。
2. 任务必须记录状态。
3. 任务必须有 traceId。
4. 长任务必须提供进度查询。
5. 失败任务必须可人工重跑。
6. 批量任务必须支持分片处理。

#### 10.3 状态规范

```text
PENDING
RUNNING
SUCCEEDED
FAILED
CANCELED
RETRYING
```

## 四、前端 UI 与文件素材

### 11. 前端 UI 规范

#### 11.1 UI 总原则

1. 统一使用 Ant Design。
2. 统一通过 `packages/ui` 输出布局、主题和业务组件。
3. 页面禁止随意自造基础控件。
4. 业务页面优先追求清晰、稳定、高效。
5. 企业后台不做营销页风格，不堆叠大面积装饰。
6. 所有页面必须具备 loading、empty、error 状态。

#### 11.2 标准布局

统一后台布局：

```text
AppShell
├─ Sidebar
├─ Header
│  ├─ Breadcrumb
│  ├─ GlobalSearch 可选
│  ├─ Notification
│  └─ UserMenu
└─ Content
```

页面类型：

| 页面类型 | 标准结构 |
|---|---|
| 列表页 | 筛选区 + 操作区 + 表格 + 分页 |
| 详情页 | 基础信息 + Tab + 时间线/日志 |
| 编辑页 | 表单 + 底部操作栏 |
| 工作台 | 指标卡 + 趋势图 + 待办列表 |
| 审批页 | 内容预览 + 审核意见 + 操作按钮 |
| AI 面板 | 输入区 + 生成结果 + 引用来源 + 应用按钮 |

#### 11.3 标准组件

`packages/ui` 至少沉淀：

```text
AppShell
PageHeader
SearchForm
DataTable
StatusTag
ActionBar
ConfirmButton
DrawerForm
DetailDescriptions
AuditTimeline
MetricCard
EmptyState
ErrorState
AiAssistantPanel
FileUploader
PermissionGate
```

#### 11.4 Ant Design 使用规则

1. 表格统一使用 `Table`。
2. 表单统一使用 `Form`。
3. 操作按钮统一使用 `Button`。
4. 删除操作必须使用 `Popconfirm` 或 `Modal.confirm`。
5. 枚举状态统一使用 `Tag`。
6. 复杂筛选使用 `Form + Collapse`。
7. 多步骤流程使用 `Steps`。
8. 抽屉适合轻量编辑，复杂编辑使用独立页面。
9. 弹窗只用于确认和短表单，不承载复杂工作流。

#### 11.5 主题 Token

统一在 `packages/ui/theme` 管理：

```ts
export const theme = {
  token: {
    colorPrimary: '#1677ff',
    borderRadius: 6,
    fontSize: 14,
  },
}
```

禁止：

1. 页面内随意写主色。
2. 同一状态使用多个颜色。
3. 使用不统一的圆角、阴影、字号。
4. 使用过度装饰性背景影响信息密度。

#### 11.6 状态和交互

每个页面必须处理：

| 状态 | 要求 |
|---|---|
| Loading | 骨架屏或 Spin |
| Empty | 空状态说明和主要操作 |
| Error | 错误提示和重试 |
| No Permission | 无权限说明 |
| Offline/Network Error | 网络异常提示 |

### 12. 文件与素材规范

#### 12.1 文件存储原则

1. 数据库存文件元数据，不直接存大文件。
2. 生产环境使用对象存储。
3. 文件访问通过后端签名或权限校验。
4. 文件删除默认软删除。
5. 重要文件必须记录上传人、来源、授权状态。

#### 12.2 文件元数据

```text
id
tenantId
fileName
fileExt
mimeType
size
storageKey
storageProvider
checksum
uploadedBy
authorizationStatus
createdAt
deletedAt
```

#### 12.3 文件处理

文件上传后异步执行：

1. 安全检查。
2. 元数据解析。
3. 文本抽取。
4. 缩略图生成。
5. AI 标签。
6. RAG 入库，可选。

### 13. 配置与环境变量

#### 13.1 环境文件

```text
.env.example
.env.development
.env.production
```

`.env.example` 必须保留完整变量名和说明，不提交真实密钥。

#### 13.2 标准环境变量

```text
NODE_ENV=
APP_ENV=
APP_PORT=
WEB_PORT=
API_PORT=
WORKER_PORT=

STORAGE_SECRET_KEY=

AI_DEFAULT_PROVIDER=
AI_DEFAULT_MODEL=
AI_API_KEY=

```

#### 13.3 端口规范

开发环境默认：

| 服务 | 端口 |
|---|---|
| API | 3010 |
| Web | 3020 |
| Worker / Workflow | 3030 |
| Qdrant | 6333 |
| Redis | 6379 |
| Postgres | 5432 |

生产环境：

1. 默认只暴露 `APP_PORT`。
2. 应用默认端口可配置，推荐使用 `9016` 作为单应用外部端口。
3. 数据库、Redis、Qdrant 只允许内网访问。

### 14. Docker 部署规范

#### 14.1 容器结构

标准服务：

```text

worker
postgres
redis
qdrant
```

小型部署可以将 `app` 和 `worker` 使用同一镜像、不同启动命令。

#### 14.2 构建流程

```text

  ↓

  ↓

  ↓
```

`/health`：进程是否存活。

### 15. 日志、审计与可观测性

#### 15.1 日志规范

日志必须结构化：

```json
{
  "level": "info",
  "time": "2026-05-18T10:00:00.000Z",
  "traceId": "trace_001",
  "tenantId": "tenant_001",
  "userId": "user_001",
  "message": "resource created"
}
```

#### 15.2 Trace ID

1. 每个请求生成或透传 `traceId`。
2. API、service、worker、AI 调用、第三方接口必须使用同一个 traceId。
3. 错误响应返回 traceId，便于排查。

#### 15.3 审计日志

必须记录：

1. 登录、退出。
2. 权限变更。
3. 新增、修改、删除关键数据。
4. 导入、导出。
5. AI 生成和 AI 应用结果。
6. 第三方配置修改。
7. 批量任务执行。

审计日志字段：

```text
id
tenantId
actorId
action
resourceType
resourceId
before
after
ip
userAgent
traceId
createdAt
```

### 18. 安全规范

#### 18.1 输入安全

1. 所有外部输入必须校验。
2. 富文本必须清洗。
3. 文件上传必须限制类型和大小。
4. 第三方回调必须验签。
5. AI 输出不得直接执行为代码或 SQL。

#### 18.2 数据安全

1. 敏感字段加密或脱敏。
2. 导出必须检查权限。
3. 生产数据不得直接复制到本地。
4. 日志不得打印密钥、Token、密码。
5. 软删除数据的恢复和彻底删除必须有权限限制。

#### 18.3 接口安全

1. 登录、模型调用、导出接口必须限流。
2. 批量接口必须限制最大数量。
3. Webhook 必须校验来源。
4. 内部接口不得暴露公网。

---

### 19. 性能规范

#### 19.1 后端

1. 列表接口必须分页。
2. 高频查询必须建立索引。
3. 大批量处理必须走 worker。
4. 不允许 API 请求中同步处理大文件。
5. 复杂统计优先异步预计算。

#### 19.2 前端

1. 表格必须分页或虚拟滚动。
2. 路由级代码分割。
3. 图片、视频使用懒加载。
4. 大表单拆分步骤或分组。
5. 请求状态必须可见。

#### 19.3 AI

1. 长文本必须分片。
2. 重复请求应做缓存或结果复用。
3. 批量生成必须走队列。
4. RAG 检索结果数量要限制。
5. 模型超时必须有降级策略。

### 25. 架构边界总结

统一底座负责：

1. 工程结构。
2. 登录权限。
3. API 规范。
4. 数据库规范。
5. UI 规范。
6. AI/RAG 封装。
7. Worker 任务。
8. 日志审计。
9. Docker 部署。

业务项目负责：

1. 定义业务对象。
2. 定义业务流程。
3. 定义页面菜单。
4. 定义权限点。
5. 定义 AI 使用场景。
6. 定义数据看板指标。

最终目标是让所有系统都像同一个工程体系中长出来的产品：结构一致、体验一致、部署一致、质量一致，但业务能力可以灵活扩展。
