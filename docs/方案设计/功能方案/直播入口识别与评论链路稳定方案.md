# 直播入口识别与评论链路稳定方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修复直播任务和直播评论任务无法稳定进入目标直播间的问题，并保证视频、直播、直播评论完整链路可观测、可停止、可验收。

**Architecture:** 手机端入口恢复层按任务类型分流，直播任务不再复用视频搜索后的首个视频入口。直播间进入采用“搜索结果页直播卡片识别 + 几何点击 + 进入后校验”的闭环，后台用明确原因码展示真实失败位置。

**Tech Stack:** Auto.js 手机端脚本、抖音搜索结果页可访问节点、OCR/可见文本、后台命令与运行日志、心跳状态、`live_comment_actions` 审计记录。

---

## 1. 背景与来源

2026-07-01 联调中，三台已安装 `1.0.20` 的手机可以执行视频采集链路，但切换到直播和直播评论后出现以下现象：

1. 视频任务可以进入抖音视频页、采集评论并上传候选记录。
2. 切到普通直播任务后，手机停留在搜索结果页或视频详情上下文，运行日志反复出现 `live_scan`、`no_live_entry`，`liveRoomEnteredCount=0`。
3. 切到直播评论任务后，后台命令先显示已接受，但手机端后续出现 `launch_flow_aborted`，没有产生 `live_comment_actions`。
4. 用户截图显示，目标直播入口主要在搜索“综合”页内：
   - 两列卡片流中，卡片右上角显示“直播中”。
   - 用户模块中，目标账号下方有大直播卡片，右上角显示“直播中”，卡片文案为“xxx正在直播”。

本方案只处理直播入口、直播评论进入目标房间、日志状态和链路验收。不处理评论话术扩展、私信、关注、点赞、绕过平台限制等能力。

## 2. 核心结论

当前失败不是单纯点击位置不准，而是入口链路错误。

手机端当前入口流中，普通 `live` 任务在 `search` 模式下会走 `enterSearchFlow()`，该流程会调用 `openFirstVideoFromSearch()`，本质是视频入口。直播扫描随后只能在视频页或视频搜索结果上下文中查找直播信号，所以经常得到 `no_live_entry`。

直播评论任务虽然有 `openTargetLiveRoomFromSearch()`，但其失败信息没有完整上报到后台。后台只能看到 `launch_flow_aborted`，无法区分“目标账号没搜到”“目标没开播”“直播卡片识别不到”“点击后未进入直播间”“进入后不是目标房间”。

## 3. 变更范围

### 3.1 手机端

需要调整以下文件的职责边界：

| 文件 | 现状问题 | 调整方向 |
|---|---|---|
| `mobile-agent/autojs/app/collector-app.js` | `live` 任务可能复用视频搜索入口 | `enterFlow()` 按任务类型分流，`live` 和 `live_comment` 不再走 `openFirstVideoFromSearch()` |
| `mobile-agent/autojs/platforms/douyin.js` | 目标直播搜索已有雏形，但识别和失败上报不够稳定 | 新增或重构直播卡片候选识别、几何点击、点击后校验 |
| `mobile-agent/autojs/app/phase-runner.js` | 直播扫描依赖 `liveScorer`，在未进入直播间时容易只滑动不进入 | 对搜索页直播入口和直播间内采样分层处理 |
| `mobile-agent/autojs/domain/live-scorer.js` | `hasLiveEntry` 依赖强文本，无法覆盖所有卡片样式 | 将“直播中”“正在直播”“头像直播标识”作为强入口信号 |

### 3.2 后台与日志

需要调整以下方向：

1. 命令结果不能只显示“accepted”，必须能看到后续业务执行结果。
2. 运行日志必须记录每一步入口候选、点击点、校验结果和失败原因。
3. 心跳中 `currentTask`、`rawPayload.currentTaskType`、后台展示状态必须一致。
4. `live_comment_actions` 应记录未进入直播间的失败动作，避免“没有记录就不知道发生了什么”。

## 4. 不变范围

1. 不新增关注、点赞、私信、下单等真实互动。
2. 不绕过验证码、登录异常、风控弹窗。
3. 不把普通直播采集和直播评论合并成一个任务。
4. 不在目标直播间未确认时发送真实评论。
5. 不在任务结束后继续随机滑动、随机点击或继续浏览抖音。

## 5. 直播入口识别策略

### 5.1 指定直播间评论任务

指定直播间评论任务使用确定性路径：

```text
读取 targetRoom
-> 使用 anchorName 或抖音号搜索
-> 停留在综合页
-> 识别目标账号和直播卡片
-> 点击直播入口
-> 校验是否进入目标直播间
-> 采样直播上下文和评论区
-> 生成并执行评论计划
```

第一阶段默认只在“综合”页识别目标直播入口。只有当综合页无法覆盖真实样式，并且配置明确允许时，才进入“用户”tab 或“直播”tab 作为兜底。

### 5.2 搜索综合页的两类主入口

#### 类型 A：两列卡片流直播入口

识别特征：

1. 卡片右上角存在“直播中”标识。
2. 卡片下方或卡片附近存在账号名、标题、点赞数、观看人数等文本。
3. 卡片标题或账号名命中 `anchorName`、`titleKeywords`、`roomKeywords` 中任一目标词。

点击策略：

1. 先取“直播中”标识的 bounds。
2. 根据 bounds 向左、向下反推卡片矩形。
3. 优先点击卡片画面中上部，不点击底部导航、评论浮层、筛选按钮。
4. 点击后等待直播间标识出现，再做目标房间校验。

失败处理：

| 失败点 | 原因码 |
|---|---|
| 找不到“直播中”标识 | `target_live_badge_not_found` |
| 找到直播标识但账号或标题不匹配 | `target_live_card_not_matched` |
| 点击后仍停留搜索页 | `target_live_card_click_no_transition` |
| 进入页面但不是直播间 | `target_live_room_not_visible` |

#### 类型 B：用户模块 + 大直播卡片入口

识别特征：

1. “用户”模块中出现目标账号名。
2. 用户头像有直播环或“直播”标识。
3. 目标用户块下方存在大直播卡片。
4. 大直播卡片右上角有“直播中”，或卡片文案包含“正在直播”。

点击策略：

1. 先定位目标用户块 bounds。
2. 在用户块下方查找大卡片 bounds。
3. 优先点击大卡片中部或右上角直播标识附近。
4. 如果大卡片点击失败，再尝试点击头像直播环。
5. 每个候选点只尝试一次，失败后回退并记录原因。

失败处理：

| 失败点 | 原因码 |
|---|---|
| 找到目标用户但无直播信号 | `target_user_not_live` |
| 找到目标用户和直播卡片但点击失败 | `target_user_live_card_click_failed` |
| 点击头像直播环失败 | `target_avatar_live_click_failed` |

### 5.3 普通直播任务

普通 `live` 任务不应从搜索页首个视频进入。

推荐路径：

```text
启动普通直播任务
-> 进入抖音推荐上下文
-> 优先进入直播 Feed 或搜索直播结果
-> 识别农业相关直播卡片
-> 进入直播间
-> 停留采样并上报记录
-> 退出直播间或切换下一个候选
```

如果任务配置要求搜索关键词，则搜索后优先进入“直播”结果或在“综合”页识别直播卡片，不允许调用 `openFirstVideoFromSearch()`。

## 6. 进入后校验

点击任何入口后，必须完成校验再进入评论逻辑。

| 校验项 | 作用 |
|---|---|
| 页面是否为直播间 | 防止进入普通视频、用户主页、合集页 |
| 主播名是否匹配 | 防止进入同名或推荐直播间 |
| 标题关键词是否匹配 | 防止账号名近似但直播内容错误 |
| 评论输入区是否存在 | 确认可以进入评论流程 |
| 是否存在验证码、登录异常、风控提示 | 出现异常时停止自动动作 |

校验失败时：

1. 不发送评论。
2. 上报明确原因码。
3. 能回退到搜索页则回退，不能回退则结束任务。
4. 达到重试上限后，任务转为失败或暂停，不继续乱点。

## 7. 日志与状态改造

### 7.1 运行日志字段

直播入口相关日志至少包含：

| 字段 | 示例 |
|---|---|
| `phase` | `target_live_search`、`target_live_card_scan`、`target_live_click`、`target_live_verify` |
| `taskType` | `live`、`live_comment` |
| `keyword` | 搜索词 |
| `candidateType` | `grid_live_card`、`user_large_live_card`、`avatar_live_entry` |
| `candidateText` | 候选卡片附近可见文本摘要 |
| `clickPoint` | `{x, y}` |
| `result` | `matched`、`clicked`、`verified`、`failed` |
| `reason` | 明确失败原因码 |

### 7.2 命令状态

后台命令的 `DONE` 只能表示“命令已被手机接收”，不能表示“直播评论已成功执行”。

需要增加业务结果展示：

| 状态 | 含义 |
|---|---|
| `command_accepted` | 手机已收到命令 |
| `target_searching` | 正在搜索目标直播间 |
| `target_found` | 已找到目标直播入口 |
| `room_entered` | 已进入直播间 |
| `room_verified` | 已确认目标直播间 |
| `comment_planned` | 已生成评论计划 |
| `comment_sent` | 已真实发送 |
| `comment_skipped` | 因配置或安全原因跳过 |
| `failed` | 任务失败，必须带原因码 |

### 7.3 心跳状态

心跳、后台列表和详情页必须使用同一套任务状态：

```text
idle
running_video
running_live
running_live_comment
paused
stopping
stopped
failed
```

不得出现 raw payload 是 `live_comment`，后台主状态却显示 `none` 的情况。

## 8. 任务结束行为

视频、直播、直播评论任一任务结束后必须进入明确收尾流程：

```text
停止当前自动动作
-> 上报最终状态和原因
-> 写入任务结束日志
-> 关闭或退出抖音
-> Agent 回到待命
```

以下情况必须停止自动动作：

1. 达到任务时长或采集数量。
2. 后台下发 STOP。
3. 任务切换。
4. 直播评论目标不可达。
5. 出现验证码、登录异常、风控弹窗。
6. 连续入口失败达到上限。

停止后不允许继续搜索、滑动、点击直播卡片或停留在抖音里继续动作。

## 10. 完整链路验收

### 10.1 单任务验收

| 任务 | 验收标准 |
|---|---|
| 视频 | 可以搜索、进入视频、采集评论、上传记录、结束后退出抖音 |
| 普通直播 | 可以进入直播入口、进入直播间、采样、上传记录、结束后退出抖音 |
| 直播评论 | 可以搜索目标主播、识别直播卡片、进入目标直播间、生成动作记录、按配置发送或跳过 |

### 10.2 串联验收

固定顺序：

```text
START video
-> 等视频任务完成或手动 STOP
-> START live
-> 等直播任务完成或手动 STOP
-> START live_comment
-> 等直播评论任务完成或失败
-> 检查手机已退出抖音且 Agent 待命
```

必须记录：

1. 每台设备的命令 ID。
2. 每个任务的开始、入口选择、候选识别、点击、校验、结束日志。
3. `collection_records` 是否有视频和直播记录。
4. `live_comment_actions` 是否有计划、跳过、发送或失败记录。
5. 任务结束后是否关闭抖音。

### 10.3 失败验收

| 场景 | 预期 |
|---|---|
| 目标主播未开播 | 不乱点，显示 `target_user_not_live` |
| 搜索结果无目标账号 | 不无限滑动，显示 `target_not_found` |
| 有直播卡片但点击失败 | 不进入评论，显示 `target_live_card_click_failed` |
| 进入非目标直播间 | 退出并显示 `target_live_room_not_matched` |
| 出现验证码或风控 | 停止任务并显示 `risk_control` |
| 后台 STOP | 立即停止动作，退出抖音并待命 |

## 11. 优先级

| 优先级 | 内容 | 原因 |
|---|---|---|
| P0 | `live` 入口不再复用视频入口 | 当前普通直播无法稳定进入直播间的根因 |
| P0 | 目标直播间搜索综合页卡片识别 | 直接覆盖用户截图中的真实入口样式 |
| P0 | 点击后校验和失败原因上报 | 防止误入、误评论、无法排查 |
| P0 | 任务结束关闭抖音并待命 | 防止任务结束后继续乱点 |
| P1 | 后台业务状态拆分 | 解决命令 DONE 但业务失败的误导 |
| P1 | 心跳状态统一 | 解决后台显示和手机实际任务不一致 |
| P2 | OCR 兜底识别直播 badge | 当可访问节点拿不到“直播中”时再启用 |

## 12. 暂不处理内容

1. 不优化评论话术质量。
2. 不增加真实互动类型。
3. 不修改账号画像配置结构。
4. 不新增大规模调度系统。
5. 不在没有目标直播间确认的情况下做任何真实发送。

## 13. 执行顺序建议

1. 先完成 Task 1、Task 2、Task 3，让手机能稳定进入目标直播间。
2. 再完成 Task 4，保证进入后不会误判。
3. 再完成 Task 5，让后台能解释每一次失败。
4. 最后完成 Task 6 和完整链路验收，确保任务结束不继续动作。

第一轮实现只需要覆盖搜索“综合”页中的两种入口样式。只有这两种入口稳定后，再考虑 OCR 兜底和更多抖音页面变体。
