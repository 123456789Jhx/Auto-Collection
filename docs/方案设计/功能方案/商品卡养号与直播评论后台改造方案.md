# 商品卡养号与直播评论后台改造方案

> 状态：后台专项实施方案，尚未实现。
> 关联业务方案：`商品卡养号与直播评论组合任务方案.md`、`商品卡片直播间评论.md`。
> 范围：只定义后台、Web 管理端、API 下发、日志审计和兼容迁移改动，不展开手机端页面操作实现。

## 1. 目标与结论

本文回答“后台怎么改”，不是重新写手机端执行流程。

后台需要承担四件事：

1. 作为商品卡养号、目标直播间评论、直播养号2的配置来源。
2. 在保存配置时完成字段校验和旧配置归一化，避免把错误 JSON 直接下发到手机。
3. 在手机拉取当前任务时下发结构化 `commerce_card_live_comment` 配置，并处理目标中心配置和旧设备配置的优先级。
4. 记录真实评论动作、跳过原因、运行关键事件，后续可以从后台判断任务卡在哪个阶段。

核心结论：

1. 继续使用现有任务类型和特性类型 `commerce_card_live_comment`，不新增新的任务类型。
2. “夏橙”只是默认搜索关键词，后台字段必须支持替换为任意关键词。
3. 一期优先改结构化配置、校验、Web 表单和手机下发，不强制新增数据库运行事件表。
4. 二期再补强任务 assignment、阶段事件、幂等键和暂停恢复快照。
5. 新配置以直播目标中心为主，旧的 `p3ExtensionsConfig.commerceCardLiveComment` 只作为兼容兜底。

## 2. 当前后台基础

| 模块 | 当前能力 | 问题 |
|---|---|---|
| `live_targets` | 已能维护目标直播间主档、名称、平台、相似度和启用状态 | 可以复用 |
| `live_target_aliases` | 已能维护目标直播间别名 | 可以复用 |
| `live_target_feature_configs` | 已能按 `live_comment`、`commerce_card_live_comment` 保存目标特性配置 | `runtime_config_json` 目前过松，缺少第二版字段校验 |
| `live_target_device_bindings` | 已能把目标配置绑定到设备 | 可以复用 |
| `device_task_assignments` | 已有任务下发、状态、期望 payload 和时间字段 | 一期可不动，二期用于阶段恢复和事件归属 |
| `live_comment_actions` | 已能记录评论发送、跳过和失败 | 一期可复用，二期补 `assignmentId`、`targetId`、`stage`、`idempotencyKey` |
| `live-target-config.service.ts` | 已有目标、别名、特性配置 schema 和旧任务配置转目标配置函数 | `runtimeConfig: z.record(z.unknown())` 无法约束配置 |
| `live-target.repository.ts` | 已能保存目标配置并向移动端组装 `liveTargets` | 需要统一保存前归一化和下发前归一化 |
| `mobile.service.ts` | 手机拉取当前任务时会合并旧配置生成的 `deviceLiveTargets` 和目标中心 `publicLiveTargets` | 当前直接拼接，容易重复下发同一商品卡任务 |
| `LiveTargetsPage.tsx` | 已有直播目标、搜索直播评论、商品卡直播评论、设备绑定 tab | 商品卡页面目前只覆盖少量一版字段 |
| `live-comment-config.ts` | 已有 P3 默认配置和 JSON 解析 | 默认字段仍是一版口径，需要兼容第二版 |

## 3. 一期后台改造边界

一期目标是让后台可以正确配置和下发第二版业务，不要求一次性完成完整运行态恢复。

一期必须完成：

1. 商品卡组合任务配置结构化。
2. 后台 API 保存配置时严格校验。
3. Web 页面从“少量输入 + 高级 JSON”改成阶段化表单。
4. 手机拉取任务时下发 `configVersion=2` 的结构化配置。
5. 目标中心配置和旧设备 JSON 去重，目标中心优先。
6. 保留旧 APK 兼容字段，避免已安装旧版本直接失效。
7. 评论动作继续写入 `live_comment_actions`。

一期暂不做：

1. 不新增独立运行事件表。
2. 不实现后台层面的完整 PAUSE/RESUME 阶段快照恢复。
3. 不强制迁移生产历史 JSON。
4. 不删除 `p3ExtensionsConfig.commerceCardLiveComment`。
5. 不把高级 JSON 作为主要配置入口。

## 4. 配置模型

配置继续落在直播目标中心：

- `live_target_feature_configs.feature_type = commerce_card_live_comment`
- `search_keywords_json`：商城搜索词，默认可以是 `["夏橙"]`，但必须可编辑。
- `product_keywords_json`：商品卡关键词，例如 `["秭归", "夏橙"]`。
- `live_signals_json`：直播标识，例如 `["直播中", "讲解中"]`。
- `required_keywords_json`：进入目标直播间前必须命中的词。
- `forbidden_keywords_json`：禁止进入或禁止评论的词。
- `runtime_config_json`：第二版运行参数。

推荐的 `runtime_config_json`：

```json
{
  "configVersion": 2,
  "enabledStages": ["product_nurture", "target_comment"],
  "executeEnabled": false,
  "manualExecutionApproved": false,
  "recommendationSignals": ["你可能还会喜欢"],
  "productCardDwellSeconds": 120,
  "productNurtureRoundMinutes": 15,
  "productNurtureMaxRounds": 3,
  "targetLiveMaxRoomsPerRefresh": 25,
  "targetCommentSearchMaxActiveMinutes": 60,
  "maxCommentsPerRoom": 1,
  "commentPool": ["111", "666"],
  "liveNurtureKeywords": [],
  "liveNurtureRefreshAfterRooms": 10,
  "liveNurtureWatchMinMinutes": 10,
  "liveNurtureWatchMaxMinutes": 20,
  "liveNurtureTotalMinMinutes": 70,
  "liveNurtureTotalMaxMinutes": 100,
  "taskMaxActiveMinutes": 240
}
```

字段说明：

| 字段 | 用途 | 默认值 |
|---|---|---|
| `configVersion` | 配置版本，第二版固定为 `2` | `2` |
| `enabledStages` | 启用阶段，可选 `product_nurture`、`target_comment`、`live_nurture` | `["product_nurture", "target_comment"]` |
| `executeEnabled` | 是否允许真实执行评论动作 | `false` |
| `manualExecutionApproved` | 是否已经人工确认真实执行范围 | `false` |
| `recommendationSignals` | 商品详情页推荐区识别词 | `["你可能还会喜欢"]` |
| `productCardDwellSeconds` | 单个商品卡详情浏览时长 | `120` |
| `productNurtureRoundMinutes` | 商品卡养号单轮时长 | `15` |
| `productNurtureMaxRounds` | 商品卡养号最大轮次 | `3` |
| `targetLiveMaxRoomsPerRefresh` | 目标直播板块单轮候选扫描上限 | `25` |
| `targetCommentSearchMaxActiveMinutes` | 仅评论阶段主动查找目标的最长时间 | `60` |
| `maxCommentsPerRoom` | 同一房间本轮最多评论数 | `1` |
| `commentPool` | 商品卡目标评论话术池 | `[]` |
| `liveNurtureKeywords` | 直播养号2标题关键词 | `[]` |
| `liveNurtureRefreshAfterRooms` | 直播养号2连续扫描多少个候选后刷新 | `10` |
| `liveNurtureWatchMinMinutes` | 直播养号2单房间最短观看 | `10` |
| `liveNurtureWatchMaxMinutes` | 直播养号2单房间最长观看 | `20` |
| `liveNurtureTotalMinMinutes` | 直播养号2总观看最短 | `70` |
| `liveNurtureTotalMaxMinutes` | 直播养号2总观看最长 | `100` |
| `taskMaxActiveMinutes` | 整体主动执行时长上限，不含人工暂停时间 | `240` |

## 5. 校验规则

后台保存 `commerce_card_live_comment` 时必须做服务端校验，不能只依赖前端。

基础规则：

1. `enabledStages` 至少包含一个阶段。
2. `enabledStages` 只能包含 `product_nurture`、`target_comment`、`live_nurture`。
3. 启用 `live_nurture` 时必须同时启用 `product_nurture`。
4. 启用 `product_nurture` 时，`searchKeywords`、`productKeywords`、`recommendationSignals` 不能为空。
5. 启用 `target_comment` 时，必须存在有效目标直播间主档和至少一个有效别名或目标名。
6. 启用真实评论时，`executeEnabled` 和 `manualExecutionApproved` 必须同时为 `true`，否则只能浏览、跳过或记录。
7. `targetLiveMaxRoomsPerRefresh` 建议限制在 20 到 30。
8. 所有分钟、秒数字段必须是正整数，并设置上限，避免后台误填造成手机端长时间卡死。
9. `liveNurtureWatchMinMinutes <= liveNurtureWatchMaxMinutes`。
10. `liveNurtureTotalMinMinutes <= liveNurtureTotalMaxMinutes`。
11. `commentPool` 必须去空、去重、限制单条长度和条数。

旧字段兼容规则：

| 旧字段 | 新字段 |
|---|---|
| `scanMinutesPerRound` | `productNurtureRoundMinutes` |
| `maxRounds` | `productNurtureMaxRounds` |
| `watchMinutesPerLive` | 保留给旧 APK；第二版不把它当成直播养号2随机观看时长 |
| `matchKeywords` | `productKeywords` |

## 6. API 与服务改造

### 6.1 `live-target-config.service.ts`

新增严格 schema：

1. `commerceCardStageSchema`
2. `commerceCardWorkflowRuntimeConfigSchema`
3. `normalizeCommerceCardWorkflowRuntimeConfig(value)`
4. `parseCommerceCardFeatureConfig(payload)`

改造点：

1. `liveTargetFeatureConfigSchema` 不能继续对所有 `runtimeConfig` 使用 `z.record(z.unknown())`。
2. 当 `featureType === "commerce_card_live_comment"` 时，必须按第二版 schema parse 和归一化。
3. 旧字段必须在 parse 阶段转换为新字段，同时保留必要的旧字段用于旧 APK。
4. `buildMobileLiveTargetConfig()` 输出时，`runtimeConfig` 必须是归一化后的对象。
5. `buildDeviceLiveTargetsFromTaskConfig()` 只作为旧配置兜底，输出 `configVersion=1` 或兼容结构，不能覆盖目标中心第二版配置。

### 6.2 `live-target.repository.ts`

改造点：

1. `upsertLiveTargetFeatureConfig()` 写库前调用归一化函数，避免脏 JSON 落库。
2. `listMobileLiveTargetsForDevice()` 下发前再次归一化，兼容历史已保存配置。
3. 如果历史数据解析失败，接口应返回可定位的错误日志，并跳过该条配置，不应让整台设备拉取任务失败。
4. 设备绑定优先级继续使用 `live_target_device_bindings.priority`。

### 6.3 `mobile.service.ts`

当前逻辑：

```ts
const liveTargets = [...deviceLiveTargets, ...publicLiveTargets];
```

需要改为显式合并：

1. 先读取目标中心 `publicLiveTargets`。
2. 再读取旧设备配置生成的 `deviceLiveTargets`。
3. 如果同一设备已经有目标中心 `commerce_card_live_comment`，则不再下发旧 `p3ExtensionsConfig.commerceCardLiveComment` 生成的商品卡目标。
4. 如果没有目标中心配置，才下发旧设备配置，保证老任务还能跑。
5. 去重键建议使用 `featureType + targetId`，没有 `targetId` 时使用 `featureType + targetCode`。
6. 合并后按设备绑定优先级排序。
7. 返回体继续保留 `commerceCardLiveComment` 和 `p3ExtensionsConfig`，但标记为旧 APK 兼容字段。

下发给新 APK 的主口径：

```json
{
  "liveTargets": [
    {
      "featureType": "commerce_card_live_comment",
      "searchKeywords": ["夏橙"],
      "productKeywords": ["秭归", "夏橙"],
      "liveSignals": ["直播中"],
      "runtimeConfig": {
        "configVersion": 2,
        "enabledStages": ["product_nurture", "target_comment"],
        "productNurtureRoundMinutes": 15,
        "productNurtureMaxRounds": 3
      }
    }
  ]
}
```

### 6.4 共享类型

建议在 `account-data-platform/packages/types/src/api/admin.ts` 或相邻共享类型文件中补充：

1. `CommerceCardWorkflowStage`
2. `CommerceCardWorkflowRuntimeConfig`
3. `MobileLiveTargetConfig`
4. `LiveTargetFeatureType`

前端、API、测试都引用共享类型，避免 `api-client.ts`、页面表单和服务端 schema 各写一套字段。

## 7. Web 管理端改造

主要文件：

- `account-data-platform/apps/web/src/routes/LiveTargetsPage.tsx`
- `account-data-platform/apps/web/src/lib/live-comment-config.ts`
- 必要时补充 `account-data-platform/apps/web/tests/live-targets-page.test.js`

页面结构建议：

1. 目标基础信息：目标名称、平台、相似度、别名、启用状态。
2. 阶段选择：商品卡养号、目标直播评论、直播养号2。
3. 商品卡养号配置：商城搜索词、商品关键词、直播信号、推荐区识别词、单商品停留秒数、单轮分钟、最大轮次。
4. 目标直播评论配置：候选扫描上限、主动查找分钟、每房间评论数、话术池。
5. 直播养号2配置：标题关键词、刷新阈值、单房间观看区间、总观看区间。
6. 真实执行许可：`executeEnabled`、`manualExecutionApproved`，并显示“开启后会真实评论”的确认提示。
7. 设备绑定：复用现有设备绑定 tab。

前端保存规则：

1. 表单值先组装为结构化 payload，再交给 API。
2. 高级 JSON 只能作为排错入口，不作为主要配置入口。
3. 保存前做轻量校验，最终以 API 校验为准。
4. 默认搜索词可以是 `夏橙`，但页面文案不能把它写死成业务唯一关键词。
5. `commentPool`、关键词类字段统一按换行、中文逗号、英文逗号切分，并去空去重。

## 8. 数据库与迁移

一期不需要新增表，因为现有表已经能存配置：

- `live_targets`
- `live_target_aliases`
- `live_target_feature_configs`
- `live_target_device_bindings`
- `live_comment_actions`

一期需要的是代码层归一化，而不是立即改表。

二期建议数据库改造：

1. 在 `device_task_assignments` 中补充阶段运行快照字段，或把快照放入 `desired_payload` 的规范结构中。
2. 新增 `device_task_assignment_events`，记录阶段切换、暂停、恢复、刷新、命中、跳过、失败。
3. 扩展 `live_comment_actions`：
   - `assignment_id`
   - `target_id`
   - `stage`
   - `idempotency_key`
4. 对 `idempotency_key` 建唯一约束，防止同一运行、同一目标、同一房间重复评论。

二期事件表建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `assignment_id` | 任务下发记录 |
| `device_id` | 设备 |
| `target_id` | 目标直播间，可空 |
| `feature_type` | `commerce_card_live_comment` |
| `stage` | 当前阶段 |
| `event_type` | 事件类型 |
| `status` | `started`、`succeeded`、`failed`、`skipped` 等 |
| `reason` | 失败或跳过原因 |
| `payload_json` | 原始上下文 |
| `occurred_at` | 发生时间 |

## 9. 日志、审计与排查

一期日志口径：

1. 手机端仍通过现有运行日志上传关键步骤。
2. 后台日志中心展示现有 runtime log。
3. 评论发送、跳过、失败继续写入 `live_comment_actions`。
4. API 保存配置失败时返回字段级错误，便于从页面直接修正。

必须能从后台判断：

1. 当前下发的是目标中心配置还是旧设备 JSON 兜底。
2. 下发配置版本是 `configVersion=1` 还是 `configVersion=2`。
3. 商品卡任务是否因为双开关未打开而跳过评论。
4. 没有找到目标直播间时，是商品卡养号轮次耗尽，还是目标评论主动查找超时。
5. 评论失败是输入框、发送按钮、目标二次校验、风控还是接口上报问题。

二期再把这些日志整理成结构化事件表，支持后台按阶段过滤。

## 10. 兼容策略

旧 APK 兼容：

1. 保留 `commerceCardLiveComment` 顶层字段。
2. 保留 `p3ExtensionsConfig.commerceCardLiveComment`。
3. 保留旧字段 `scanMinutesPerRound`、`watchMinutesPerLive`、`maxRounds`、`matchKeywords`。
4. 旧 APK 不认识 `enabledStages` 时仍按一版流程执行。

新 APK 口径：

1. 优先读取 `liveTargets[]` 中 `featureType=commerce_card_live_comment` 的配置。
2. 如果 `runtimeConfig.configVersion === 2`，按第二版阶段执行。
3. 如果没有第二版配置，再回退旧字段。

后台兼容：

1. 目标中心配置优先。
2. 旧设备 JSON 只在没有目标中心商品卡配置时生成兜底目标。
3. Web 页面保存第二版配置后，不自动删除旧设备 JSON。
4. 后续确认所有设备升级后，再清理旧字段。

## 11. 实施顺序

推荐按以下顺序开发：

1. 在 `packages/types` 增加共享类型。
2. 在 `live-target-config.service.ts` 增加第二版 schema、归一化和旧字段映射。
3. 改造 `live-target.repository.ts` 的保存和下发归一化。
4. 改造 `mobile.service.ts` 的 `liveTargets` 合并和旧配置兜底规则。
5. 改造 `LiveTargetsPage.tsx`，把商品卡配置改成阶段化表单。
6. 更新 `live-comment-config.ts` 默认值和兼容解析。
7. 增加 API、Web 页面和配置归一化测试。
8. 再启动手机端第二版 runner 改造。
9. 真机验证通过后，再考虑二期运行事件表和幂等增强。

## 12. 验收口径

后台一期验收通过条件：

1. 后台能创建一个 `commerce_card_live_comment` 目标配置，搜索词不是 `夏橙` 时也能保存并下发。
2. 启用商品卡养号后，API 下发包含 `configVersion=2`、`enabledStages`、商品卡浏览时长、轮次和推荐区识别词。
3. 启用目标评论后，API 下发包含目标名、别名、相似度、评论池、双开关。
4. 目标中心配置和旧 `p3ExtensionsConfig` 同时存在时，手机拉取结果只有一个有效商品卡配置，以目标中心为准。
5. 未打开 `executeEnabled` 或 `manualExecutionApproved` 时，配置仍可下发，但真实评论必须处于禁止状态。
6. 错误配置保存失败时，前端能看到明确字段错误。
7. 老配置仍能被旧 APK 拉取，不出现任务配置空白。

后台一期不通过条件：

1. 仍需要主要依赖高级 JSON 才能配置第二版流程。
2. `liveTargets` 中重复下发同一商品卡任务。
3. `夏橙` 被写死在后台逻辑中，无法替换。
4. 后台允许保存负数、超大时长、空阶段、空搜索词等明显错误配置。
5. 真实评论开关未双重确认时仍可能下发为可发送状态。
6. 新配置导致旧 APK 拉取任务失败。
