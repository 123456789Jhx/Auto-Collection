# 商品卡养号与直播评论后台改造方案

> 状态：后台专项实施方案，待确认，尚未实现。
> 关联业务方案：`商品卡养号与直播评论组合任务方案.md`、`商品卡片直播间评论.md`。
> 配合规则：组合任务方案定义业务流程和运行安全底线，本文定义后台落地方式；两者冲突时以组合任务方案为准。
> 范围：只定义后台、Web 管理端、API 下发、运行归属、日志审计和兼容迁移，不展开手机端页面操作细节。

## 1. 目标与结论

本文回答“后台怎么改”，不是重新写手机端执行流程。

后台需要承担五件事：

1. 作为商品卡养号、目标直播间评论、直播养号2的配置来源。
2. 在保存配置时完成字段校验和旧配置归一化，避免把错误 JSON 直接下发到手机。
3. 在手机拉取当前任务时下发结构化 `commerce_card_live_comment` 配置，并处理目标中心配置和旧设备配置的优先级。
4. 为每次运行冻结目标、配置修订和完整配置快照，不能让运行中配置修改改变已启动任务。
5. 记录 assignment 状态、阶段事件、真实评论副作用和跳过原因，使后台能判断任务卡在哪个阶段并安全恢复。
6. 把 assignment 和控制命令拆成一对多关系，确保 PAUSE、RESUME、STOP 操作同一运行且命令回执不覆盖业务终态。
7. 把真实评论审批、全局急停和发送许可从普通运行 JSON 中拆出，形成可实时撤销、可限额、可审计的安全覆盖层。

核心结论：

1. 继续使用现有任务类型和特性类型 `commerce_card_live_comment`，不新增新的任务类型。
2. “夏橙”只是默认搜索关键词，后台字段必须支持替换为任意关键词。
3. 配置准备可以先部署，但只能保存、校验和预览第二版配置；在运行安全门槛完成前，`commerceCardWorkflowV2Enabled` 必须保持关闭。
4. 第二版无评论灰度前必须完成同一 assignment 状态流转、不可变配置快照、阶段事件、checkpoint v2、版本能力门禁和在途任务停止语义。
5. 真实评论开放前必须完成评论幂等唯一约束、评论副作用状态、审批绑定配置修订和全局急停开关，不能推迟到上线后补。
6. 新配置以直播目标中心为主，旧的 `p3ExtensionsConfig.commerceCardLiveComment` 只作为显式第一版兼容，不自动把第二版流程降级成第一版执行。
7. START 创建一次 assignment；所有后续控制命令写入 `mobile_commands` 并关联原 assignment，现有单一 `device_task_assignments.command_id` 不再承担完整控制历史。
8. 第二版真实评论只接受服务端原子预占后签发的短时发送许可；手机断网、许可过期、稳定 roomKey 缺失或账号身份不一致时必须 fail closed。

两份方案的对应关系：

| 组合任务方案要求 | 后台实现责任 |
|---|---|
| `enabledStages` 与阶段参数 | 严格 schema、阶段化表单、保存归一化 |
| 目标直播间门禁 | 目标主档、别名、绑定、选中目标快照 |
| PAUSING/PAUSED/RESUMING | 同一 assignment 状态流转和稳定检查点回执 |
| 评论幂等 | assignment 归属、服务端预占、唯一幂等键和动作状态 |
| 配置不可变 | `revision`、`config_hash`、`config_snapshot` |
| 实时撤销 | 运行时功能控制、独立执行审批和短时发送许可 |
| 命令历史 | assignment 一对多 command、命令序号和状态版本 |
| 旧 APK 兼容 | 能力上报、版本门禁、V1/V2 单一有效口径 |
| 灰度和回退 | 功能开关、设备 allowlist、在途任务取消和审计保留 |

## 3. 分阶段后台改造边界

### 3.1 阶段 A：配置准备

阶段 A 可以独立部署，但不能创建可执行的第二版 assignment。

必须完成：

1. 商品卡组合任务配置结构化和严格校验。
2. Web 页面从少量字段或高级 JSON 改成阶段化表单。
3. 生成 `configVersion=2` 的预览 payload，并显示字段级错误。
4. 目标中心配置与旧设备 JSON 建立明确来源优先级。
5. 补齐共享 `MobileLiveTargetConfig` 和第二版运行配置契约。
6. `commerceCardWorkflowV2Enabled=false`，任务启动接口拒绝 V2 START/RESUME。
7. 建立默认关闭的运行时功能控制、设备 allowlist、最低版本和 capability 持久化；开关修改必须有审计。

### 3.2 阶段 B：无评论灰度

阶段 B 用于关闭真实评论的真机流程验证，必须完成：

1. START 创建 assignment 并冻结 selectedTarget、expectedAccount、configRevision、configHash、snapshotHash、expiresAt 和完整 configSnapshot。
2. PAUSE、RESUME、STOP 引用同一 assignment，不再为控制命令创建新运行；命令表增加 assignment 外键和单调序号。
3. 完成 assignment 状态机、stateVersion 乐观锁、每设备单一非终态运行约束、阶段事件、progress/complete 回执和 checkpoint v2 对账。
4. 设备上报第二版能力，后台按版本、capability 和 allowlist 决定是否允许启动。
5. `commerceCardRealCommentEnabled=false`，服务端和手机端均强制真实发送无效。
6. 关闭 V2 或移出 allowlist 时拒绝新 START/RESUME，并停止在途 V2 运行。

### 3.3 阶段 C：受控真实评论

阶段 C 开启前必须完成：

1. `live_comment_actions` 关联 assignment、目标、账号、稳定 roomKey、comment slot 和稳定幂等键。
2. 评论动作至少支持 `planned`、`submitting`、`submitted`、`sent`、`unknown`、`failed`、`skipped`，并使用 action stateVersion 约束转换。
3. 新增 reserve/update/query/resolve 接口；点击发送前完成服务端原子预占、本地 pendingSideEffect 和短时许可校验。
4. 新增独立执行审批，绑定配置哈希、设备、预期抖音账号、目标、评论池哈希、单房上限、总额度、日上限和有效期；审批可实时撤销。
5. 全局 `commerceCardRealCommentEnabled`、当前 `executeEnabled`、审批状态/额度、assignment 状态、账号、稳定 roomKey 和许可有效期在每次副作用前动态检查。
6. `unknown` 动作使 assignment 进入非终态 BLOCKED；后台人工确认原动作后才能显式 RESUME 或 STOP。

### 3.4 后续运营增强

可以延后：

1. 历史 JSON 批量迁移和旧字段清理。
2. 跨运行统计报表、自动重试控制台和高级筛选。
3. 更丰富的运行证据归档和趋势分析。
4. 高级 JSON 继续只读保留一个稳定 APK 版本周期。

## 4. 配置模型

### 4.1 业务运行配置

配置继续落在直播目标中心：

- `live_target_feature_configs.feature_type = commerce_card_live_comment`
- `search_keywords`：商城搜索词，默认可以是 `["夏橙"]`，但必须可编辑。
- `product_keywords`：商品卡关键词，例如 `["秭归", "夏橙"]`。
- `required_keywords`：进入目标直播间前必须命中的词。
- `forbidden_keywords`：禁止进入或禁止评论的词。
- `live_signals`：只服务第一版兼容，第二版目标入口不再依赖商品卡直播标识。
- `runtime_config_json`：第二版运行参数。

推荐的 `runtime_config_json`：

```json
{
  "configVersion": 2,
  "enabledStages": ["product_nurture"],
  "executeEnabled": false,
  "recommendationSignals": ["你可能还会喜欢"],
  "productCardDwellSeconds": 120,
  "productNurtureRoundMinutes": 15,
  "productNurtureMaxRounds": 3,
  "targetLiveMaxRoomsPerRefresh": 25,
  "targetCommentSearchMaxActiveMinutes": 60,
  "maxCommentsPerRoom": 1,
  "commentPool": [],
  "liveNurtureKeywords": [],
  "liveNurtureRefreshAfterRooms": 10,
  "liveNurtureWatchMinMinutes": 10,
  "liveNurtureWatchMaxMinutes": 20,
  "liveNurtureTotalMinMinutes": 70,
  "liveNurtureTotalMaxMinutes": 100,
  "taskMaxActiveMinutes": 240
}
```

字段说明：

| 字段 | 用途 | 默认值 |
|---|---|---|
| `configVersion` | 配置版本，第二版固定为 `2` | `2` |
| `enabledStages` | 启用阶段，可选 `product_nurture`、`target_comment`、`live_nurture` | `["product_nurture"]` |
| `executeEnabled` | 目标功能的实时发送开关；评论预占时读取当前值，可即时阻断后续发送 | `false` |
| `recommendationSignals` | 商品详情页推荐区识别词 | `["你可能还会喜欢"]` |
| `productCardDwellSeconds` | 单个商品卡详情浏览时长 | `120` |
| `productNurtureRoundMinutes` | 商品卡养号单轮时长 | `15` |
| `productNurtureMaxRounds` | 商品卡养号最大轮次 | `3` |
| `targetLiveMaxRoomsPerRefresh` | 目标直播板块单轮候选扫描上限 | `25` |
| `targetCommentSearchMaxActiveMinutes` | 仅评论阶段主动查找目标的最长时间 | `60` |
| `maxCommentsPerRoom` | 同一房间本轮最多评论数 | `1` |
| `commentPool` | 商品卡目标评论话术池，无业务默认值 | `[]` |
| `liveNurtureKeywords` | 直播养号2标题关键词 | `[]` |
| `liveNurtureRefreshAfterRooms` | 直播养号2连续扫描多少个候选后刷新 | `10` |
| `liveNurtureWatchMinMinutes` | 直播养号2单房间最短观看 | `10` |
| `liveNurtureWatchMaxMinutes` | 直播养号2单房间最长观看 | `20` |
| `liveNurtureTotalMinMinutes` | 直播养号2总观看最短 | `70` |
| `liveNurtureTotalMaxMinutes` | 直播养号2总观看最长 | `100` |
| `taskMaxActiveMinutes` | 整体主动执行时长上限，不含人工暂停时间 | `240` |

`manualExecutionApproved`、`manualApprovalConfigHash`、`manualApprovalExpiresAt` 只保留给第一版兼容读取。第二版返回同名字段时必须标记为派生展示值，来源是独立审批记录，不能由 Web 直接写回 V2 runtime config。

### 4.2 配置聚合 revision 与哈希

`live_target_feature_configs` 增加单调递增 `revision` 和 `config_hash`，但 revision 不能只在 runtime JSON 保存时变化。以下操作都必须通过配置聚合服务在事务中递增 revision 并重算 hash：

1. 修改目标名称、平台或相似度。
2. 新增、修改、启用或停用别名。
3. 修改搜索词、商品词、必需词、禁入词或运行参数。
4. 修改设备绑定或预期账号范围。

哈希规则：

1. 服务端使用带版本号的 canonical JSON 和 SHA-256 计算 `config_hash`，Web 和手机不能自行计算。
2. `config_hash` 覆盖 targetId/targetCode、目标名、平台、相似度、启用别名及类型、关键词、启用阶段、评论池、评论上限和所有影响执行行为的参数。
3. 审批人、审批时间、审批状态等元数据不进入 config_hash。
4. assignment 另存完整 `effectiveWorkflow` 的 `snapshot_hash`，用于 checkpoint 恢复完整性校验。
5. 保存接口必须接收 `expectedRevision`；并发编辑版本不一致时返回 `CONFIG_REVISION_CONFLICT`，禁止后写静默覆盖先写。

### 4.3 运行时功能控制与设备能力

新增可运行时修改且可审计的功能控制，不依赖重新部署：

| 表/字段 | 作用 |
|---|---|
| `feature_rollout_controls.feature_key` | `commerce_card_workflow_v2` 或 `commerce_card_real_comment` |
| `enabled`、`revision` | 当前开关和控制版本，默认均为 false |
| `min_app_version` | 服务端最低版本门禁 |
| `required_capabilities_json` | workflow、checkpoint、resume、幂等和稳定 roomKey 要求 |
| `capability_ttl_seconds` | capability 最大允许陈旧时间，默认 600 秒 |
| `updated_by`、`updated_at`、`reason` | 开关修改审计 |
| `feature_rollout_device_allowlist` | 按 feature_key 维护设备灰度名单 |

`collector_devices` 增加 `capabilities_json` 和 `capabilities_reported_at`。手机自报能力只能作为事实输入，不能绕过服务端 `min_app_version`；版本或 capability 任一不足、能力超过 TTL 未更新时都拒绝 V2 START/RESUME。

### 4.4 独立执行审批

新增 `commerce_card_execution_approvals`，至少包含：

1. target、device、expectedAccountId/Name。
2. configHash、commentPoolHash、maxCommentsPerRoom。
3. maxTotalComments、dailyAccountTargetLimit 和跨运行冷却时间。
4. validFrom、expiresAt、status。
5. approvedBy/At/reason 和 revokedBy/At/reason。
6. 已消费额度和最后发送时间，更新时使用事务锁。

状态为 `ACTIVE` 且范围、哈希、时间和额度全部匹配时才算有效审批。目标身份、别名、设备范围、预期账号、评论池、评论上限或启用阶段变化时，配置聚合事务必须自动撤销同范围 ACTIVE 审批；撤销审批或关闭 executeEnabled 只阻断在途 assignment 的后续评论，不热替换其浏览和阶段配置快照。

## 5. 校验规则

后台保存 `commerce_card_live_comment` 时必须做服务端校验，不能只依赖前端。

基础规则：

1. `enabledStages` 至少包含一个阶段。
2. `enabledStages` 只能包含 `product_nurture`、`target_comment`、`live_nurture`。
3. 启用 `live_nurture` 时必须同时启用 `product_nurture`。
4. 启用 `product_nurture` 时，`searchKeywords`、`productKeywords`、`recommendationSignals` 不能为空。
5. 启用 `product_nurture` 或 `target_comment` 时，必须绑定有效目标直播间主档。
6. 启用 `target_comment` 且 `maxCommentsPerRoom > 0` 时，`commentPool` 必须人工填写、去空、去重并限制单条长度和条数；去重后的数量不得小于 `maxCommentsPerRoom`。
7. 启用 `live_nurture` 时，`liveNurtureKeywords` 必填。
8. `targetLiveMaxRoomsPerRefresh` 必须是 20 到 30 之间的整数。
9. `productCardDwellSeconds` 限制为 60 到 180；`productNurtureRoundMinutes` 限制为 5 到 30；`productNurtureMaxRounds` 限制为 1 到 6。
10. `liveNurtureWatchMinMinutes <= liveNurtureWatchMaxMinutes`，范围分别受 1 到 30、1 到 60 限制。
11. `liveNurtureTotalMinMinutes <= liveNurtureTotalMaxMinutes`，范围分别受 10 到 180、10 到 240 限制。
12. `taskMaxActiveMinutes` 限制为 30 到 360；后台同时计算最短、常规和最坏主动时长。配置最坏时长超过上限时必须拒绝保存或要求用户明确接受提前终止，不能静默显示为保证可完成。
13. `enabledStages` 保存时去重并按 `product_nurture -> target_comment -> live_nurture` 固定顺序归一化。
14. 创建 assignment 时 `expiresAt` 必须晚于当前时间加 `taskMaxActiveMinutes`，默认增加 60 分钟暂停预留；不得继续固定使用 3600 秒。
15. 目标门禁规则固定为：标准名或启用别名至少命中一项，全部 requiredKeywords 命中，任一 forbiddenKeywords 命中即否决；短名称只允许严格匹配。
16. 有效发送只能由全局真实评论开关、当前 executeEnabled、有效审批、配置哈希、审批额度、assignment 状态、expectedAccount、稳定 roomKey 和短时许可共同派生，后台不得自动开启任一控制项。
17. 无稳定 roomKey、账号身份不一致、capability 过期或服务端预占不可达时真实评论 fail closed。

旧字段兼容规则：

| 旧字段 | 新字段 |
|---|---|
| `searchKeywords` | `search_keywords` |
| `scanMinutesPerRound` | `productNurtureRoundMinutes` |
| `maxRounds` | `productNurtureMaxRounds` |
| `watchMinutesPerLive` | 保留给旧 APK；第二版不把它当成直播养号2随机观看时长 |
| `matchKeywords` | `productKeywords` |
| `targetRoom` | 迁移到目标主档、别名和功能配置，不复制进运行 JSON |
| `maxCommentsPerRoom` | 原义保留，并增加 assignment 级幂等约束 |
| `commentPool` | 原义保留，无默认话术 |
| `liveSignals` | 只用于第一版兼容 payload |
| `manualExecutionApproved` | 不迁入第二版 runtime config；只作为第一版兼容字段或独立审批的派生展示值 |

## 6. API 与服务改造

### 6.1 `live-target-config.service.ts`

新增严格 schema：

1. `commerceCardStageSchema`
2. `commerceCardWorkflowRuntimeConfigSchema`
3. `normalizeCommerceCardWorkflowRuntimeConfig(value)`
4. `parseCommerceCardFeatureConfig(payload)`
5. `mobileLiveTargetConfigSchema`
6. `commerceCardAgentCapabilitiesSchema`

改造点：

1. `liveTargetFeatureConfigSchema` 不能继续对所有 `runtimeConfig` 使用 `z.record(z.unknown())`。
2. 当 `featureType === "commerce_card_live_comment"` 时，必须按第二版 schema parse 和归一化。
3. 第二版 schema 不包含 `liveSignals`；该字段只在生成第一版兼容 payload 时保留。
4. 旧字段必须在 parse 阶段转换为 canonical 配置，但不能把无等价语义的 `watchMinutesPerLive` 自动映射为阶段三观看时长。

### 6.6 assignment、命令与移动端运行接口

阶段 B 前必须新增或扩展：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/mobile/tasks/current` | 返回当前 assignment 的单一 effectiveWorkflow 快照 |
| GET/PATCH | `/api/v1/admin/feature-rollout-controls/:key` | 查询或修改 V2/真实评论运行时控制，要求操作原因 |
| PUT | `/api/v1/admin/feature-rollout-controls/:key/devices` | 替换指定功能的设备 allowlist |
| POST | `/api/v1/admin/task-assignments/:id/commands` | 向同一 assignment 下发 PAUSE、RESUME、STOP |
| POST | `/api/v1/admin/commerce-card-execution-approvals` | 创建带范围、额度和有效期的执行审批 |
| GET | `/api/v1/admin/commerce-card-execution-approvals` | 查询审批状态、范围和剩余额度 |
| POST | `/api/v1/admin/commerce-card-execution-approvals/:id/revoke` | 实时撤销审批并写审计 |
| POST | `/api/v1/admin/live-comment-actions/:id/resolve` | 人工确认 submitted/unknown 动作最终状态 |
| POST | `/api/v1/mobile/task-assignments/:id/events` | 按事件序号和幂等键上报阶段事件 |
| PATCH | `/api/v1/mobile/task-assignments/:id/progress` | 上报进度和检查点摘要 |
| POST | `/api/v1/mobile/task-assignments/:id/complete` | 上报 SUCCEEDED、FAILED、CANCELLED 或 EXPIRED 终态 |
| POST | `/api/v1/mobile/task-assignments/:id/comment-actions/reserve` | 原子门禁检查、幂等预占并签发短时发送许可 |
| PATCH | `/api/v1/mobile/task-assignments/:id/comment-actions/:actionId` | 按 action stateVersion 更新动作状态 |
| GET | `/api/v1/mobile/task-assignments/:id/comment-actions/by-key/:key` | 崩溃恢复时查询原评论动作 |

接口约束：

1. assignment 必须属于当前 deviceToken 对应设备。
2. 已终态 assignment 拒绝新事件、进度和评论动作。
3. 重复 sequence 或 idempotencyKey 只有 payload 完全一致时才幂等返回原结果；内容不同返回 `IDEMPOTENCY_CONFLICT`。
4. 事件 sequence 必须连续；插入事件、更新 lastEventSeq 和 stateVersion 在同一事务中完成，跳号返回 `EVENT_SEQUENCE_GAP`。
5. START 创建新 assignment 和第一条 START command；PAUSE、RESUME、STOP 必须携带原 assignmentId、commandIdempotencyKey 和 expectedStateVersion。
6. 同一设备并发 START 使用事务锁和数据库唯一约束保证只创建一个非终态 assignment。
7. 命令 `DONE` 只表示当前控制命令已应用，不能统一把 assignment 写成 `ACKED`。
8. START DONE 映射 RUNNING；PAUSE DONE 只在稳定检查点成功后映射 PAUSED；RESUME DONE 映射 RUNNING；STOP 对任一非终态 assignment 映射 CANCELLED。
9. BLOCKED 是可人工恢复状态，不通过 complete 接口写入，也不写 completedAt；解除 blocker 后显式 RESUME。
10. 任务业务终态只由 complete 接口或服务端过期/明确终止规则决定，并写入 completedAt 和 terminalReason。
11. 评论 reserve 不信任手机上报的 target/account/config 字段，必须从 assignment 和服务端当前安全控制中派生并核对。
12. reserve 成功返回 actionId、permitToken、permitExpiresAt；服务不可达、许可过期、审批撤销、账号不一致或稳定 roomKey 缺失时 fail closed。
13. action 状态转换使用 expectedActionStateVersion；`submitted/unknown` 不允许自动回到 planned/submitting。

canonical assignment 状态统一为：

```text
PENDING, DISPATCHED, RUNNING, PAUSING, PAUSED, RESUMING,
BLOCKED, SUCCEEDED, FAILED, CANCELLED, EXPIRED
```

其中 `SUCCEEDED`、`FAILED`、`CANCELLED`、`EXPIRED` 为终态；`BLOCKED` 为非终态人工处理状态。

所有接口错误统一返回：

```text
code, category, stage, retryable, attempt, recoveryAction, details
```

4. 审批额度消费和评论动作预占在同一事务中完成，避免并发超发。

阶段 C 同时扩展 `live_comment_actions`：

1. `assignment_id`、`target_id`、`stage`、`assignment_event_id`、`expected_account_id`。
2. `room_key_version`、`room_key`、`comment_slot`、`comment_hash`。
3. `attempt_no`、`action_state`、`state_version`、`idempotency_key`。
4. `permit_expires_at`、`submitted_at`、`confirmed_at`、`resolved_by`、`resolved_at`。
5. `(tenant_id, idempotency_key)` 使用覆盖历史记录的唯一约束，评论动作不得通过软删除后重新发送。
6. 幂等键由 tenant、assignment、target、发送账号、roomKeyVersion、标准化 roomKey 和 comment slot 组成，不包含轮次、刷新次数或动态页面文本。
7. planned/submitting/submitted/sent/unknown/failed/skipped 更新同一动作行，并通过 stateVersion 限制状态转换；不能为每个状态插入一条独立动作。

允许转换为 `planned -> submitting -> submitted -> sent/unknown`、`planned/submitting -> failed/skipped`、`unknown -> sent/failed`。最后一组只允许后台人工处理接口执行；sent、failed、skipped 为动作终态。

丰富报表和历史事件归档可以延后，但运行身份、状态、快照、命令一对多、功能控制、执行审批、稳定 roomKey 和评论幂等不能在对应灰度阶段后补。`unknown` 不进入自动重试控制。

## 9. 日志、审计与排查

阶段 A 配置日志：

1. 配置保存记录 target、revision、configHash、操作者和字段级校验结果。
2. 配置预览记录来源、configVersion、适用设备能力和未通过门禁原因。
3. API 保存配置失败时返回字段级错误，便于从页面直接修正。

阶段 B/C 运行日志：

1. 手机端继续上传 runtime log，但结构化 assignment event 是运行状态的事实来源。
2. 每条阶段事件至少包含 assignmentId、configRevision、configHash、snapshotHash、stateVersion、stage、fromState、toState、sequence、reasonCode、retryable 和 recoveryAction。
3. 评论预占、提交、确认、未知、人工处理、跳过和失败继续写入 `live_comment_actions`，并关联 assignment、审批、账号、roomKeyVersion、roomKey、slot 和幂等键。
4. 保留第一版 `commerce_card_live_start`、`commerce_card_scan_start`、`commerce_card_live_comment_send/result`、`commerce_card_live_finish` 映射，历史日志不重写。
5. PAUSE、RESUME、STOP、全局急停、审批失效和 V2 回退都必须写入 assignment 事件。

必须能从后台判断：

1. 当前下发的是目标中心配置还是旧设备 JSON 兜底。
2. 下发配置版本是 `configVersion=1` 还是 `configVersion=2`。
3. 本次 assignment 使用的 target、expectedAccount、revision、configHash、snapshotHash、审批和配置来源。
4. 商品卡任务是否因为全局急停、当前 executeEnabled、审批撤销/过期/额度、哈希不一致、账号不一致、roomKey 缺失或许可过期而跳过评论。
5. 没有找到目标直播间时，是商品卡养号轮次耗尽，还是目标评论主动查找超时。
6. 评论失败发生在预占、检查点、输入框、发送按钮、提交确认、目标二次校验、账号校验、风控还是接口上报阶段。
7. PAUSE 是否已经到达稳定检查点，RESUME 是否继续同一 assignment，命令是否因 stateVersion 或顺序冲突被拒绝。
8. 旧 APK、appVersion、capability、capability 过期或 allowlist 不满足时为什么被拒绝执行 V2。
9. submitted/unknown 评论由谁、何时、基于什么证据处理，assignment 后续是 RESUME、STOP 还是终态。

不得记录 Token、Cookie、账号密码、完整评论流或未脱敏个人数据。

## 10. 兼容策略

### 10.1 能力与版本门禁

设备心跳或注册信息增加：

1. `supportedCommerceWorkflowVersions`。
2. `checkpointVersion`。
3. `supportsAssignmentResume`。
4. `supportsCommentIdempotency`。
5. `supportsStableRoomKey`。
6. `capabilitiesReportedAt`。

后台同时检查：

1. `commerceCardWorkflowV2Enabled` 全局功能开关。
2. 租户/设备 allowlist。
3. 最低支持 appVersion。
4. assignment 所需 capability。
5. `commerceCardRealCommentEnabled` 全局真实评论急停开关。
6. capability 是否在默认 600 秒 TTL 内，且服务端版本映射是否允许该能力组合。

手机自报 capability 与服务端最低版本任一不通过都拒绝 V2。功能开关和 allowlist 来自可审计运行时控制表，不使用只有重新部署才能修改的环境变量作为唯一急停手段。

### 10.2 单一有效执行口径

旧 APK 兼容：

1. 保留 `commerceCardLiveComment` 顶层字段。
2. 保留 `p3ExtensionsConfig.commerceCardLiveComment`。
3. 保留旧字段 `scanMinutesPerRound`、`watchMinutesPerLive`、`maxRounds`、`matchKeywords`。
4. 旧 APK 只能执行显式保留的 V1 快照，不能依赖“忽略 enabledStages”来解释 V2。
5. V2 配置无法无损投影为 V1 时拒绝启动，并记录 `agent_capability_not_supported`。

新 APK 口径：

1. 配置页可以读取 `liveTargets` 目录，但执行时只读取 assignment 的单一 `effectiveWorkflow`。
2. V2 能力齐全且设备在灰度名单时才允许创建 V2 assignment。
3. 没有有效 V2 assignment 时，配置目录本身不触发 runner；V1 只能由后台显式选择兼容版本，不能由手机静默降级。

后台兼容：

1. 保存 V2 草稿不影响当前 V1 运行。
2. 只有全部门禁通过且已经创建 V2 assignment 时才压制当前响应中的 V1 可执行字段。
3. Web 页面保存第二版配置后，不自动删除旧设备 JSON。
4. 运行或暂停中的 assignment 始终使用启动时快照，配置 N 修改为 N+1 只影响下一次运行。
5. 兼容读取至少保留一个稳定 APK 版本周期，确认所有设备升级后再清理旧字段。

唯一选择表：

| 条件 | 后台行为 |
|---|---|
| 已存在非终态 V2 assignment | 返回该 assignment 的 effectiveWorkflow，不返回 V1 可执行口径 |
| V2 全局开关关闭 | V2 配置仅用于草稿和预览；只有显式创建 V1 运行时才执行 V1 |
| V2 开启但设备不在 allowlist、版本不足或 capability 过期 | 拒绝 V2；需要 V1 时由后台显式选择，禁止自动降级 |
| V2 全部门禁通过且配置有效 | 创建 V2 assignment，并压制同次响应中的 V1 可执行字段 |
| V2 门禁通过但配置、账号、审批或时长校验失败 | 返回明确错误，不自动回退 V1 |

### 10.3 灰度与在途任务回退

放量顺序：

1. V2 配置保存和预览。
2. 指定设备无评论 dry-run。
3. 指定设备受控真实评论。
4. 扩大设备 allowlist。

关闭 V2 时：

1. 拒绝新的 V2 START 和 RESUME。
2. 对在途 V2 assignment 下发 STOP，确认终态并保留所有事件和评论审计。
3. 不把 V2 checkpoint 交给 V1 runner。
4. 只有所有 V2 assignment 已终态且设备回到 idle，才允许降级 APK。
5. 重新开启开关不会自动复活已取消或已过期运行。

全局真实评论急停必须在每次评论 reserve 时动态检查；即使配置快照不可变，急停、当前 executeEnabled、审批状态/额度、assignment 状态、expectedAccount、expiresAt 和风控结果仍以实时状态为准。手机只接受短时 permit，服务端不可达或 permit 过期时禁止点击发送。

## 11. 实施顺序

推荐按以下顺序开发：

1. 确认组合任务方案中的阶段组合、时长、退出抖音、审批粒度、BLOCKED 恢复和评论失败策略。
2. 审计并修复 Drizzle migration journal 与 `0005-0019` SQL 对账问题。
3. 在 `packages/types` 增加共享配置、完整 effectiveWorkflow、命令、assignment、审批、评论动作、发送许可和功能控制类型。
4. 在 `live-target-config.service.ts` 增加第二版 schema、配置聚合 revision、canonical configHash/snapshotHash、expectedRevision 和旧字段映射。
5. 新增功能控制、capability 持久化和 allowlist，两个商品卡控制项默认关闭。
6. 改造 `live-target.repository.ts` 的聚合事务保存、配置目录查询和 V1/V2 唯一选择规则。
7. 改造 `LiveTargetsPage.tsx` 和 `live-comment-config.ts`，完成阶段化表单、实时开关、独立审批和时长校验。
8. 部署阶段 A；保持 V2 与真实评论全局开关关闭，验证配置保存、预览、并发 revision 和旧 APK 不受影响。
9. 扩展 assignment、mobile_commands 一对多关系、stateVersion、单设备运行唯一约束、事件、运行接口、状态迁移和任务调度/日志页面。
10. 与手机端 checkpoint v2、同 assignment PAUSE/RESUME、命令乱序保护和状态机一起完成阶段 B 无评论 dry-run。
11. 新增执行审批和评论 reserve/update/query/resolve 协议，扩展稳定 roomKey、账号校验、幂等唯一约束和额度消费事务。
12. 完成断网 fail closed、许可过期、审批撤销、并发 reserve、submitted/unknown 和崩溃恢复测试。
13. 开启单设备受控真实评论，验证全局急停、实时开关、审批额度、账号/目标校验、重复键和在途回退。
14. 逐步扩大 allowlist；验收通过后再处理报表、历史 JSON 迁移和旧字段清理。

## 12. 验收口径

阶段 A 配置准备验收：

1. 后台能创建一个 `commerce_card_live_comment` 目标配置，搜索词不是 `夏橙` 时也能保存并下发。
2. 后台可以保存并预览 `configVersion=2`、`enabledStages`、商品卡浏览时长、轮次和推荐区识别词，但启动接口在 V2 开关关闭时明确拒绝执行。
3. 启用目标评论后，API 预览包含目标名、别名及类型、相似度、必需词、禁入词、评论池、executeEnabled 和派生审批状态。
4. 目标中心 V2 与旧 `p3ExtensionsConfig` 同时存在时，预览结果能解释来源和优先级，不产生两个可执行口径。
5. 未打开 `executeEnabled` 或不存在 ACTIVE 审批时，配置仍可预览，但真实评论必须处于禁止状态；`manualExecutionApproved` 只读派生。
6. 错误配置保存失败时，前端能看到明确字段错误。
7. 老配置仍能被旧 APK 拉取，不出现任务配置空白。
8. 两个管理员同时编辑同一 revision 时，后提交者收到 CONFIG_REVISION_CONFLICT，不覆盖先提交内容。
9. V2 与真实评论运行时控制默认关闭，修改开关、allowlist 或最低版本均有操作者和原因审计。

阶段 B 无评论灰度验收：

1. 不支持 capability 的设备无法创建 V2 assignment。
2. START、PAUSE、RESUME、STOP 使用同一 assignment；命令各有独立 ID/sequence，PAUSE 稳定回执前状态为 PAUSING。
3. 配置 N 启动后修改成 N+1，运行和恢复仍使用 N 的 selectedTarget 和 configSnapshot。
4. 事件 sequence、stateVersion、设备归属、终态写保护、snapshotHash 和 expiresAt 校验生效。
5. 关闭 V2 后在途任务停止，不再点击或输入，且不能自动恢复。
6. `commerceCardRealCommentEnabled=false` 时所有评论副作用被双端阻断。
7. 同一设备并发两个 START 时数据库只保留一个非终态 assignment，另一个返回明确冲突。
8. 旧 PAUSE/RESUME 命令乱序或重复到达时不能覆盖较新状态；STOP 对任一非终态状态优先。
9. assignment 默认过期时间能覆盖 taskMaxActiveMinutes 加暂停预留，不再固定一小时。

阶段 C 真实评论验收：

1. 同一 assignment、目标、发送账号、稳定 roomKey 和 comment slot 的物理发送最多一次。
2. 在发送前、发送后未确认和上报超时三个位置杀进程，恢复后均不重复发送。
3. `unknown` 状态使 assignment 进入 BLOCKED，只能通过后台人工确认接口处理，不自动重试。
4. 修改目标、别名、设备、预期账号、评论池、评论上限或阶段后，旧审批自动撤销，在途 assignment 的下一次 reserve 也被拒绝。
5. 全局急停、executeEnabled 或审批关闭/撤销后，在途任务下一次 reserve 立即停止发送并写入原因。
6. 重复幂等键由数据库唯一约束返回原动作；不同 payload 使用同一键时返回冲突，审计仍可追溯。
7. 服务端不可达、permit 过期、稳定 roomKey 缺失或抖音账号不一致时手机不点击发送。
8. 连续创建新 assignment 不能绕过审批总额度、账号/目标日上限和跨运行冷却。
9. 并发 reserve 不会超发审批额度，planned/submitting/submitted/sent 更新同一 action 行。

不通过条件：

1. 仍需要主要依赖高级 JSON 才能配置第二版流程。
2. `liveTargets` 中重复下发同一商品卡任务。
3. `夏橙` 被写死在后台逻辑中，无法替换。
4. 后台允许保存负数、超大时长、空阶段、空搜索词等明显错误配置。
5. 无全局急停放行、实时 executeEnabled、ACTIVE 审批或短时 permit 时仍可能点击发送。
6. 新配置导致旧 APK 拉取任务失败。
7. 配置准备完成后直接启动 V2 runner，却没有 assignment 快照、状态事件、checkpoint v2 或能力门禁。
8. 真实评论开放时没有 assignment 归属、expectedAccount、稳定 roomKey、幂等预占、唯一约束、独立审批、额度、短时许可或全局急停。
9. RESUME 创建新 assignment，assignment 仍只有单一 commandId，或 PAUSE/命令 DONE 把 assignment 写成错误终态。
10. 旧 APK 收到混合 V1/V2 payload 后静默执行第一版流程。
11. 同一设备可并发创建两个非终态 assignment，或旧 stateVersion 能覆盖新状态。
12. submitted/unknown 评论可以自动重试，或人工处理没有操作者和证据审计。
