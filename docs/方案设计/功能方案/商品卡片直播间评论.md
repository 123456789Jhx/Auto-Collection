# 商品卡片直播间评论二阶段方案

> 状态：需求已整理，尚未实现。当前 `1.0.37/73` 只完成“商城搜索商品卡、浏览匹配商品、搜索目标直播间、评论和观看”的部分链路；在本方案完成开发和真机验收前，线上行为仍以《商品卡直播评论方案》为准。

## 1. 文档目标

本文把“商品卡养号、目标直播间回复、直播养号”整理为 `commerce_card_live_comment` 的三阶段状态机，明确页面动作、配置字段、停止条件、审计和验收口径。

本方案不合并或复用旧 `live_comment` runner，也不改变普通 `live`、视频采集等任务。三个阶段属于同一个商品卡任务，由同一设备串行执行。

## 2. 变更与不变范围

本次计划新增：

1. 商品详情页约 2 分钟浏览和“你可能还会喜欢”商品卡循环。
2. 商品养号后从抖音直播板块识别目标直播间。
3. 目标直播间评论后的普通直播流养号阶段。
4. 三阶段断点、日志、总时长上限和 STOP/PAUSE 响应。

继续保持：

1. 任务类型仍为 `commerce_card_live_comment`，不调用 `live-comment-runner.js`。
2. 不购买、不加购物车、不关注、不私信，不绕过验证码、登录校验或平台风控。
3. 真实评论默认关闭，必须同时开启 `executeEnabled` 和 `manualExecutionApproved`。
4. 评论发送、跳过、失败以及每个阶段的结束原因都必须写入审计日志。

## 3. 总体流程

```text
配置和风险预检
-> 阶段一：商品卡养号
-> 直播板块识别目标直播间
-> 阶段二：目标直播间回复
-> 阶段三：普通直播流养号
-> 完成并上报
```

任意阶段收到 STOP、PAUSE、任务切换或风险信号时立即停止当前点击、滑动、输入和等待。PAUSE 保留检查点，RESUME 从当前阶段恢复；STOP 清理任务状态并返回待命。

## 4. 阶段一：商品卡养号

1. 启动抖音并进入商城，使用后台 `searchKeywords` 的首个有效词搜索，默认“夏橙”。
2. 在搜索结果中按 `productKeywords` 匹配商品卡，默认匹配“秭归”“夏橙”。
3. 点击匹配商品卡，在详情页持续浏览约 120 秒；等待必须可被 STOP/PAUSE 中断，期间按页面状态向下浏览。
4. 识别“你可能还会喜欢”等推荐区域，在推荐商品中继续匹配并进入下一张商品卡；未找到时返回搜索结果继续扫描。
5. 单次商品养号阶段默认运行 15 分钟。阶段结束后返回系统桌面并重新启动抖音，不强制停止应用、不清理应用数据。
6. 重新进入直播板块，按 `targetRoom` 配置识别目标直播间。每次刷新最多滑动 25 个直播间；允许配置为 20 至 30。
7. 找到目标直播间后记录 `product_nurture_target_found` 并进入阶段二；未找到时点击左下角“首页”刷新，再重新执行阶段一。

阶段一允许重复，但受任务总时长、STOP/PAUSE 和风控限制，不得形成无法终止的死循环。

## 5. 阶段二：目标直播间回复

1. 复用阶段一识别到的目标直播间候选，进入后再次校验主播名、直播间名和必须/排除关键词。
2. 候选失效时回到直播板块继续扫描；每扫描 25 个直播间仍未命中，则点击“首页”刷新后重新进入直播板块。
3. 目标直播间校验成功后，从 `commentPool` 取评论内容，发送数量受 `maxCommentsPerRoom` 限制。
4. 未开启真实执行或未人工批准时，不发送评论，但记录 `commerce_card_send_not_approved`，随后仍可进入阶段三。
5. 评论成功、跳过或失败都要记录目标、内容摘要、动作状态、失败原因和时间；同一任务内不得对同一直播间重复评论。

“持续查找”表示在任务总时长内持续刷新，不能绕过 STOP/PAUSE、风控或总时长上限。

## 6. 阶段三：普通直播流养号

1. 前提是阶段一已成功识别目标直播间；阶段二评论可以是已发送或因未审批而跳过。
2. 进入直播板块，读取直播间标题，与后台 `liveNurtureKeywords` 匹配。
3. 命中后进入直播间，单房随机观看 10 至 20 分钟；本阶段不发送评论。
4. 连续滑动 10 个直播间仍未命中时，点击左下角“首页”刷新，再进入直播板块继续。
5. 任务启动时在 70 至 100 分钟之间生成本次累计观看目标并写入日志；达到目标后完成任务。
6. 单房观看时间和累计目标一经生成，在 PAUSE/RESUME 后保持不变，避免恢复任务时重新随机导致时长漂移。

## 7. 配置字段

现有字段继续复用，新字段加入 `p3ExtensionsConfig.commerceCardLiveComment`：

| 字段 | 默认值 | 说明 |
|---|---:|---|
| `searchKeywords` | `["夏橙"]` | 商城搜索词 |
| `productKeywords` | `["秭归", "夏橙"]` | 商品卡和推荐商品匹配词 |
| `targetRoom` | 必填 | 目标直播间名称、主播名、匹配词和排除词 |
| `commentPool` | 现有配置 | 阶段二评论内容池 |
| `productNurtureMinutes` | `15` | 每轮商品卡养号时长 |
| `productCardDwellSeconds` | `120` | 单商品详情页浏览时长 |
| `recommendationSignals` | `["你可能还会喜欢"]` | 推荐商品区域识别文本 |
| `targetLiveMaxSwipesPerRefresh` | `25` | 每次刷新最多扫描直播间数量，范围 20 至 30 |
| `liveNurtureKeywords` | 必填 | 阶段三直播间标题匹配词 |
| `liveNurtureRefreshAfterSwipes` | `10` | 阶段三未命中后的刷新阈值 |
| `liveNurtureWatchMinMinutes` | `10` | 单房最短观看时间 |
| `liveNurtureWatchMaxMinutes` | `20` | 单房最长观看时间 |
| `liveNurtureTotalMinMinutes` | `70` | 累计观看目标下限 |
| `liveNurtureTotalMaxMinutes` | `100` | 累计观看目标上限 |
| `taskMaxMinutes` | `180` | 三阶段任务总时长上限 |

后台保存时校验最小值不大于最大值、关键词非空、目标直播间配置有效；前后端和手机端必须使用同一字段定义。

## 8. 状态、日志与恢复

检查点至少保存：

1. `phase`：`product_nurture`、`target_live_comment`、`live_nurture`。
2. 当前轮次、商品浏览数量、直播间滑动数量和刷新次数。
3. 当前目标直播间、已评论直播间集合和评论审计结果。
4. 阶段三本次随机出的单房观看时间、累计目标和已累计分钟数。
5. `phaseStartedAt`、`taskStartedAt`、最近页面摘要和 `stopReason`。

关键结束原因包括：`manual_pause`、`manual_stop`、`task_switched`、`task_timeout`、`risk_control`、`target_live_not_found`、`product_card_not_found`、`live_nurture_completed`。日志必须说明阶段、目标词、页面摘要、失败原因和恢复动作。

## 9. 前后端与手机端影响

1. 后台配置页增加阶段一和阶段三字段，继续显示真实发送开关与人工审批状态。
2. API、Zod schema、Web 类型和手机配置解析同步新增字段；配置仍存入现有 JSON，不新增数据库表。
3. `commerce-card-live-runner.js` 改为三阶段状态机；`douyin.js` 增加推荐商品遍历、直播板块扫描和首页刷新能力。
4. 日志中心展示当前阶段、目标时长、已完成时长、滑动/刷新次数和停止原因。
5. 保持 `live_comment`、`live` 与 `commerce_card_live_comment` 的 runner 和任务状态互斥。

## 10. 验收标准

1. 商品卡阶段可搜索关键词、进入匹配商品、单卡浏览约 120 秒并继续匹配推荐商品，总时长约 15 分钟。
2. 商品卡阶段结束后能重新启动抖音并进入直播板块，不清理登录状态。
3. 目标直播间扫描达到配置阈值后会刷新，不会无限滑动同一页面。
4. 目标直播间必须二次校验后才能评论；未审批、重复房间和发送失败均有审计记录。
5. 阶段三只进入标题匹配的直播间，单房观看 10 至 20 分钟，累计达到 70 至 100 分钟后结束。
6. STOP、PAUSE、RESUME、任务切换和风控在三个阶段及长等待中均能生效。
7. 超过 `taskMaxMinutes` 后按 `task_timeout` 结束，不再点击、滑动或评论。
8. 普通 `live` 和旧 `live_comment` 不会进入本任务的任何阶段。
9. 自动化测试覆盖三阶段流转、区间配置、刷新阈值、审批开关、重复评论、超时和状态恢复；真机验收记录实际页面文本与结束原因。

6. 完成自动化测试、代码审查、APK 打包和真机三阶段回归后，再把本文状态改为“已实现”。
