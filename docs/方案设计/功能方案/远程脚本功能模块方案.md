\# 远程脚本功能模块 · 分节点实施清单



> 目标项目：`Auto-Collection-main`（Bun + Hono API / React 19 + AntD Web / PostgreSQL + Drizzle / AutoX.js 移动端）

> 用途：本清单拆分为 8 个独立开发节点，逐个提交给 Codex 实施。提交时将项目文档与项目文件夹一并作为上下文。

\## 一、模块整体架构



\### 1.1 模块定位



"远程脚本"是一个\*\*底层基座组件\*\*：把未来各类业务（发视频、直播互动、采集策略等）抽象为"脚本类型 + 配置实例"两层模型。新增一种业务 = 注册一个类型定义（含配置 Schema），无需改动表结构和页面骨架，即可获得完整的 CRUD、校验、审计与后续下发能力。

\### 1.3 配置数据结构与存储方案



存储：PostgreSQL（Drizzle ORM），沿用全项目约定（`tenant\_id` 多租户预留 + 审计列 + `deleted\_at` 软删除）。



\*\*表1：脚本类型定义 `remote\_script\_definitions`\*\*（基座注册表，代码维护、启动同步，不走 UI 编辑）



| 字段 | 类型 | 说明 |

|---|---|---|

| id | uuid pk | |

| script\_key | varchar(64) | 类型唯一键，如 `generic\_form`、未来的 `publish\_video` |

| name | varchar(100) | 显示名，如"发视频配置" |

| description | varchar(500) | 用途说明 |

| config\_schema | jsonb | 配置 Schema 子集（见 1.4），驱动 API 校验 + Web 动态表单 |

| status | varchar(32) | `ENABLED` / `DISABLED`，默认 ENABLED |

| + auditColumns | | tenant\_id / created\_at / updated\_at / created\_by / updated\_by / deleted\_at |



唯一约束：`(tenant\_id, script\_key) WHERE deleted\_at IS NULL`



\*\*表2：业务配置实例 `remote\_script\_configs`\*\*（UI CRUD 的核心对象）



| 字段 | 类型 | 说明 |

|---|---|---|

| id | uuid pk | |

| script\_key | varchar(64) | 逻辑关联 definitions.script\_key（同租户） |

| config\_name | varchar(100) | 配置名称，如"6月玉米发视频计划" |

| config\_payload | jsonb | 配置内容，按所属类型的 config\_schema 校验 |

| revision | integer | 每次保存 +1，默认 1（下发与缓存版本依据） |

| config\_hash | varchar(64) | sha256(script\_key + 规范化 payload + revision) |

| status | varchar(32) | `ENABLED` / `DISABLED`，默认 ENABLED |

| remark | varchar(500) | 备注 |

| + auditColumns | | 同上 |



唯一约束：`(tenant\_id, script\_key, config\_name) WHERE deleted\_at IS NULL`

索引：`(tenant\_id, script\_key, status)`、`(tenant\_id, created\_at)`



\*\*表3：设备绑定 `remote\_script\_device\_bindings`\*\*（阶段一下只建表，节点8 启用）



| 字段 | 类型 | 说明 |

|---|---|---|

| id | uuid pk | |

| config\_id | uuid fk → remote\_script\_configs.id | |

| device\_id | uuid fk → collector\_devices.id | |

| priority | integer | 默认 100，冲突时数值小者优先 |

| enabled | boolean | 默认 true |

| + auditColumns | | 同上 |



唯一约束：`(tenant\_id, config\_id, device\_id) WHERE deleted\_at IS NULL`



> 建表模板直接参照现有 `live\_targets` / `live\_target\_device\_bindings`（schema.ts 第 343-419 行），风格完全一致。



\### 1.4 配置 Schema 子集（关键架构决策）



为避免引入 ajv 等重依赖，定义一个 \*\*JSON Schema 子集\*\*，同一份 Schema 三处消费：



```json

{

&#x20; "type": "object",

&#x20; "properties": {

&#x20;   "keywords":   { "type": "array", "items": { "type": "string" }, "maxItems": 20, "description": "关键词" },

&#x20;   "titleTpl":   { "type": "string", "minLength": 1, "maxLength": 100, "description": "标题模板" },

&#x20;   "dailyLimit": { "type": "integer", "minimum": 1, "maximum": 50, "description": "每日上限" },

&#x20;   "mode":       { "type": "string", "enum": \["immediate", "scheduled"], "description": "发布方式" },

&#x20;   "enabled":    { "type": "boolean", "description": "是否启用" }

&#x20; },

&#x20; "required": \["keywords", "titleTpl"]

}

```



\- 支持的能力仅：`type(object/string/integer/number/boolean/array)`、`required`、`enum`、`minLength/maxLength`、`minimum/maximum`、`maxItems`、`description`（作为表单 label/校验提示）

\- API 侧用它做入参校验（节点4 实现约 100 行的校验器）；Web 侧用它渲染动态表单（节点7）；未来移动端可用它做配置生效前自检



\### 1.5 API 契约（Admin 域，全部过现有 admin-auth 中间件）



| 方法 | 路径 | 说明 |

|---|---|---|

| GET | `/api/v1/admin/remote-scripts/definitions` | 类型列表（含 schema） |

| GET | `/api/v1/admin/remote-scripts/configs?scriptKey=\&status=\&keyword=\&page=\&pageSize=` | 配置分页列表 |

| POST | `/api/v1/admin/remote-scripts/configs` | 新建配置 |

| GET | `/api/v1/admin/remote-scripts/configs/:id` | 配置详情 |

| PATCH | `/api/v1/admin/remote-scripts/configs/:id` | 更新（revision+1、重算 hash；支持仅改 status 做启停） |

| DELETE | `/api/v1/admin/remote-scripts/configs/:id` | 软删除 |



错误码沿用现有风格：`VALIDATION\_ERROR` / `NOT\_FOUND` / `CONFIG\_NAME\_CONFLICT` / `SCRIPT\_TYPE\_DISABLED` / `PAYLOAD\_SCHEMA\_MISMATCH`。

## 六、更新通道边界与更新中心统一入口

更新中心是运营入口，不合并移动端的三条实际更新链路。三条通道必须分别发布、分别校验、分别回滚：

| 通道 | 版本标识 | 允许内容 | 设备侧行为 | 是否需要重打 APK |
|---|---|---|---|---|
| `remote-script` 配置 | `revision` + `configHash` | 业务参数、开关、设备绑定 | 拉取、校验、缓存、ACK；空闲时生效 | 否 |
| `biz-scripts` | 点分版本 + 包/文件 SHA-256 | `features/`、`domain/` 下业务 JS | 空闲门禁后下载、校验、覆盖层切换；失败恢复上一版本或 APK 基线 | 否 |
| APK 基座（`stable`/`gray`/`dev`） | APK `versionName`/`versionCode` | `app/`、`core/`、`platforms/`、`utils/`、入口、原生库和资源 | 按 APK 安装流程覆盖升级并重启 Agent | 是 |

### 6.1 更新中心职责

更新中心提供业务脚本和 APK 基座两个页签。业务脚本页签调用专用构建/发布接口，只能产出 `biz-scripts` 包；APK 页签按 `stable`、`gray`、`dev` 查询版本历史、SHA、发布状态和设备生效状态。页面不得把业务脚本发布按钮描述为 APK 构建或安装，也不得在业务包流程中写入 APK 版本。

### 6.2 版本校验与回滚口径

业务脚本必须同时通过包级 SHA、manifest 版本/通道、逐文件 SHA 和路径白名单校验，并在 Agent 空闲时切换 `current` 覆盖层。目录切换失败时恢复 `backup`，上报 `FAILED`/`ROLLBACK`。引擎停止失败保留待加载版本并报告失败；启动加载失败按 6.5 隔离该包，下一引擎整套使用 APK 基线。配置 `revision/configHash` 与业务包版本不可混用。

### 6.3 必须重新构建 APK 的变化

凡是改变原生代码、Android 权限、AutoX.js 引擎或 native library、启动入口/守护与更新器、`app/core/platforms/utils` 基座脚本、内置资源、签名/包名/versionCode 的变更，都必须重新构建并签名 APK。仅改变 `features/`、`domain/` 业务逻辑或远程配置时，沿对应远程通道发布即可。

### 6.5 业务基线与整套加载门禁（2026-09-10）

- APK 打包时在实际暂存脚本目录生成 `biz-script-baseline.json`，`schemaVersion=2`、`channel=biz-scripts`，记录独立业务 `version`、`apkBuildId`、业务逐文件清单 `files`、业务清单指纹 `sourceSha256`、基座逐文件清单 `baseFiles` 和基座兼容标识 `baseCompatibilityId`。业务基线使用 UTC 构建时间 `yyyyMMdd.HHmmssfff`，与 APK versionName 独立；正式构建成功才导出配套基线文件。
- 兼容标识从排序后的基座 JS 路径和 SHA256 生成，覆盖 `app/core/platforms/utils` 及根目录入口 JS，排除含部署地址/密钥的 `config.js`；业务修改不改变兼容标识。原生/引擎变化由显式运行时协议版本共同约束。每个清单指纹使用排序后的 `path:sha256` 行以 LF 连接的 UTF-8 SHA256。
- 新业务包必须携带同一 schema、兼容标识和完整业务清单指纹。构建须提供真实 APK 的基线 manifest，并校验当前基座源文件与该基线一致；版本高于 APK 基线及已发布业务版本。增量包仍匹配已有完整业务版本及逐文件清单，不允许从不兼容基座拼装。
- 下载前拒绝不高于有效版本的包；包内兼容信息受 ZIP SHA 保护，在激活前再次校验。启动时在首个业务 require 前复用相同门禁，拒绝缺元数据、旧版、不兼容或损坏的存量覆盖目录，不删除用户数据。不再把 APK 内业务无条件当作 0.0.0；缺少基线元数据时仅使用 APK 业务并拒绝热更新。
- 合格覆盖包以已验证清单复制到当前引擎私有运行视图，未列文件不进入视图，清单缺少的业务文件不逐个回落 APK。视图中的基座依赖由本地生成的代理指向 APK 原始基座模块，既保留 CommonJS 相对依赖，又不接受业务包提供 core/app/platforms/utils；引擎固定该视图，磁盘 current 的切换不冒充内存生效。
- 更新目录切换后报告待重启版本；运行中版本仍以当前引擎加载状态为准。重启失败必须明确报告，不能把下载/落盘成功当作新动作已运行。回滚及重启后旧覆盖层仍经过同一基线与兼容校验。
- 业务 require 或主入口初始化失败时，以 `version/sourceSha256/baseCompatibilityId` 写入 `biz-scripts/rejected.json`，不在当前已加载部分业务的引擎内切换来源。下一引擎跳过同一失败指纹并整套使用 APK；更新器不重复下载同一失败版本，修复必须分配新版本。普通任务阶段异常不作为启动失败标记。引擎自动重启仍依赖既有 watchdog；未实际重启时不得声称恢复已完成。
- 启动日志记录内置基线、实际业务版本、来源和指纹；视频动作日志记录动作标识、随机端点、控制点和派发结果。贝塞尔失败时明确失败，不再静默调用直线 swipe 冒充成功。保留用户已确认的矩形范围、方向、时长及评论抓取业务行为。
- 本节点仅修源码及独立测试；不运行 APK 构建、真实业务 ZIP 构建、共享暂存配置测试、安装或远程发布。后续严格执行三对话联合打包规则，单机验证后再另行授权推广。

### 6.6 本机目录上传、试运行与推广（2026-09-10 用户同意）

- 更新中心第一版选择本机 `mobile-agent/autojs` 目录，不接 Git。只上传 `features/domain` 业务 JS 正文；基座只上传路径与 SHA256，不上传 `config.js`、配置、密钥、资源或其他文件。固定完整业务包，暂不提供增量选项。
- 服务端从实际成功构建 APK 的配套基线读取兼容信息；缺失或无效时入口明确不可发布。上传的基座清单须与该基线完全一致，服务端重新计算业务文件 SHA、路径白名单、包大小与语法校验。拒绝不完整基座、重复路径、越界路径、超限正文；删除的业务文件列入预览。预览相对 APK 基线，明确显示比较版本。
- 不依赖服务端源码目录、PowerShell 或 APK 工具链。使用跨平台 ZIP 库生成不可变完整业务包与 schemaVersion=2 清单，版本单调递增。待发布记录、设备范围、操作人和版本修订持久化；归档存储在独立数据库记录，避免服务器重启/多实例丢包，不执行上传源码。
- 状态为 DRAFT -> TESTING -> PROMOTED，任一未撤回状态可 REVOKED。试运行与推广均由前端明确选择设备并二次确认，不默认广播。推广前所有试运行设备必须有新鲜心跳，确认同一版本、来源 overlay、业务指纹和基座兼容标识；撤回仅停止后续下发，不伪装成设备已经回滚。并发操作校验 revision。
- 仅向当前租户、启用、明确范围内、具备匹配基座与热更新能力且近期在线的设备提供新业务版本。旧无范围发布入口拒绝业务脚本发布，APK 发布链路不变。包下载使用不可猜测的发布包地址，DRAFT/REVOKED 不可下载；撤回不强制中断已开始下载或正在运行的设备。
- 业务实际版本以手机心跳中的 `bizScriptRuntime` 为准，下载或 APPLIED 只代表待加载。增加 `pendingBizScriptsVersion` 与加载来源/指纹；失败不得被后续普通 CHECKED 覆盖为成功。业务检查与事件不写 APK appVersion/targetVersion/updateStatus 字段。
- 每包最多 500 个业务文件、每文件 512 KiB、正文合计 8 MiB、请求 16 MiB。归档和元数据迁移随源码交付，真实数据库迁移、生产部署、设备发放及 APK 联合打包仍另行确认；测试只使用隔离数据、临时目录和浏览器模拟接口。

### 6.4 评论词抓取首个直播间入口与诊断日志

#### 2026-09-08 评论历史到底提示替换文本停滞判断

本补充替换下文全部按正文精确去重、模糊比较、参考页对齐及连续三次无新增提前结束的规则。用户确认实时“新消息”数量与当前历史页是否到底无关，停止依据改为指定区域出现“没有更多信息了”。删除隔离采集中的参考页、编辑距离、杂行过滤、连续计数及为文本进展补读的逻辑；原始评论逐条保存和原有 ID 规则不变，普通评论 OCR 的空读/异常三次重试保留。

每次评论区下滑使用 1080×2248 基准的 `(220,1537) → (220,1962)` 和 520ms 移动时长（2026-09-08 按用户要求将起点从 y=1522 下移 15 像素），到终点不松手，原地保持 2000ms。使用 Android 8.0/API 26 及以上的 `StrokeDescription(..., true)` 与 `continueStroke(..., 2000, false)` 连续手势；移动完成回调启动有限时长的终点保持，由系统负责松手，普通 tap/swipe 行为不变。保持期间约每 100ms 尝试截图（识别耗时计入两秒窗口，最多 20 次），只裁剪矩形 `(39,1483)–(385,1554)`，宽 346、高 71；坐标在布局模块按实际屏幕宽高同比例取整。提示使用原图 OCR，去空白后匹配完整词组“没有更多信息了”，不使用正文相似度或新消息数量。

截图返回时再次确认手指仍在保持阶段，防止把松手后的画面当作依据；有效截图的 OCR 可以晚于松手结束。第一次命中即可在手势结束后以 `COMMENT_HISTORY_END` 收口，不再补抓一页、不等待连续三次；工作流沿用现有切房动作和 800–1200ms 切房前等待。没有命中则继续抓取及下滑，分钟上限仍为兜底。全部为空也不能作为历史到底证据。停止指令、平台验证和期限检查优先于命中结果；手势/截图/OCR 失败保留已有评论并明确失败，工作流只在采集成功结束后切房。截图和裁剪图均回收，日志记录保持时长、动作坐标、提示裁剪区域、原文、尝试次数及命中结果。无连续手势能力时失败，不降级为松手后等待；本次涉及基座 accessibility.js，需重新构建 APK 验证真实 Android 回调与提示出现时机。

#### 2026-09-05 原始评论逐条保留与切房返回

抓取阶段不按评论正文去重：每个 OCR 页面解析出的每一条正文都保留，重复正文也作为独立原始记录返回；“是否新增”只使用内部比较集合，不改变抓取结果。入库时继续由词库唯一约束和噪声清洗处理重复项。支持中文/英文冒号和分号（`：`、`:`、`；`、`;`），仅截取首个分隔符后的内容。

评论采集结束时设备位于主播资料页，工作流必须先点击主播资料页左上角返回直播主界面，等待页面稳定后再执行切房手势和下一直播间人数/小黄车筛选，避免在资料页重复执行当前直播间流程。结果记录 `captureElapsedMs` 和停止原因，便于核对实际抓取时长。

#### 2026-09-05 评论抓取时限与正文规则

后续确认补充：分钟上限同时配合连续无新增提前结束。首次评论识别仅建立正文集合，不计为一次滑动；每次成功滑动后的 OCR 页面若无新增正文则计数加一，出现新增正文则清零。连续三次滑动后无新增，以 `NO_NEW_COMMENTS` 结束当前采集、释放绑定并立即切房，不等待剩余分钟数。OCR 调用失败沿用异常重试，不作为无新增页面计数。以下原时间方案中的“不以连续无新增结束”由本补充替代，旧业务规则保持原样。

隔离评论抓取使用 `captureDurationMinutes` 控制每个直播间的采集时长，单位为整数分钟，默认 5，范围 1–60。前端保留设置及批次配置，每台设备下发同一批次设定；旧养号配置不扩展。计时从主播资料读取、绑定及返回直播界面之后开始，到期结束当前采集并切换直播间，再进行下一直播间筛选；不以滑动次数或连续无新增评论结束定时采集。同步 OCR 已开始时无法强制中断，到期返回的结果不收集、不再发起评论 OCR 或评论滑动。

采集期间每约 60 秒通过现有 claim 接口续期设备与直播间绑定，续期失败停止采集。OCR 按整行识别，仅取每行第一个中文或英文冒号后的非空正文，不拼接下一行，不输出评论者用户名。主播名称仍用于直播间识别。原始评论保留正文；词库入库沿用原有噪声处理。此变更无需数据库迁移。

评论词抓取在直播搜索结果页使用业务专用的固定区域随机点击动作，不依赖共享直播入口识别作为进入成功条件。点击区域按屏幕比例限制在横向 `17%–86%`、纵向 `28%–65%`；点击后等待约 `4–7` 秒再进入人数 OCR，其他直播业务继续使用共享入口能力。该动作只记录点击指令与等待结果，不能把“点击函数返回成功”解释为页面已完成跳转。

评论词运行时必须记录入口点击坐标、等待时长、人数 OCR 区域、OCR 原文、解析人数、阈值比较和切房原因，日志用于真机验收和问题定位。专用点击动作的停止控制必须从工作流透传到等待循环；停止控制未闭环前，不得标记该入口改造为真机验收通过。

### 2026-09-14 评论词按设备动作间隔（用户确认实施）

- 复用设备画像 JSONB 的 `commentActionTiming` 子字段，契约为 `{schemaVersion:1,enabled,actions:{actionKey:{beforeMs:[min,max],afterMs:[min,max]}}}`。区间为 0–120000 的整数毫秒，最小值不得大于最大值；未配置字段继承统一动作默认值。原 `openDouyinWaitMs` 仅作为未配置专用启动间隔时的兼容来源，不追加第二段等待。
- 17 个可配置动作：打开抖音、打开搜索入口、输入关键词、提交搜索、打开直播标签、进入首个直播间、人数识别、商品卡识别、主播信息、主播主页、身份识别、返回直播间、评论识别、评论翻页、本房抓取完成、切换直播间、评论 OCR 重试。每项支持动作前与动作后区间。相邻动作的间隔等于“上一动作后等待 + 下一动作前等待”，两者各随机一次；输入框显示明确单位与合计关系。
- `features/new-comment/action-timing.js` 是业务等待唯一执行入口；单个动作开始时固定配置，当前动作与后置等待使用同一快照，下一动作读取已刷新的设备配置。停止检查优先，等待分片最多 100ms；异常不得默认为成功或继续派发下一个动作。日志区分配置来源、选中毫秒、实际耗时和动作执行时间。
- 评论词专用导航位于 `features/new-comment/navigation.js`，直接调用无附带延迟的点击/手势及有限节点探测，不调用共享 adapter 内的业务 sleep；其他功能继续使用各自已有实现。搜索三个子动作独立计时。原直播标签两层等待合并为 3500–7000ms；首个直播间沿用本轮盘点确认的源码默认 7500–8500ms，替代上文历史 4–7 秒说明；抓取完成后切房前的 800–1200ms 保留为独立 `finishRoomCapture` 动作。
- 元素查找轮询、系统启动/授权弹窗条件探测、手势 duration/startHold/endHold、保持期间每 100ms 的 OCR 探测及停止轮询属于动作内部时序，第一版不开放修改。实际页面响应与 OCR 耗时单独记录，不声称设置值是整个动作的总耗时上限。动作路径与范围页面保留未开放页签。
- 单设备 GET/PATCH `/admin/devices/:deviceCode/comment-action-timing`；复制 POST `/admin/device-profile-overrides/copy` 仅复制源设备已保存的评论词间隔快照。复制前读取目标配置并展示差异；源和目标以 `updatedAt` 乐观锁校验，事务内写配置与刷新命令，冲突返回 409，不覆盖机型、截图授权、路径、账号或其他任务配置。目标得到独立配置副本，之后调整源设备不联动目标。
- 前端展示已保存/等待刷新，不以 HTTP 成功宣称手机已生效。首次交付需要 Web/API 部署与兼容业务完整包更新；以后只调参数走配置刷新，无需反复构建 APK。若实现触及基座文件，仍遵守既有 APK 边界与联合打包规则。本轮实施不包含构建 APK、安装、业务包发布或替用户发起真机任务。
- 评论任务运行期间，只有本功能保存/复制生成的 `REFRESH_CONFIG` 可以作为控制消息领取为 `FETCHED`，不能占用第二个 `CLAIMED/RUNNING` 业务执行席位；STOP 仍优先。旧 APK 对领取命令自动发送的 RUNNING 回报视为传输确认，不晋升该消息状态、不延长 60 秒租约；终态回报沿用既有流程。
- 批量复制要求源设备已启用并保存完整间隔，未启用时前端提示启用、后端拒绝复制，避免各设备恢复默认时的旧启动间隔被误解为相同值。父画像与子面板必须检查保存前版本是否连续；不能以子面板新版本号授权父页面旧画像覆盖并发改动。
- 抓取计时到期后不派发新的识别/滑动；若识别已在期限内完成，只是动作后等待消耗完剩余时长，仍保留该次已完成的评论。识别本身超过期限则沿用不收集结果的原约束；该区分不得因新增后等待而混淆。
