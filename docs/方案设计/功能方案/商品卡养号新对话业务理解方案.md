# 商品卡养号新对话业务理解方案

> 状态：已按首轮方案同步手机端实现，仍需真机回归确认推荐区识别稳定性。
>
> 来源：2026-07-15 新对话说明、真机日志 `docs/info`、用户截图中的商品详情推荐区形态。
>
> 关系：本文用于收敛商品卡养号 V2 的执行口径。当前已同步手机端实现；后台与更细粒度 OCR 兜底可在真机回归后继续补强。

## 1. 文档目标

本文记录当前确认中的商品卡养号业务逻辑，重点回答四个问题：

1. 商品卡养号一轮应该怎么跑。
2. 商品详情页推荐商品卡应该怎么识别。
3. 一轮养号结束后如何进入直播板块验证目标直播间。
4. 三轮未达标、异常中止和后台状态应该怎么表达。

本文只写业务理解和后续实现边界，不直接修改手机脚本、后台接口或数据库。

## 2. 核心结论

1. 商品卡养号首个商品卡来自商城搜索结果页“全部”板块。
2. 进入首个商品详情后，后续商品卡来自当前详情页下方的推荐商品列表。
3. 推荐商品列表不能只靠 `你可能还会喜欢` 一个标签判断；该标签是强信号，但不是唯一信号。
4. 推荐商品卡识别应先定位商品卡列表区域，再枚举商品卡并做关键词匹配，不能全屏先找 `夏橙` 再反推容器。
5. 单轮商品卡养号总时长控制在 15 分钟内，目标是约 7 至 8 张商品卡，不要求每张卡精确停留 2 分钟。
6. 一轮商品卡养号结束后，应直接退出抖音，再重新打开抖音进入直播板块扫描目标直播间。
7. 目标直播间命中则养号成功；未命中则进入下一轮商品卡养号。
8. 最多执行 3 轮；一天内 3 轮都未命中目标直播间，记录为养号失败并结束。
9. 搜索失败、页面卡死、无法进入商城、无法进入直播板块、脚本异常等不应记为养号失败，应记为异常中止。
10. 手动暂停、停止和后台任务切换必须保留原有控制语义，不能混入养号失败。

## 3. 一轮商品卡养号流程

单轮流程：

```text
打开抖音
-> 进入商城
-> 搜索 searchKeywords，例如“夏橙”
-> 进入搜索结果“全部”板块
-> 在“全部”列表中找 productKeywords 命中的商品卡
-> 点击首张商品卡进入详情
-> 在详情页向下滑动
-> 定位推荐商品卡列表
-> 在推荐商品卡列表中枚举商品卡
-> 对每张商品卡做关键词匹配
-> 命中后点击商品卡主体
-> 进入新的商品详情
-> 重复详情页推荐商品卡循环
-> 单轮 15 分钟内结束
```

关键点：

1. 搜索结果页只负责打开首张商品卡。
2. 后续商品卡应在详情页内连续跳转，不应每张都返回搜索结果页。
3. 详情页推荐区识别失败时，应继续下滑查找，不应立刻结束整轮。
4. 单轮结束后不在商品详情页里扫描直播间。

## 4. 推荐商品卡识别策略

推荐商品卡识别分为四层，按顺序使用。

### 4.1 第一层：推荐区标题强信号

适用场景：

```text
你可能还会喜欢
下面是两列商品卡
```

识别方法：

1. 在当前屏幕找推荐区标题，例如：
   - `你可能还会喜欢`
   - `你可能想看`
   - `猜你喜欢`
   - `推荐商品`
   - `相关商品`
2. 记录标题节点的下边界。
3. 只扫描标题下方区域。
4. 判断标题下方区域是否出现商品卡结构。
5. 在商品卡结构内做关键词匹配。

要求：

1. 不能只要出现标题就直接点击。
2. 必须确认标题下方存在商品卡。
3. 商品卡点击点应选择图片中心或卡片主体中心，不能点击标题文字碎片。

### 4.2 第二层：推荐 Tab 选中强信号

适用场景：

```text
顶部 tab：商品 / 评价 / 详情 / 推荐
推荐 tab 被选中
屏幕主体区域全是商品卡
```

识别方法：

1. 判断当前仍在商品详情页。
2. 判断顶部 `推荐` tab 是否被选中，或屏幕文本显示 `推荐 已选中`。
3. 如果推荐 tab 选中，则把 tab 下方到购买底栏上方的区域视为推荐商品列表候选区。
4. 在该区域扫描两列商品卡。

要求：

1. 不能因为出现 `推荐` 两个字就认定进入推荐列表。
2. 必须结合商品卡结构判断。
3. 该策略用于覆盖 UI 不显示 `你可能还会喜欢`、但切到推荐 tab 的情况。

### 4.3 第三层：商品卡结构兜底

当推荐区标题和推荐 tab 都不可靠时，使用商品卡结构判断。

商品卡结构信号：

| 信号 | 说明 |
|---|---|
| 两列瀑布流 | 每张卡宽度约为屏幕一半 |
| 大图区域 | 商品卡上半部分通常是图片 |
| 标题文本 | 图片下方有商品标题 |
| 价格 | 出现 `¥`、`￥`、`新人价`、`券后价`、`到手价` |
| 销量/推荐 | 出现 `已售`、`达人推荐`、`销量`、`店铺销量` |
| 促销 | 出现 `立减`、`包邮`、`极送达` 等 |
| 排除项 | 不能包含 `进店`、`客服`、`购物车`、`加入购物车`、`领券购买`、`专享价` 等底栏动作 |

兜底判断建议：

```text
扫描当前屏幕可见节点
-> 按 bounds 过滤出类似商品卡的矩形区域
-> 聚合卡片区域内文本
-> 判断是否有价格和商品信号
-> 排除底栏按钮和当前商品详情参数区
-> 形成商品卡候选列表
```

### 4.4 第四层：OCR 兜底

适用场景：

1. 无障碍文本读不到推荐卡标题。
2. 图片上有大字，例如“新鲜甜夏橙”，但 text/desc 中没有。
3. 推荐区肉眼可见商品卡，但无障碍树只暴露价格或零散数字。

识别方法：

1. 截取推荐商品列表区域。
2. 按两列商品卡布局切块。
3. 对每个卡片区域执行 OCR。
4. OCR 文本命中 `productKeywords` 时，点击对应卡片主体。

要求：

1. OCR 只作为兜底，不应替代无障碍识别主链路。
2. OCR 命中后仍需点击后做页面签名校验，确认确实进入新商品详情。

## 5. 关键词匹配顺序

推荐商品卡点击不应使用旧顺序：

```text
全屏找“夏橙”
-> 从“夏橙”文本节点向父级找容器
-> 点击候选节点
```

新的顺序应为：

```text
定位推荐商品列表区域
-> 枚举商品卡候选
-> 聚合每张卡的标题、价格、销量和 OCR 文本
-> 对卡片文本做 productKeywords 匹配
-> 命中后点击卡片主体
-> 点击后校验是否进入新商品详情
```

这样可以避免点到当前商品详情标题、规格参数、购买底栏或不可跳转的文字节点。

## 6. 点击成功校验

点击推荐商品卡后，必须校验是否真的进入新商品详情。

建议校验：

1. 点击前记录当前商品详情文本签名。
2. 点击后等待页面跳转。
3. 再次读取当前屏幕文本。
4. 新签名必须不同于旧签名。
5. 新页面仍然命中 `productKeywords`。
6. 新页面仍然是商品详情页或商城商品页。

失败处理：

1. 如果签名未变化，说明没有打开新商品。
2. 将该卡片 bounds 记入跳过列表。
3. 继续在当前推荐列表中找下一张商品卡。
4. 不应因为一次点击失败就退出整轮任务。

## 7. 单轮时间和商品卡数量

单轮时长：

1. 每轮商品卡养号总时长为 15 分钟内。
2. 目标浏览 7 至 8 张商品卡。
3. 平均约 2 分钟一张，但不是强制精确要求。

执行原则：

1. 以 15 分钟总时长为硬边界。
2. 商品卡数量是期望值，不是强制精确数。
3. 等待和下滑必须可中断，便于 PAUSE、STOP 和任务切换。
4. 如果 15 分钟内只完成少于 7 张，但页面流程正常，应结束本轮并进入直播板块验证。
5. 如果页面识别异常导致无法继续浏览，应记录异常中止。

## 8. 一轮结束后的直播目标验证

商品卡养号单轮结束后，流程必须从商品页切出，不能在商品详情页里直接扫描直播间。

正确流程：

```text
商品卡养号 15 分钟结束
-> 直接退出抖音
-> 回到系统桌面
-> 重新打开抖音
-> 点击直播板块
-> 浏览直播间候选
-> 判断是否匹配目标直播间
```

目标直播间判断依据：

1. 目标直播间名称。
2. 目标别名。
3. 主播名或房间标题中的目标文本。
4. 禁入词和必需词校验。
5. 进房后二次校验。

不允许：

1. 在商品详情弹层中直接执行直播流候选扫描。
2. 把商品详情页文本当成直播间候选文本。
3. 找不到目标直播间后直接判定异常。

## 9. 三轮闭环

最多执行 3 轮商品卡养号。

```text
第 1 轮商品卡养号 15 分钟
-> 退出抖音
-> 重新进入直播板块找目标直播间
-> 找到：养号成功
-> 未找到：进入第 2 轮

第 2 轮商品卡养号 15 分钟
-> 退出抖音
-> 重新进入直播板块找目标直播间
-> 找到：养号成功
-> 未找到：进入第 3 轮

第 3 轮商品卡养号 15 分钟
-> 退出抖音
-> 重新进入直播板块找目标直播间
-> 找到：养号成功
-> 未找到：养号失败
```

业务状态：

| 状态 | 含义 |
|---|---|
| 养号成功 | 3 轮内任一轮结束后，在直播板块命中目标直播间并通过二次校验 |
| 养号失败 | 3 轮商品卡养号均完成，但每轮后的直播板块扫描都未命中目标直播间 |
| 异常中止 | 搜索失败、进入商城失败、进入直播板块失败、页面卡死、脚本异常、无障碍异常、OCR 异常等非业务未命中问题 |
| 手动暂停 | 用户或后台 PAUSE，不计为失败 |
| 手动停止 | 用户或后台 STOP，不计为养号失败 |

## 10. 后台展示口径

后台应区分业务失败和异常。

建议展示：

| 后台展示 | 触发条件 |
|---|---|
| 商品卡养号中 | 正在执行 15 分钟商品卡浏览 |
| 直播目标验证中 | 一轮商品卡结束后，已退出抖音并进入直播板块扫描 |
| 养号成功 | 目标直播间命中并通过二次校验 |
| 养号失败 | 3 轮完成后仍未命中目标直播间 |
| 异常中止 | 页面、脚本、权限、搜索、网络以外的流程异常导致无法继续 |
| 已暂停 | PAUSE 后停在稳定检查点 |
| 已取消 | STOP 或任务替换 |

后台日志至少应记录：

1. 当前轮次。
2. 本轮商品卡浏览开始和结束时间。
3. 本轮浏览商品卡数量。
4. 推荐区识别策略命中方式：标题、推荐 tab、结构兜底或 OCR。
5. 每次推荐卡点击是否成功跳转。
6. 直播目标验证候选数量。
7. 最终结果：成功、失败、异常、暂停或取消。

## 11. 当前代码与目标差异

根据 `docs/info` 日志和当前实现，现有问题主要是：

1. 推荐商品卡识别仍偏向“全屏找关键词文本，再向父级找容器”，容易点到当前商品详情文本或不可跳转节点。
2. 一轮商品卡浏览结束后，当前实现可能还停留在商品详情页，却开始执行目标直播间扫描。
3. 目标直播间扫描在商品详情页里滑动，最终无法重新进入商城，导致 `commerce_search_failed`。
4. 收尾逻辑把该失败当成任务失败，直接退出抖音。

目标实现需要调整为：

1. 先定位推荐商品列表，再匹配商品卡。
2. 单轮商品卡结束后直接退出抖音。
3. 重新打开抖音并进入直播板块后，再执行目标直播间扫描。
4. 目标未命中进入下一轮，不应误报异常。
5. 三轮都未命中才是养号失败。

## 12. 建议后续落地顺序

后续如果确认本文口径，建议按以下顺序实施：

1. 先拆出商品卡识别模块，避免继续扩大 `douyin.js`。
2. 实现推荐商品列表区域识别：标题、推荐 tab、结构兜底。
3. 实现商品卡候选枚举和关键词匹配。
4. 增加 OCR 兜底，但保持默认关闭或低优先级。
5. 调整单轮结束行为：退出抖音、重新进入直播板块。
6. 调整三轮闭环状态：成功、失败、异常中止分开。
7. 补充真机日志字段和回归测试。
8. 最后再同步后台展示和组合任务正式方案。

## 13. 暂不处理内容

1. 不新增购买、加购物车、收藏、关注、私信等动作。
2. 不绕过登录、验证码、平台风控或系统权限限制。
3. 不把 OCR 作为唯一识别方式。
4. 不在商品详情页里直接发送评论。
5. 不把目标直播间未命中记录为脚本异常。
6. 不把异常中止记录为养号失败。
