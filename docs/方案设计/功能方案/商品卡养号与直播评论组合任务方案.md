# 商品卡养号与直播评论组合任务方案

> 状态：第二版设计提案，待确认，尚未实现。
>
> 来源：`商品卡片直播间评论.md` 手写原稿。
>
> 现行基线：`商品卡直播评论方案.md`。本文只有在确认、开发、测试和真机验收完成后，才替代第一版执行口径。
>
> 配套后台方案：`商品卡养号与直播评论后台改造方案.md`。本文定义业务流程和运行安全底线，后台方案负责分阶段落地，不能降低本文的启用门槛。

## 1. 文档目标与设计结论

本文把手写原稿中的“商品卡养号、目标直播间回复、直播养号2”转换为可配置、可暂停、可恢复、可审计的自动化任务设计。

本文推荐继续使用现有任务类型 `commerce_card_live_comment`，在一个任务下通过 `enabledStages` 选择执行阶段。该组合方式是基于现有调度和 runner 的设计建议，不是手写原稿已经明确的技术结论，实施前需要确认。

核心结论：

1. 商品卡养号、目标直播间评论和关键词直播养号是三个独立业务阶段，组合执行时顺序固定。
2. 商品卡养号结束后的目标直播间扫描是阶段转换门禁，不应在阶段二无条件重复扫描。
3. 原稿要求商品卡养号后退出抖音再重新进入。本方案解释为“返回系统桌面后重新启动抖音”，不强制结束进程，不清理应用数据。
4. 商品卡关键词只用于商城商品匹配，不能代替目标直播间名称、主播名或别名。
5. 商品养号首个商品来源必须是商城搜索结果页“全部”板块中的关键词匹配商品卡；进入商品详情后，后续商品来源切换为详情页推荐商品卡列表，不再把搜索结果页当作每个商品之间的常规跳板。
6. 原稿中的“一直刷，不停止”必须受任务有效期、主动执行时长、STOP、PAUSE、任务切换和风控限制，不能实现为无限循环。
7. 真实评论必须同时满足全局急停放行、任务执行开关开启、有效执行审批、assignment 处于可发送状态、发送许可未过期和服务端幂等预占成功，并留下动作审计。
8. 新流程改变了现行“从商品卡直播入口直接进房”的路径，实施时必须同步修订相关现行方案，不能只改手机脚本。
9. assignment 表示一次不可替换的业务运行；START 创建 assignment，PAUSE、RESUME、STOP 只是关联到该 assignment 的控制命令，不能再创建新运行。
10. 第二版人工批准必须是可审计、可撤销、有范围和有效期的独立审批记录；`manualExecutionApproved` 只能作为兼容字段或派生展示值，不能继续作为唯一授权事实。
11. 真实评论必须由服务端在副作用前原子签发短时发送许可；手机无法连接服务端、无法取得稳定房间标识或无法确认当前账号时一律禁止发送。

## 2. 当前实现基线与差异

| 维度 | 当前实现 | 第二版目标 | 结论 |
|---|---|---|---|
| 任务隔离 | 已有独立 `commerce_card_live_comment` 和 `commerce-card-live-runner.js` | 保持独立，不复用普通 `live` 或旧 `live_comment` runner | 保留 |
| 商品卡浏览 | 搜索结果中浏览少量商品卡，详情页只短暂停留 | 首个商品从商城搜索结果“全部”板块进入；后续在商品详情页约 120 秒浏览、下滑到推荐商品卡列表并继续按关键词匹配 | 改造 |
| 商品卡轮次 | `scanMinutesPerRound` 最长 15 分钟，但达到卡片数量后可提前结束 | 单轮主动执行约 15 分钟，按时间和安全上限共同结束 | 改造 |
| 目标直播间入口 | 商品卡浏览后调用综合搜索入口查目标直播间 | 返回桌面、重启抖音、进入直播板块扫描目标 | 主流程变更 |
| 未命中目标 | 当前可按成功结束任务 | 商品养号模式回到下一轮；仅评论模式刷新直播板块后继续 | 修复语义 |
| 目标评论 | 已有进房评论、双开关和评论动作审计 | 增加直播板块 20 至 30 个候选的刷新循环和稳定幂等 | 扩展 |
| 直播养号2 | 未实现 | 标题关键词匹配、单房 10 至 20 分钟、累计 70 至 100 分钟 | 新增 |
| 暂停恢复 | PAUSE 当前会使 runner 失败退出，检查点不能恢复阶段进度 | PAUSE 在稳定检查点确认，RESUME 从原状态恢复 | 重构 |
| 后台配置 | 已有直播目标配置和少量运行参数 | 按三个阶段提供结构化表单和严格类型 | 扩展 |
| 运行记录 | 心跳、运行日志和评论动作已存在 | 增加运行快照、阶段事件、幂等键和任务归属 | 扩展 |

现有测试只能证明第一版实现自洽。其中“目标未找到即成功结束”和“PAUSE 即失败”的断言与第二版目标冲突，实施时必须替换，不能作为第二版验收依据。

## 3. 待确认设计决策

以下决策按“推荐方案”写入本文，但在改代码前需要业务确认：

| 决策 | 推荐值 | 原因 |
|---|---|---|
| 任务组织 | 一个任务类型下使用 `enabledStages` | 复用现有调度入口，同时允许只跑原稿中的某一段 |
| 默认阶段 | `product_nurture` | 第二版默认先做无评论养号；启用目标评论时必须人工填写评论池并重新批准 |
| 退出抖音 | 返回系统桌面后重新启动，不强制结束进程 | 保留原稿“退出再进入”的可见行为，同时避免强杀和数据风险 |
| 商品养号最大轮次 | 3 轮 | 防止目标长期不开播时形成不可终止循环 |
| 仅评论阶段主动查找上限 | 60 分钟 | 将“持续查找”变为有明确终点的可审计执行 |
| 整体主动执行上限 | 240 分钟 | 覆盖 45 分钟商品养号、60 分钟目标查找、100 分钟直播养号及页面切换 |
| PAUSE 时间 | 不计入主动执行时长 | 恢复后不因人工暂停损失业务时长；任务绝对过期时间仍继续计算 |
| assignment 绝对有效期 | 启动时显式设置，默认 `taskMaxActiveMinutes + 60` 分钟 | 当前 1 小时默认值无法覆盖第二版完整流程；暂停超过预留时间后应按绝对过期终止 |
| 执行审批粒度 | 每次审批绑定目标、设备、抖音账号、配置哈希、评论池哈希、额度和有效期 | 允许即时撤销，避免把审批混入不可变业务快照 |
| 评论状态未知 | assignment 进入可恢复的 `BLOCKED`，只允许人工确认后 RESUME 或 STOP | 点击后无法确认时不能自动重试，也不能直接丢失运行上下文 |
| 单房多条评论 | 默认 1；大于 1 时按稳定 slot 顺序执行且话术池数量不得小于上限 | 保证崩溃恢复后仍能准确判断每个 slot 是否已经提交 |

若以上任一项调整，需要同步修改配置默认值、校验规则、状态机和验收矩阵。

## 4. 变更范围

本方案计划变更：

1. 将商品卡 runner 从单轮循环改为显式阶段状态机。
2. 增加搜索结果“全部”板块首卡入口、商品详情长停留、推荐商品循环和商品养号轮次门禁。
3. 增加直播板块目标扫描、首页刷新和进房后二次校验。
4. 增加关键词直播养号阶段。
5. 增加结构化阶段配置、共享类型和服务端校验。
6. 增加任务运行快照、阶段事件、检查点和评论幂等归属。
7. 扩展后台配置、调度进度和日志中文展示。
8. 补齐新旧配置、旧 APK 和旧日志事件兼容。

本方案暂不处理：

1. AI 生成评论或 AI 语义匹配。
2. 购买、加购物车、关注、私信、点赞或跳转外部联系方式。
3. 绕过验证码、登录校验、平台风控或系统安装限制。
4. 多平台适配；第二版只验收抖音。
5. 同一设备并行执行多个前台任务。

## 5. 不变范围

1. 任务类型继续使用 `commerce_card_live_comment`。
2. 编排入口继续由任务调度页下发 START、PAUSE、RESUME、STOP。
3. 目标名称、别名、相似度、禁入词和设备绑定继续归直播目标配置中心管理。
4. 商品卡任务继续使用专用 runner；可以复用底层页面识别、目标匹配和普通直播评分工具，但不能调用其他业务 runner 代跑。
5. 普通 `video`、`live` 和 `live_comment` 的业务入口与状态互斥关系不变。
6. 评论成功、失败、跳过都必须写入 `live_comment_actions` 或其后续兼容结构。
7. 手机 Agent 保持常驻；任务结束、暂停或失败不等于退出 Agent。

## 6. 禁止事项

1. 禁止无限滑动、无限刷新或不可中断的长等待。
2. 禁止用商品关键词直接认定目标直播间身份。
3. 禁止在进房后二次校验失败时发送评论。
4. 禁止在全局急停未放行、实时任务开关关闭、无有效审批或服务端未签发短时发送许可时发送评论。
5. 禁止对同一运行、同一直播间重复发送已提交或状态未知的评论。
6. 禁止把新配置继续主要暴露为高级 JSON 文本框。
7. 禁止把本提案描述为当前已经上线的能力。
8. 禁止在迁移元数据未核对前直接执行生产数据库迁移。

## 7. 阶段选择与状态机

### 7.1 阶段选择

配置只使用 `enabledStages`，不再同时设计 `mode`，避免两个字段表达同一件事。

允许的阶段值：

| 值 | 业务含义 |
|---|---|
| `product_nurture` | 商品卡养号，并通过目标直播间门禁确认养号结果 |
| `target_comment` | 进入并校验目标直播间后执行评论 |
| `live_nurture` | 按直播标题关键词进行普通直播观看养号 |

组合规则：

1. `target_comment` 可以独立执行，对应手写原稿第 2 段。
2. `live_nurture` 必须同时启用 `product_nurture`，因为原稿明确要求“养号1成功之后”才能执行。
3. 多阶段启用时执行顺序固定为 `product_nurture -> target_comment -> live_nurture`。
4. `product_nurture` 与 `target_comment` 连续执行时，共用已经验证的目标直播间上下文，阶段二不重新扫描。
5. `product_nurture` 未启用时，`target_comment` 从目标直播间门禁开始。

### 7.2 任务生命周期

服务端 assignment 运行状态：

```text
PENDING
-> DISPATCHED
-> RUNNING
-> PAUSING -> PAUSED -> RESUMING -> RUNNING
-> BLOCKED -> RESUMING -> RUNNING
-> SUCCEEDED | FAILED | CANCELLED | EXPIRED
```

状态说明：

| 状态 | 含义 |
|---|---|
| `PAUSING` | 已收到 PAUSE，等待手机停在稳定检查点 |
| `PAUSED` | 检查点已落盘且暂停回执已上报 |
| `BLOCKED` | 验证码、账号不一致、评论状态未知或平台风控阻断；不是业务终态，禁止自动继续，只能人工处理后显式 RESUME 或 STOP |
| `CANCELLED` | 收到 STOP 或被其他任务明确替换 |
| `EXPIRED` | 超过任务绝对有效期，不能再 RESUME |

终态只有 `SUCCEEDED`、`FAILED`、`CANCELLED`、`EXPIRED`。`BLOCKED` 不写 `completedAt`，但必须记录 blocker 类型、进入时间、处理人和解除结果。

### 7.3 assignment 与控制命令

第二版必须把“运行”和“命令”拆开：

1. START 在事务中创建一个 assignment 和第一条 START command。
2. 一个 assignment 可以关联多条 command；PAUSE、RESUME、STOP 必须携带原 `assignmentId`。
3. command 使用 assignment 内单调递增的 `commandSequence` 和幂等键，重复请求返回原命令，不重复改变状态。
4. 每次状态写入携带 `expectedStateVersion`；版本不一致时返回冲突，禁止旧命令覆盖新状态。
5. 同一设备同一时刻只允许一个非终态 assignment。并发 START 必须由数据库约束和事务保证只有一个成功。
6. command 的 `FETCHED/DONE/FAILED/IGNORED` 只描述命令处理结果，不代表 assignment 已业务完成。
7. 旧表中的单一 `commandId` 只能迁为 `startCommandId` 或废弃，不能继续表达整次运行的全部控制历史。

允许的主要控制转换：

| 命令 | 允许的 assignment 状态 | 成功后的状态 |
|---|---|---|
| START | 无现有非终态 assignment | `PENDING -> DISPATCHED -> RUNNING` |
| PAUSE | `RUNNING` | `PAUSING -> PAUSED` |
| RESUME | `PAUSED`、已解除 blocker 的 `BLOCKED` | `RESUMING -> RUNNING` |
| STOP | 任一非终态状态 | `CANCELLED` |

处于 `PAUSING` 或 `RESUMING` 时收到 STOP，STOP 优先；过期 assignment 收到任何 RESUME 都返回 `assignment_expired`。

### 7.4 手机端业务状态

```text
PRECHECK
-> PRODUCT_ENTER_MALL
-> PRODUCT_SEARCH
-> PRODUCT_BROWSE_DETAIL
-> PRODUCT_RECOMMENDATION_LOOP
-> TARGET_GATE_ENTER_LIVE_TAB
-> TARGET_GATE_SCAN
-> TARGET_GATE_VERIFY
-> TARGET_COMMENT_SEND
-> LIVE_NURTURE_SCAN
-> LIVE_NURTURE_WATCH
-> COMPLETE
```

关键回退：

1. 商品养号后的 `TARGET_GATE_SCAN` 未命中，返回 `PRODUCT_SEARCH` 开始下一轮商品养号。
2. 仅评论模式的 `TARGET_GATE_SCAN` 达到候选上限，执行首页刷新后继续扫描。
3. `TARGET_GATE_VERIFY` 进房后二次校验失败，退出当前房间并继续扫描，不允许评论。
4. `LIVE_NURTURE_SCAN` 连续 10 个候选未命中，执行首页刷新后继续。
5. 任一状态遇到风险进入 `BLOCKED`；收到 STOP 进入 `CANCELLED`。

## 8. 三阶段详细流程

### 8.1 阶段一：商品卡养号

入口流程：

1. 启动抖音并进入商城。
2. 点击商城搜索框，使用 `searchKeywords` 的首个有效词搜索；`夏橙` 只是默认配置。
3. 搜索完成后必须定位到结果页“全部”板块。该板块是商品养号首个商品卡来源，不能主动切到直播、店铺或其他非商品结果流。
4. 从“全部”板块商品卡列表中提取商品卡文本，命中 `productKeywords` 后进入商品详情。这里复用搜索结果商品卡关键词匹配能力，只负责打开本轮详情页链路的第一张商品卡。

单商品浏览：

1. 单商品主动浏览时长默认 120 秒。
2. 等待必须拆成不超过 1 秒的可中断片段，并持续检查 PAUSE、STOP、任务切换、风险和绝对过期时间。
3. 浏览期间按页面状态向下滑动，记录实际进入时间、计划时长、实际时长和商品指纹。
4. 识别 `recommendationSignals`，默认包含“你可能还会喜欢”。
5. 进入详情页推荐商品卡列表后，必须先确认候选节点属于商品卡容器，再用 `productKeywords` 匹配商品标题、描述或可见商品文案。只有推荐商品卡容器命中关键词时才点击进入下一张商品详情。
6. 如果当前屏没有命中推荐商品卡，继续在详情页向下滑动并重新识别；不得因为看到普通标签、评论、推荐词或非商品文本命中关键词就点击。
7. 如果详情页连续滑动到底、页面签名长期不变或推荐区无法继续打开新商品，并且本轮 15 分钟仍未结束，可以返回商城搜索结果“全部”板块补充打开下一张关键词匹配商品卡；该回退是兜底，不是每个商品详情浏览后的常规动作。
8. 同一运行内按稳定商品指纹去重，避免在两个商品间反复跳转。

单轮结束：

1. 单轮商品养号主动执行时长默认 15 分钟。
2. 轮次结束后返回系统桌面，再重新启动抖音。
3. 进入抖音直播板块并调用共享目标直播间门禁。
4. 目标直播间验证成功时，阶段一完成。
5. 未验证到目标时返回下一轮商品养号，最多执行 `productNurtureMaxRounds` 轮，并受任务主动执行上限约束。
6. 达到轮次或任务上限仍未命中时，以 `product_target_not_found` 失败结束，不得标记成功。

### 8.2 共享目标直播间门禁

门禁既是阶段一的成功条件，也是独立目标评论模式的入口。

1. 从直播板块逐个读取直播卡片标题、主播名和可见文本。
2. 与 `targetName`、已启用别名、主播别名、`requiredKeywords` 和 `forbiddenKeywords` 匹配。
3. 标准化后相似度达到 `similarityThreshold`，默认 0.90，且未命中禁入词，才允许进入候选房间。
4. 短于 4 个有效字符的名称不使用宽松相似度，只允许标准名或别名精确/包含命中。
5. 进房后再次读取主播名、房间标题和页面文本进行二次校验。
6. 目标身份命中必须使用明确布尔规则：标准名或已启用别名至少命中一项；`requiredKeywords` 全部命中；任一 `forbiddenKeywords` 命中即否决；短名称继续使用严格匹配规则。
7. `targetFingerprint` 只保存本次匹配证据，不作为评论幂等键。证据至少包含命中的名称/别名、必需词、禁入词结果、相似度和截断页面摘要。
8. `roomKey` 必须按稳定来源生成，优先级为平台 roomId/deep link roomId，其次为主播稳定账号 ID 与直播场次标识。不得使用会随评论、人数或标题变化的整屏文本生成 roomKey。
9. roomKey 必须携带 `roomKeyVersion`。无法取得稳定 roomKey 时可以继续只读浏览，但真实评论必须记录 `stable_room_key_unavailable` 并禁止发送。
10. 验证成功后保存 `targetFingerprint`、`roomKeyVersion` 和 `roomKey`。
11. 从阶段一进入且启用了 `target_comment` 时，保持在当前已验证房间，直接进入评论阶段，不重复扫描。
12. 只启用 `product_nurture` 时，验证成功后退出房间并正常完成。

刷新策略：

1. 每次最多检查 `targetLiveMaxRoomsPerRefresh` 个候选，默认 25，配置范围 20 至 30。
2. 从商品养号进入时，达到上限仍未命中就返回下一轮商品养号。
3. 仅评论模式达到上限时，点击左下角首页刷新，再重新进入直播板块。
4. 仅评论模式在 `targetCommentSearchMaxActiveMinutes` 内持续查找；单轮未命中是可恢复事件，不是成功或终态失败。

### 8.3 阶段二：目标直播间评论

1. 进入本阶段前必须已经通过共享门禁、取得稳定 roomKey，并确认当前抖音账号与 assignment 的 `expectedAccountId` 或批准账号一致。
2. 评论 slot 固定为 `0..maxCommentsPerRoom-1`。每个 slot 首次选择话术后冻结 `commentIndex` 和 `commentHash`，PAUSE、RESUME 或进程重启后不得重新随机。
3. 评论前生成稳定幂等键，由 tenant、assignment、target、发送账号、`roomKeyVersion`、roomKey 和 comment slot 组成，不包含轮次、刷新次数或当前页面文本。
4. 手机调用服务端评论预占接口。服务端在同一事务中检查全局急停、当前任务执行开关、有效审批、审批额度、assignment 状态/版本、设备和账号归属、目标、配置哈希、绝对有效期以及跨运行限流。
5. 预占成功时返回原有或新建的 `actionId`、`permitToken` 和短时 `permitExpiresAt`。重复幂等键必须返回原动作，不创建第二条记录。
6. 手机在点击前把 `actionId`、slot、commentHash、permitExpiresAt 写入 `pendingSideEffect`，检查点写入失败时不得点击。
7. 手机以状态版本条件把动作更新为 `submitting`；只有发送许可仍有效且服务端允许转换时才能点击发送。无法联网、许可过期或服务端拒绝时一律 fail closed。
8. 点击发送后立即把动作更新为 `submitted`；确认平台已发送后更新为 `sent`，无法确认时更新为 `unknown`。
9. 恢复时必须先按 actionId 或幂等键查询服务端。`sent`、`submitted` 或 `unknown` 均不得自动重发。
10. `unknown` 使 assignment 进入 `BLOCKED`。后台人工确认原动作是 sent 或 failed 后，才允许显式 RESUME；人工确认过程必须记录操作者和证据。
11. 点击前的输入框、按钮或页面校验失败记录 `failed`，默认使 assignment 进入 `FAILED`；只有明确标记为 retryable 且未消耗过发送许可时，才允许在相同 action 上有限重试。
12. 未取得有效审批导致的跳过记录 `skipped`，不视为系统失败；若启用了阶段三，可以继续执行。
13. 单次审批还必须限制总评论数、账号/目标日上限和跨 assignment 冷却时间，不能通过重复 START 绕过单次运行的 `maxCommentsPerRoom`。

动作状态转换固定为：

```text
planned -> submitting -> submitted -> sent
                                -> unknown
planned/submitting -> failed | skipped
unknown --人工处理--> sent | failed
```

`sent`、`failed`、`skipped` 是动作终态。`permitToken` 只用于一次短时发送授权，不写入普通日志、事件证据或长期检查点；检查点只保存 permitExpiresAt 和 actionId。

### 8.4 阶段三：直播养号2

前置条件：

1. 本次运行已成功完成 `product_nurture` 的目标直播间门禁。
2. `liveNurtureKeywords` 非空。
3. 阶段二可以已成功，也可以因未批准而跳过；已批准但发送失败默认不能继续。

执行规则：

1. 进入抖音直播板块，逐个读取直播标题和可见文本。
2. 命中 `liveNurtureKeywords` 且未命中禁入词时进入房间。
3. 单房观看时长在 10 至 20 分钟之间随机生成。
4. 整体累计观看目标在 70 至 100 分钟之间随机生成。
5. 两个随机值在首次生成后写入检查点，PAUSE、RESUME 或进程重启后不得重新随机。
6. 本阶段不发送评论，不点赞，不关注。
7. 观看累计只统计实际处于匹配直播间的主动观看时间，不统计页面切换、刷新和 PAUSE 时间。
8. 连续检查 10 个候选仍未命中时，点击首页刷新并重新进入直播板块。
9. 达到累计观看目标后以 `live_nurture_completed` 正常完成。

### 9.1 配置唯一来源

| 数据 | 存储位置 | 说明 |
|---|---|---|
| 目标标准名、平台、相似度 | `live_targets` | 目标身份主记录 |
| 直播间名、主播名等别名 | `live_target_aliases` | 不在运行 JSON 中重复维护 |
| 搜索词、商品词、禁入词、运行参数 | `live_target_feature_configs` | `feature_type=commerce_card_live_comment` |
| 设备与目标绑定 | `live_target_device_bindings` | 控制某台手机使用哪个目标 |
| 真实评论执行审批 | `commerce_card_execution_approvals` | 独立于运行 JSON，可撤销、可限额、绑定账号和配置哈希 |
| V2/真实评论运行时控制 | `feature_rollout_controls`、`feature_rollout_device_allowlist` | 默认关闭，维护最低版本、capability TTL、allowlist 和修改审计 |

配置目录和运行快照分开处理：

1. 目标中心 V2 配置与旧 V1 配置可以同时存在；只有全部门禁通过并已经创建 V2 assignment 时，当前响应才完全压制 V1 可执行字段。
2. 目标中心记录内部按 `(featureType, targetCode)` 去重。
3. 创建 assignment 时必须明确 `selectedTargetId`、`targetCode` 和 `configRevision`，并冻结单一 `effectiveWorkflow`；手机 runner 不能从 `liveTargets` 目录中自行取第一个目标。
4. `live_target_feature_configs` 作为配置聚合 revision 的承载记录；目标主档、别名、设备绑定或除 `executeEnabled` 之外的业务运行参数变化时均通过同一服务原子递增 revision 并重算 `config_hash`，运行中配置修改只影响下一 assignment 的业务快照。

| `liveNurtureTotalMaxMinutes` | `100` | 10-240 | 累计观看目标上限 |
| `taskMaxActiveMinutes` | `240` | 30-360 | 任务主动执行上限 |

数组字段继续使用现有结构化列：

1. 商城搜索词使用 `search_keywords`。
2. 商品匹配词使用 `product_keywords`。

### 9.3 执行审批与配置哈希

第二版新增独立执行审批对象，推荐存入 `commerce_card_execution_approvals`：

| 字段 | 说明 |
|---|---|
| `id` | 审批 ID，写入 assignment |
| `target_id`、`device_id` | 批准的目标和设备 |
| `expected_account_id`、`expected_account_name` | 批准的抖音账号身份；至少一个稳定标识存在 |
| `config_hash` | 被批准的规范化执行配置哈希 |
| `comment_pool_hash` | 去空、去重、固定顺序后的话术池哈希 |
| `max_comments_per_room` | 单房上限 |
| `max_total_comments` | 本审批累计可发送总量 |
| `daily_account_target_limit` | 同账号、同目标自然日上限 |
| `valid_from`、`expires_at` | 审批生效和失效时间 |
| `approved_by`、`approved_at`、`approval_reason` | 审批审计 |
| `revoked_by`、`revoked_at`、`revoke_reason` | 撤销审计 |
| `status` | `ACTIVE`、`REVOKED`、`EXPIRED`、`CONSUMED` |

哈希规则：

1. `config_hash` 只能由服务端计算，使用带版本号的 canonical JSON 和 SHA-256；Web 和手机只消费结果，不自行拼接哈希。
2. 哈希必须覆盖 targetId/targetCode、平台、目标名、启用别名及类型、相似度、必需词、禁入词、搜索词、商品词、启用阶段、评论池、评论上限和所有影响页面路径、匹配判断或副作用范围的业务运行参数。
3. `executeEnabled`、全局急停、allowlist、capability、审批状态、审批额度和短时发送许可属于实时安全控制，不进入 `config_hash`，不递增配置 revision，也不因自身变化撤销审批；它们只在评论预占时动态检查并写审计。
4. 审批元数据、操作者、创建时间等不影响执行语义的字段不进入 `config_hash`。
5. assignment 另外保存覆盖完整 `effectiveWorkflow` 的 `snapshot_hash`，用于恢复时校验快照完整性；不能用只覆盖敏感字段的审批哈希代替。
6. 修改目标、别名、设备绑定、预期账号或除 `executeEnabled` 之外的业务运行配置时，必须生成新 config revision 和 config_hash；不能只在 `runtime_config_json` 更新时递增 revision。
7. 修改目标身份、别名、设备范围、预期账号、评论池、评论上限或启用阶段时，服务端必须自动撤销同范围 ACTIVE 审批；在途 assignment 下一次预占立即被阻断。
8. 撤销审批或关闭 `executeEnabled` 只阻断后续评论副作用，不热替换 assignment 的浏览、阶段和匹配快照。

### 9.4 校验规则

1. `enabledStages` 至少包含一个阶段。
2. 启用 `live_nurture` 时必须同时启用 `product_nurture`。
3. 启用 `product_nurture` 时 `searchKeywords`、`productKeywords` 和 `recommendationSignals` 非空。
4. 启用 `target_comment` 或 `product_nurture` 时必须绑定有效目标。
5. 启用 `target_comment` 且 `maxCommentsPerRoom>0` 时 `commentPool` 非空，去重后的数量不得小于 `maxCommentsPerRoom`，每条话术必须满足长度和敏感内容校验。
6. 启用 `live_nurture` 时 `liveNurtureKeywords` 非空。
7. 所有最小值不得大于对应最大值。
8. 后台同时计算最短、常规和最坏主动执行时长。`taskMaxActiveMinutes` 小于最坏时长时必须明确显示会提前截断，并禁止把预计最长完成时间展示为可保证结果。
9. 创建 assignment 时 `expiresAt` 必须晚于当前时间加 `taskMaxActiveMinutes`，默认再增加 60 分钟暂停预留；不得继续固定使用 3600 秒。
10. 创建执行审批时，后台必须显示目标、设备、预期账号、评论池、单房上限、审批总额度、日上限和有效期确认信息。
11. 有效发送必须满足全局 `commerceCardRealCommentEnabled=true`、当前 `executeEnabled=true`、审批 ACTIVE、审批 configHash 等于 assignment configHash、审批未过期且额度未耗尽。
12. 目标、别名、设备绑定、预期账号、评论池、评论上限或启用阶段变化时，旧审批自动撤销；其他进入 configHash 的字段变化后，旧审批不能用于新 assignment。
13. `liveNurtureTotalMaxMinutes + productNurtureRoundMinutes * productNurtureMaxRounds` 超过 `taskMaxActiveMinutes` 时，必须拒绝保存或要求用户明确接受安全上限会提前终止，不能静默产生不可完成配置。

### 9.5 第一版字段迁移

| 第一版字段 | 第二版处理 | 说明 |
|---|---|---|
| `searchKeywords` | 迁移到 `search_keywords` | 含义基本一致 |
| `matchKeywords` | 迁移到 `product_keywords` | 第一版主要用于商品卡匹配，不能迁成目标别名 |

| `commentPool` | 原义保留 | 保存时去空值、去重复 |

## 10. 调度、运行数据与恢复

### 10.1 运行实例

复用 `device_task_assignments` 作为一次任务运行，不再另建与分配重复的运行主表。建议增加：

| 字段 | 作用 |
|---|---|
| `selected_target_id` | 本次运行明确选择的目标，禁止 runner 自行取列表第一项 |
| `target_code` | 目标业务编码快照 |
| `config_revision` | 本次运行使用的配置修订号 |
| `config_hash` | 本次运行敏感配置哈希，用于审批校验 |
| `config_snapshot` | 启动时不可变配置快照 |
| `snapshot_hash` | 完整 effectiveWorkflow 的完整性哈希 |
| `execution_approval_id` | 启动时选择的审批记录；发送时仍需检查其当前状态 |
| `expected_account_id`、`expected_account_name` | 本次运行允许使用的抖音账号 |
| `current_stage` | 当前业务阶段 |
| `progress_json` | 轮次、扫描、刷新、观看等当前进度 |
| `started_at` | 手机真正开始执行的时间 |
| `last_event_seq` | 已确认的最后事件序号 |
| `state_version` | assignment 乐观锁版本，状态变化时原子递增 |
| `block_reason` | BLOCKED 原因和待人工处理类型 |
| `terminal_reason` | 终态原因；暂停原因只进入事件，不覆盖终态字段 |

新增 `device_task_assignment_events` 保存状态转换和阶段事件：

1. `assignment_id`、`sequence`、`event_type`。
2. `stage`、`from_state`、`to_state`、`status`、`reason_code`。
3. `idempotency_key`、`evidence_json`、`occurred_at`、`actor`。
4. 唯一约束 `(tenant_id, assignment_id, sequence)` 和 `(tenant_id, idempotency_key)`。
5. 插入事件和更新 assignment 的 `last_event_seq/state_version` 必须在同一事务中完成；出现 sequence 跳号时返回 `event_sequence_gap`。
6. 同一 sequence 或 idempotencyKey 携带不同 payload 时返回冲突，不能按普通重复请求吞掉。

`mobile_commands` 增加 `assignment_id` 和 `command_sequence`，形成 assignment 一对多命令历史。`device_task_assignments.command_id` 迁为可空的 `start_command_id`，后续控制命令不覆盖它。

数据库必须增加“每台设备最多一个非终态 assignment”的并发保护。推荐使用事务锁配合部分唯一约束，不能继续先批量 SUPERSEDE、再无事务创建新 assignment。

扩展 `live_comment_actions`：

1. `assignment_id`、`target_id`、`stage`、`device_id`、`expected_account_id`。
2. `room_key_version`、`room_key`、`comment_slot`、`comment_hash`。
3. `attempt_no`、`action_state`、`state_version`、`idempotency_key`、`assignment_event_id`。
4. `permit_expires_at`、`submitted_at`、`confirmed_at`、`resolved_by`、`resolved_at`。
5. 同一幂等键只能有一条动作记录，状态转换通过更新同一行完成，不能为 planned/submitted/sent 各插一行。
6. 评论动作属于不可删除审计事实；即使支持软删除展示，唯一约束也必须覆盖历史记录，不能删除后重新发送。

动作状态至少支持 `planned`、`submitting`、`submitted`、`sent`、`unknown`、`failed`、`skipped`。`unknown` 不允许自动重试。

业务配置修改只影响下一次运行；已运行或已暂停任务继续使用 `config_snapshot`。全局急停、当前 `executeEnabled`、审批撤销/过期、assignment 状态和发送额度属于实时安全覆盖层，每次预占时重新读取。

配置 revision 以目标功能配置为聚合根，但目标主档、别名、设备绑定和除 `executeEnabled` 之外的业务运行配置变化都必须通过同一服务递增 revision。创建 assignment 时保存 selectedTarget、revision、configHash、snapshotHash 和完整快照；RESUME 校验 assignmentId 和快照完整性，不要求当前目标中心仍停留在旧 revision。

### 10.2 检查点 v2

手机本地 `task-scheduler-state.json` 保存：

```text
checkpointVersion, assignmentId, configRevision, configHash, snapshotHash,
taskType, state, stateVersion, stage, cycleIndex,
stateEnteredAt, stageActiveElapsedMs, taskActiveElapsedMs,
cardIndex, browsedCardFingerprints,
liveScanIndex, liveMissCount, liveRefreshCount,
roomKeyVersion, currentRoomKey, targetFingerprint,
commentActionsByRoom,
plannedWatchMs, completedWatchMs, remainingWatchMs,
pendingSideEffect, expectedAccountId, pageSignature,
checkpointSequence, checkpointHash, updatedAt
```

约束：

1. 不把大段动态评论文本或完整 UI 树写入检查点，只保留截断证据和稳定指纹。
2. 每次进商城、完成搜索、进入/离开商品卡、目标扫描、首页刷新、进房验证、评论前后、观看开始/结束都落稳定检查点。
3. checkpoint 写入失败时停止外部副作用并上报 `checkpoint_write_failed`。
4. 旧版 checkpoint 无法安全升级时，从当前阶段入口重建上下文；涉及状态未知评论时禁止重发。
5. `commentActionsByRoom` 保存 roomKey、slot、actionId、commentHash 和服务端动作状态，不再只保存房间级布尔值。
6. `pendingSideEffect` 至少包含 actionId、idempotencyKey、slot、commentHash、permitExpiresAt 和最后确认状态，不保存完整 UI 树。
7. 手机上报的 checkpoint 摘要必须带单调递增 `checkpointSequence` 和 hash；旧摘要或不同内容的重复序号不得覆盖新进度。

### 10.3 PAUSE、RESUME、STOP

| 命令 | 手机端语义 | 服务端语义 |
|---|---|---|
| START | 使用配置快照创建新运行并从 PRECHECK 开始 | `PENDING -> DISPATCHED -> RUNNING` |
| PAUSE | 停止新点击和输入，在稳定检查点落盘后回执 | `RUNNING -> PAUSING -> PAUSED` |
| RESUME | 读取同一 assignment 检查点，校验页面和 blocker 已解除后恢复 | `PAUSED/BLOCKED -> RESUMING -> RUNNING` |
| STOP | 立即禁止新副作用，落终止检查点并回待命 | 任一非终态 -> `CANCELLED` |

PAUSE 不得被 runner 返回为普通失败。任务主动执行上限不统计 PAUSED 时长，但 `expiresAt` 是绝对时间，过期后必须进入 `EXPIRED`。

进程重启恢复条件：

1. assignmentId 与后台当前运行一致。
2. configRevision 与配置快照一致。
3. checkpointVersion 可识别。
4. 页面上下文能恢复或能从当前阶段入口安全重建。
5. 不存在未处理的 `submitted/unknown` 评论；存在时保持 BLOCKED，先查询或人工处理原动作。
6. 设备仍满足 V2 capability、allowlist 和最低版本门禁。
7. 当前抖音账号仍与 assignment 的 expectedAccount 一致。
8. assignment 的 snapshotHash、stateVersion 和服务端 checkpoint 摘要能够对账。

任一条件不满足时上报 `resume_checkpoint_invalid`，不得从第 1 轮静默重跑。

## 13. 兼容、回退与关联文档

### 13.1 配置和 APK 兼容

1. 第二版配置携带 `configVersion=2`。
2. 设备上报 `supportedCommerceWorkflowVersions`、`checkpointVersion`、`supportsAssignmentResume`、`supportsCommentIdempotency`、`supportsStableRoomKey` 和 `reportedAt`。
3. 新 APK 可以查看第二版配置目录，但执行时只使用 assignment 的单一 `effectiveWorkflow` 快照。
4. 旧 APK 只接收显式第一版快照，不下发其无法识别的第二版阶段组合；第二版无法无损投影时拒绝启动。
5. 兼容读取至少保留一个稳定 APK 版本周期。
6. 启动运行时保存不可变配置快照，运行中修改配置不热替换当前状态机。
7. 同一响应不得让 V1 和 V2 同时成为可执行口径。
8. capability 必须持久化并带上报时间；启动 V2 时同时校验服务端最低版本映射和最近一次 capability。默认超过 10 分钟未更新视为过期，禁止 V2 START/RESUME。
9. 手机自报 capability 不能覆盖服务端已知的最低 appVersion 约束，版本和 capability 任一不足都拒绝 V2。

V1/V2 唯一选择表：

| 条件 | 可执行口径 |
|---|---|
| 已存在非终态 V2 assignment | 只返回该 assignment 的 V2 effectiveWorkflow，不生成 V1 |
| V2 全局开关关闭 | V2 配置只作为草稿/预览；只有明确创建 V1 运行时才执行 V1 |
| V2 开启，但设备不在 allowlist、版本不足或 capability 过期 | 拒绝 V2；如业务仍需 V1，必须由后台显式选择 V1，禁止静默降级 |
| V2 开启，所有门禁通过且配置有效 | 创建 V2 assignment，并完全压制同次响应中的 V1 可执行字段 |
| V2 门禁通过但配置或审批范围无效 | 拒绝启动并返回字段级原因，不自动回退 V1 |

### 13.2 功能回退

增加 `commerceCardWorkflowV2Enabled` 功能开关：

1. 关闭时不创建第二版 assignment；只有后台显式创建第一版运行时才走第一版 runner。
2. 开启时只允许已安装支持第二版 APK 的设备接收任务。
3. 第二版异常时可以关闭开关并安装上一稳定 APK；已产生的运行事件和评论审计不删除。

另设默认关闭的 `commerceCardRealCommentEnabled` 全局急停开关。它必须是服务端可运行时修改、可审计的控制项，不能依赖重新部署才能关闭。业务配置快照不可变，但全局急停、当前 executeEnabled、审批状态/额度、assignment 状态、expiresAt 和风控结果必须在每次评论预占时动态检查；手机只使用短时发送许可，不能长期缓存允许状态。

关闭 V2 时：

1. 拒绝新的 V2 START 和 RESUME。
2. 对在途 V2 assignment 下发 STOP，并保留运行事件和评论审计。
3. 不把 V2 checkpoint 交给第一版 runner。
4. 只有所有 V2 assignment 已终态且设备回到 idle，才允许降级 APK。
5. 重新开启开关不会自动复活已取消或已过期任务。

只完成结构化配置和 Web 表单不代表第二版可执行。在 assignment 快照、状态事件、checkpoint v2、能力门禁和在途回退完成前，V2 开关必须关闭；评论幂等、审批绑定和全局急停完成前，真实评论开关必须关闭。

## 14. 风险与处理

| 风险 | 处理 |
|---|---|
| 三段是否属于同一任务尚未确认 | 使用 `enabledStages` 作为推荐设计，确认前不改代码 |
| 抖音直播板块入口或页面结构变化 | 使用状态识别、文本、OCR 和几何候选组合，并保留真机 fixture |
| 商品详情 120 秒等待无法及时暂停 | 拆成短片段等待，每秒轮询控制命令并落阶段进度 |
| 总任务时长较长 | 使用主动时长和绝对过期双上限，后台显示预计区间 |
| 目标名较短导致误匹配 | 短名称只允许精确或包含命中，进房后二次验证 |
| 崩溃后重复评论 | 评论副作用状态机、稳定幂等键和服务端唯一约束 |
| 同一 assignment 只能关联一个 command | command 增加 assignment 外键和序号，PAUSE/RESUME/STOP 复用同一运行 |
| 并发 START 创建两个运行 | 事务锁、stateVersion 和每设备单一非终态 assignment 约束 |
| 配置快照不可变导致无法即时撤销 | 把全局急停、实时 executeEnabled 和独立审批作为动态安全覆盖层 |
| roomKey 来自动态页面文本 | 定义稳定 roomKey 来源和版本；无法取得时禁止真实评论 |
| 新 assignment 绕过单次评论上限 | 审批总额度、账号/目标日上限和跨运行冷却共同限制 |
| 设备切换抖音账号后继续发送 | assignment 和审批绑定 expectedAccount，PRECHECK 和预占双重校验 |
| PAUSE 被误报失败 | 增加 PAUSING/PAUSED，只有检查点成功后确认暂停 |
| 配置有新旧两套来源 | 目标库优先、旧 JSON 仅兜底，并按目标编码去重 |
| 旧日志页面无法识别新事件 | 保留第一版主事件，新增事件建立中文映射 |
| 数据库迁移漏执行 | 先修复 migration journal，再生成和验证新迁移 |
| 真实评论误触发 | 全局急停、实时任务开关、独立审批、短时发送许可、目标/账号二次校验和动作审计 |

## 15. 验收矩阵

| 场景 | 操作 | 预期 | 证据 |
|---|---|---|---|
| 原稿保留 | 查看两个文档 | 手写原稿未被覆盖，新方案状态为待确认 | Git diff、文件路径 |
| 配置校验 | 启用阶段三但关闭阶段一 | 后台拒绝保存并显示中文原因 | API 校验响应、页面截图 |
| 商品搜索 | 配置非“夏橙”关键词启动 | 手机使用后台词，不存在写死 | 配置快照、运行日志 |
| 单商品浏览 | 进入匹配商品详情 | 计划约 120 秒，期间可 PAUSE/STOP | 时间日志、命令回执 |
| 搜索结果首卡 | 商城搜索关键词后停在“全部”板块 | 只从“全部”商品卡列表点击首个关键词匹配商品，不切直播、店铺或其他结果流 | 录屏、运行日志 |
| 推荐商品循环 | 商品详情页下滑到“你可能还会喜欢”或同类推荐区 | 在推荐商品卡容器内匹配关键词，命中进入下一卡；未命中继续下滑，连续到底后才兜底返回“全部”补卡 | 录屏、状态事件 |
| 商品单轮 | 主动执行达到 15 分钟 | 返回桌面并重新启动抖音 | 时间线、录屏 |
| 阶段转换 | 商品养号后命中目标 | 进入并二次验证；阶段二不重复扫描 | targetFingerprint、状态事件 |
| 商品养号未命中 | 单次目标门禁失败 | 返回下一轮商品养号，不标记成功 | 运行时间线 |
| 仅评论模式 | 连续扫描 25 个候选未命中 | 点击首页刷新并继续，直到成功或主动上限 | 候选计数、刷新事件 |
| 目标误匹配 | 候选相似但进房验证失败 | 退出并继续，不发送评论 | 匹配证据、评论审计为空 |
| 未批准评论 | 打开 executeEnabled 但没有 ACTIVE 审批 | 不发送，记录 skipped 和审批原因 | `live_comment_actions`、审批查询 |
| 评论幂等 | 评论提交后模拟进程退出并恢复 | 不重复发送状态已知或未知的评论 | 幂等键、动作记录 |
| 评论预占断网 | 服务端预占失败或发送许可过期 | 手机不点击发送，记录 fail closed 原因 | API 日志、动作记录 |
| 稳定房间键缺失 | 只能读取动态页面文本，无法取得稳定 roomKey | 允许只读浏览，禁止真实评论 | 门禁事件、评论审计 |
| 评论状态未知 | 点击后杀进程并使平台结果不可确认 | 动作为 unknown，assignment 进入 BLOCKED，人工处理前不能 RESUME | 动作状态、人工处理审计 |
| 审批即时撤销 | assignment 运行中撤销审批或关闭 executeEnabled | 已完成浏览不回滚，下一次评论预占立即被拒绝 | 审批事件、预占响应 |
| 跨运行限流 | 连续创建两个 assignment 指向同一账号和目标 | 第二次受审批总额度、日上限或冷却时间限制 | 审批消费记录 |
| 账号切换 | assignment 运行中切换抖音账号 | PRECHECK/预占识别不一致并进入 BLOCKED，不发送 | 账号证据、状态事件 |
| 阶段三匹配 | 标题命中养号关键词 | 单房随机观看 10 至 20 分钟 | 配置快照、观看事件 |
| 阶段三刷新 | 连续 10 个候选未命中 | 首页刷新后继续 | 刷新计数、录屏 |
| 阶段三完成 | 累计观看达到随机目标 | 在 70 至 100 分钟目标处完成 | 检查点、终态事件 |
| PAUSE/RESUME | 在商品详情、目标扫描、评论前、观看中暂停恢复 | PAUSED 不变 FAILED，恢复同一 assignment 和阶段 | 命令回执、检查点对账 |
| 命令一对多 | 同一 assignment 依次 PAUSE、RESUME、STOP | 命令各有独立 ID/序号，assignmentId 始终不变 | command 时间线、数据库记录 |
| 命令乱序 | RESUME 先于 PAUSE DONE 到达或重复发送旧命令 | stateVersion 冲突，旧命令不覆盖新状态 | API 冲突响应、状态事件 |
| 并发启动 | 同一设备同时提交两个 START | 数据库只允许一个非终态 assignment，另一个明确冲突 | 数据库约束、API 响应 |
| STOP/任务切换 | 任一阶段停止或切换任务 | 不再点击、输入或发送，Agent 回待命 | 运行终态、心跳 |
| 风控 | 出现验证码或登录异常 | 立即 BLOCKED，不自动绕过；人工解除后才允许显式 RESUME | 风控日志、状态事件 |
| 绝对过期 | 默认完整流程运行超过当前 1 小时旧默认值 | 使用显式 expiresAt；到期后进入 EXPIRED，不能恢复 | assignment、时间线 |
| 旧 APK | 未升级设备拉取任务 | 只接收第一版兼容配置或被禁止启动第二版 | 版本门禁日志 |
| V1/V2 选择 | 逐项组合全局开关、allowlist、版本和 capability | 每种条件只有一个明确执行口径，不静默降级 | 选择决策日志、响应快照 |
| 任务隔离 | 分别启动 live、live_comment、commerce 任务 | 只有 commerce 进入本状态机 | 调度日志、定向测试 |
| 后台展示 | 查看任务和日志详情 | 使用中文阶段、进度和原因，不以系统 ID 为主展示 | 页面截图 |

真机验收至少保留：命令回执、结构化运行日志、评论动作审计、关键页面截图或录屏、任务配置快照和最终状态对账。

## 16. 实施顺序

1. 确认第 3 节的任务组合、退出抖音、时长、审批粒度、BLOCKED 恢复和评论失败策略。
2. 同步修订第 13.3 节列出的现行方案，明确第二版尚未上线。
3. 审计并修复 Drizzle migration journal，再设计数据库 migration。
4. 先确定 assignment/command 一对多模型、完整状态转换表、stateVersion 和单设备运行唯一约束。
5. 扩展共享类型、第二版配置 schema、完整 effectiveWorkflow、canonical hash 和目标聚合 revision。
6. 建立独立执行审批、全局运行时急停、审批额度和 capability 持久化模型。
7. 建立评论 reserve/update/query/resolve 协议、稳定 roomKey 和 comment slot 规则。
8. 改造后台配置表单、审批确认、任务启动参数、绝对过期时间和阶段进度展示。
9. 新增纯领域状态机和 checkpoint v2，先用虚拟时钟覆盖状态转换、乱序命令和恢复对账。
10. 把 `commerce-card-live-runner.js` 收敛为编排器，拆分商品养号、目标门禁/评论和直播养号处理器。
11. 在 `douyin.js` 增加商城搜索结果“全部”板块首卡入口、详情页推荐商品卡容器扫描、直播板块候选扫描、稳定房间身份、账号校验、首页刷新和页面恢复原子动作。
12. 补充并发 START、命令乱序、PAUSE/RESUME/STOP、任务切换、审批撤销、断网 fail closed、崩溃恢复和评论幂等测试。
13. 运行前后端 lint、typecheck、测试和构建；运行手机端定向测试及 `node --check`。
14. 打包新 APK，在关闭真实发送的条件下完成多机真机流程回归。
15. 单独开启受控评论验收，对账全局急停、实时开关、执行审批、短时许可、目标/账号验证、幂等键和评论动作审计。
16. 验收通过后开启 `commerceCardWorkflowV2Enabled`，更新项目记录、卡点记录和代码审查风险记录。
