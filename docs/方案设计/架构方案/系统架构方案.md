# 系统架构方案

本文是当前项目唯一架构方案入口，合并原后台监控架构、手机自动化脚本架构和任务切换重构中的架构结论。已废弃的 ZIP 自动更新方案不再作为当前架构组成部分。

## 1. 架构目标

当前系统要解决三个问题：

1. 手机端脚本可以长期常驻，稳定拉取配置、执行任务、上传心跳、日志和结果。
2. 后台可以集中管理设备、任务、命令、采集记录、直播评论动作和日志。
3. 视频、直播、直播评论任务能从后台切换，并逐步支持手机端从不同抖音页面恢复到目标任务上下文。

系统不追求一次性大规模设备编排，当前目标是小范围真机联调、可观测、可回退、可排查。

## 2. 总体结构

```text
后台 Web
  -> 调用后台 API
  -> 查看设备、任务、日志、采集记录、直播评论和配置

后台 API
  -> 维护设备、任务模板、设备覆盖配置、命令队列、心跳、日志和结果
  -> 向手机端提供注册、配置拉取、命令拉取、结果上传接口

手机 Agent
  -> 常驻轮询后台配置和命令
  -> 通过 AutoX.js 操作抖音
  -> 执行视频、直播、直播评论任务
  -> 上报心跳、结构化日志、完整日志和执行结果

PostgreSQL / Redis
  -> PostgreSQL 保存业务状态、日志和审计数据
  -> Redis 用于后台运行辅助能力
```

## 3. 模块边界

| 模块 | 职责 | 不承担 |
|---|---|---|
| 手机 Agent | 页面识别、任务执行、抖音操作、状态上报 | 不决定多设备调度策略 |
| 后台 API | 设备认证、配置合并、命令队列、数据入库、后台查询 | 不直接控制手机屏幕 |
| 后台 Web | 运营查看、配置保存、命令触发、日志排查 | 不保存业务主状态 |
| PostgreSQL | 设备、任务、命令、日志、采集结果、直播评论动作 | 不存放 APK 构建产物 |
| Redis | 运行期辅助能力 | 不作为任务审计主存储 |

## 4. 技术栈

| 层级 | 技术 |
|---|---|
| 手机端 | AutoX.js / JavaScript / Android |
| 后台 API | Bun + Hono |
| 后台 Web | React 19 + Vite + Ant Design |
| 数据库 | PostgreSQL + Drizzle ORM |
| 缓存 | Redis |
| 部署 | Docker Compose |
| APK 构建 | Gradle |

## 5. 数据分层

当前数据库按职责分层：

| 层级 | 代表对象 | 用途 |
|---|---|---|
| 设备层 | `collector_devices` | 设备身份、token、版本、在线概况和账号画像 |
| 配置层 | `collection_tasks`、`device_task_configs` | 公共任务模板和设备级覆盖配置 |
| 命令层 | `mobile_commands` | 后台向手机下发启动、暂停、停止、刷新配置等命令 |
| 事实层 | `device_heartbeats` | 手机最近实际状态、任务、进度和原始心跳 |
| 结果层 | `collection_records`、`live_comment_actions` | 采集结果和直播评论计划、跳过、失败、发送记录 |
| 日志层 | `runtime_logs`、`device_log_files` | 结构化运行事件和完整日志文件 |
| 版本层 | `agent_versions`、`agent_update_events` | Agent 版本检查和更新事件审计 |

后续如实现后台统一任务调度，可新增 `device_task_assignments` 作为“后台期望任务状态层”。该表只记录任务分配和调度审计，不复制心跳、日志和命令结果。

## 6. 手机端架构

手机端按五层组织：

| 层级 | 职责 |
|---|---|
| Task Scheduler | 维护 `video`、`live`、`live_comment` 当前活跃任务和切换状态 |
| Page Detector | 识别当前抖音页面、弹窗、网络异常、搜索页、直播间等状态 |
| Recovery Router | 根据目标任务恢复到标准上下文 |
| Task Flow | 执行视频采集、直播采集、直播评论业务流程 |
| Action Verifier | 校验动作结果，上报失败原因和上下文 |

核心原则：

1. 任务流程不再假设每次都从抖音首页开始。
2. 任务启动前先恢复到目标上下文。
3. 长循环、等待、搜索、直播间停留和发送前都要检查任务是否被后台切换。
4. 未确认目标直播间时不能真实发送评论。
5. 未知弹窗、权限弹窗、网络异常要先上报清楚，再按保守策略处理。

## 7. 标准上下文

| 上下文 | 目标 |
|---|---|
| `feed_context` | 视频任务或普通直播发现可继续 |
| `video_playback_context` | 视频任务可播放、滑动和采集 |
| `search_input_context` | 可以输入新搜索关键词 |
| `search_result_context` | 已在指定关键词搜索结果页 |
| `target_live_room_context` | 已进入并确认目标直播间 |
| `live_comment_ready_context` | 直播间内可输入或发送评论 |

直播评论任务要求恢复到 `target_live_room_context`；视频任务要求恢复到 `video_playback_context`；普通直播任务可以从 `feed_context` 或直播发现上下文开始。

## 8. 后台命令链路

```text
后台页面保存配置或点击控制按钮
-> 后台 API 写入配置或 mobile_commands
-> 手机 Agent 轮询命令
-> 手机 Agent ACK 命令
-> taskScheduler 更新当前任务
-> 手机端恢复目标上下文并执行
-> 心跳、日志、结果回传后台
```

命令表只负责传输和回执，不能替代任务实际状态。实际状态以手机心跳和运行日志为准；直播评论结果以 `live_comment_actions` 为准。

## 9. 后台任务调度方向

当前后台已有命令下发和手机端任务切换基础，但统一调度还在收敛中。目标方向是引入 Task Orchestrator：

```text
后台页面/自动计划/直播评论活动
-> Task Orchestrator 计算设备期望任务
-> 写入任务分配记录
-> 生成 mobile_commands
-> 手机端切换 activeTaskType
-> 心跳上报 actualTaskType
-> 后台对账并重试或标记失败
```

调度优先级：

| 优先级 | 规则 |
|---|---|
| 最高 | 管理员 STOP 或设备禁用 |
| 高 | 手动指定任务 |
| 中高 | 直播评论活动抢占视频/普通直播 |
| 中 | 普通直播采集 |
| 普通 | 视频采集 |
| 低 | 无任务时待命 |

## 10. 日志与可观测性

系统必须同时保留两类日志：

1. `runtime_logs`：结构化事件，适合后台列表、筛选、失败原因、任务切换排查。
2. `device_log_files`：手机完整日志最近内容，适合还原脚本运行细节。

关键事件需要记录：

| 事件 | 需要字段 |
|---|---|
| 任务切换 | 当前任务、新任务、命令 ID、原因 |
| 页面识别 | 页面状态、置信度、可见文本样本、activity、失败原因 |
| 上下文恢复 | 起始状态、目标上下文、动作、尝试次数、结果 |
| 搜索直播间 | 关键词、目标主播、是否找到直播入口、失败原因 |
| 评论动作 | 计划、跳过、失败、发送、目标直播间校验结果 |
| 权限和弹窗 | 弹窗类型、处理策略、是否阻断任务 |

## 11. 安全边界

1. 不绕过验证码、登录异常、账号风控和平台安全限制。
2. 不采集非公开内容。
3. 不默认执行点赞、关注、私信等真实互动。
4. 评论真实发送必须同时满足目标直播间确认、`allowRealSend=true`、发送次数和间隔限制。
5. 风控、验证码、登录异常、未知阻断状态出现时，优先暂停或等待人工处理。

## 12. 部署边界

生产环境使用 Docker Compose 部署后台 API、Web、PostgreSQL 和 Redis。移动端通过 APK 安装测试。

当前不再维护手机 Agent ZIP 自动更新链路：

1. 不再上传 ZIP 更新包到服务器。
2. 不把 ZIP 自动更新作为验收项目。
3. 手机端版本以 APK 安装和后台版本记录为准。
4. 历史版本回退以 Git 标签、APK 文件和服务器部署记录为准。

## 13. 回退原则

1. 后续重构必须保留当前可运行版本作为基线。
2. 手机端状态驱动恢复、任务切换中断、后台调度都要分阶段上线。
3. 每个阶段都应能关闭新逻辑，回到旧任务执行路径。
4. 数据库优先新增字段或新增表，不破坏现有字段含义。
5. 生产部署前记录提交号、镜像时间、数据库迁移和 APK 版本。
