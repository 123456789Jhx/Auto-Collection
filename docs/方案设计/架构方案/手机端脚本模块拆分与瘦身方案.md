# 手机端脚本模块拆分与瘦身方案

> 状态：架构治理方案，待确认，暂不实现。
>
> 来源：2026-07-15 商品卡养号联调复盘；用户反馈 `douyin.js` 和 `app` 目录内 runner 文件过大，影响性能、review 和功能稳定性。
>
> 范围：仅规划 `mobile-agent/autojs/` 的 AutoX.js/CommonJS 脚本拆分、职责边界、验证方式和落地顺序；不直接修改代码。

## 1. 背景与现状

手机端脚本已经从视频采集扩展到直播、直播评论、商品卡养号、目标直播间门禁、后台命令、心跳和任务状态恢复。功能持续叠加后，部分文件承担了过多职责。

当前重点大文件规模：

| 文件 | 行数约值 | 当前职责 |
|---|---:|---|
| `mobile-agent/autojs/platforms/douyin.js` | 4573 | 抖音启动、搜索、商城、商品卡、直播页、目标匹配、页面恢复、点击与滑动 |
| `mobile-agent/autojs/app/commerce-card-live-runner.js` | 1697 | 商品卡 V1/V2 runner、阶段状态、后台事件、商品卡养号、目标直播间、评论动作 |
| `mobile-agent/autojs/app/control-loop.js` | 1375 | 常驻命令轮询、任务切换、状态上报、开始暂停停止 |
| `mobile-agent/autojs/app/collector-app.js` | 1199 | Agent 主入口、任务执行、配置应用、收尾 |
| `mobile-agent/autojs/core/uploader.js` | 1186 | 后台通信、日志、心跳、上传和辅助哈希 |

主要问题：

1. `douyin.js` 同时包含平台基础能力和多个业务流程，review 时难以定位影响范围。
2. 商品卡识别逻辑继续写进 `douyin.js` 会进一步扩大单文件复杂度。
3. `commerce-card-live-runner.js` 同时管业务状态机、后台上报和页面操作，调试链路容易混在一起。
4. AutoX.js 运行在手机端，超大脚本会增加解析、内存和异常定位压力。
5. 文件大不是唯一性能问题；如果拆分后启动时仍一次性 `require` 所有模块，启动解析压力不会明显下降。

## 2. 核心结论

1. 必须先做职责拆分，再做业务修复；否则商品卡推荐区识别、OCR 兜底和三轮养号会继续堆进大文件。
2. 拆分目标不是“为了拆文件而拆文件”，而是让每个模块只有一个稳定职责。
3. 性能优化不能只靠文件变小，还要避免启动阶段加载不需要的业务模块。
4. 第一阶段应保持行为不变，只抽出无副作用或低副作用的逻辑，降低回归风险。
5. `douyin.js` 应逐步退回“抖音平台适配器”，不再承载商品卡完整业务规则。
6. `commerce-card-live-runner.js` 应逐步退回“任务编排与后台状态上报”，不再直接写页面识别细节。
7. 新模块必须继续使用 AutoX.js 现有 CommonJS 风格，不能直接套用 Web 端 TypeScript/ESM 模式。

## 3. 设计目标

### 3.1 代码结构目标

目标结构：

```text
mobile-agent/autojs/
  app/
    commerce-card-live-runner.js
    product-nurture-runner.js
  platforms/
    douyin.js
    douyin-commerce-actions.js
    douyin-live-actions.js
  domain/
    commerce-card/
      candidate-detector.js
      recommendation-zone.js
      card-signature.js
      product-keyword-matcher.js
      ocr-card-detector.js
    product-nurture/
      round-flow.js
      target-gate-flow.js
      result-state.js
  core/
    uploader.js
    control-command-client.js
    heartbeat-reporter.js
```

说明：

1. `platforms/` 只放和抖音 UI 具体操作强绑定的能力。
2. `domain/` 放可单测的业务判断、候选打分、状态转换和结果归一化。
3. `app/` 放任务入口、后台交互、阶段编排和异常收口。
4. `core/` 放通用基础设施，例如上传、心跳、命令客户端。

### 3.2 文件规模目标

建议目标：

| 类型 | 建议上限 | 说明 |
|---|---:|---|
| 平台适配器 | 1500 至 2500 行 | `douyin.js` 可作为过渡期例外，但要持续下降 |
| 业务 runner | 600 至 900 行 | 只保留状态编排和上报 |
| domain 模块 | 100 至 500 行 | 优先保持纯函数或轻依赖 |
| core 基础设施 | 300 至 800 行 | 超出后继续按客户端、序列化、重试拆分 |

不要求一次达标，但每次新增业务能力时不得继续扩大已有超大文件。

## 4. 模块职责边界

### 4.1 `douyin.js` 保留内容

保留：

1. 打开抖音、回到首页、进入商城、进入直播 tab。
2. 基础搜索动作、输入、提交、页面等待。
3. 基础点击、滑动、返回和页面上下文判断。
4. 读取当前屏幕文本、节点 bounds、通用弹窗处理。
5. 对外暴露稳定的平台能力接口。

逐步移出：

1. 商品卡推荐区识别规则。
2. 商品卡候选打分。
3. 商品卡浏览轮次。
4. 目标直播间三轮门禁状态机。
5. 商品卡 OCR 分块策略。
6. 业务结果状态归一化。

### 4.2 商品卡 domain 模块

建议新增：

| 模块 | 职责 |
|---|---|
| `domain/commerce-card/recommendation-zone.js` | 判断 `你可能还会喜欢`、推荐 tab、推荐列表区域 |
| `domain/commerce-card/candidate-detector.js` | 根据 bounds、文本、商品信号枚举商品卡候选 |
| `domain/commerce-card/product-keyword-matcher.js` | 聚合商品标题、价格、销量、OCR 文本并匹配关键词 |
| `domain/commerce-card/card-signature.js` | 生成商品详情签名，判断点击前后是否进入新商品 |
| `domain/commerce-card/ocr-card-detector.js` | OCR 兜底识别商品卡图文，默认低优先级调用 |

要求：

1. 尽量只接收普通对象、文本、bounds 字符串和配置。
2. 不直接调用 `textMatches`、`descMatches`、`click`、`swipe` 等 AutoX.js 全局 API。
3. 可以被 Node 测试直接覆盖。
4. 输出候选列表和原因，便于日志解释为什么点某张卡。

### 4.3 商品卡平台动作模块

建议新增 `platforms/douyin-commerce-actions.js`。

职责：

1. 把 AutoX.js 无障碍节点转换为 domain 可处理的候选输入。
2. 根据 domain 返回的候选执行点击。
3. 截取推荐列表区域供 OCR 使用。
4. 处理抖音商品详情页的真实滑动、等待和返回。

该模块可以依赖 AutoX.js API，但不直接决定业务状态。

### 4.4 商品卡养号流程模块

建议新增 `domain/product-nurture/round-flow.js`。

职责：

1. 组织单轮 15 分钟商品卡浏览。
2. 控制首卡来自“全部”板块。
3. 控制后续卡来自详情页推荐列表。
4. 记录本轮浏览数量、跳转成功次数、推荐识别策略。
5. 返回本轮结果：完成、异常、暂停、取消。

建议新增 `domain/product-nurture/target-gate-flow.js`。

职责：

1. 单轮商品卡结束后，要求退出抖音。
2. 重新打开抖音并进入直播板块。
3. 扫描目标直播间候选。
4. 返回命中、未命中或异常。

建议新增 `domain/product-nurture/result-state.js`。

职责：

1. 统一三轮闭环状态。
2. 区分养号成功、养号失败、异常中止、暂停、取消。
3. 给 runner 提供后台可上报的标准 reason code。

### 4.5 runner 模块

`commerce-card-live-runner.js` 最终只保留：

1. 解析后台下发的 `effectiveWorkflow`。
2. 设置当前阶段。
3. 调用 product nurture 模块。
4. 调用目标评论模块。
5. 调用直播养号模块。
6. 上报阶段事件、checkpoint 和最终结果。

不再直接写：

1. 商品卡候选识别。
2. 推荐区识别。
3. 商品卡点击细节。
4. 直播候选页面滑动细节。
5. 复杂的商品卡内部循环。

## 5. 性能治理原则

### 5.1 文件拆分不等于性能提升

AutoX.js/CommonJS 下，如果入口启动时一次性 `require` 所有模块，总解析量仍然存在。拆分主要先降低维护复杂度。

真正有助于性能的是：

1. 只在任务需要时加载业务模块。
2. 商品卡任务不加载普通视频/直播评论内部模块。
3. 普通直播任务不加载商品卡 OCR 模块。
4. OCR 模块默认延迟加载，只有无障碍识别失败时才加载。
5. 大量正则、关键词集合和候选规则放到模块内缓存，避免循环中重复构建。

### 5.2 建议加载策略

| 模块 | 加载时机 |
|---|---|
| 基础 logger、config、permission | Agent 启动时 |
| control-loop、heartbeat | Agent 启动时 |
| douyin 平台基础适配 | 执行抖音相关任务时 |
| 商品卡识别模块 | 执行 `commerce_card_live_comment` 时 |
| OCR 兜底模块 | 推荐商品卡无障碍识别失败时 |
| 目标评论 runner | 执行目标评论阶段时 |

### 5.3 避免循环依赖

禁止形成：

```text
douyin.js -> commerce-card module -> douyin.js
```

推荐方向：

```text
runner
-> product-nurture flow
-> douyin commerce actions
-> commerce-card domain
```

domain 模块不能反向依赖 runner 或 platform。

## 6. 分阶段落地计划

### 阶段 A：现状盘点与安全护栏

目标：不改行为，只建立拆分边界。

任务：

1. 统计大文件行数、公开函数和被测试覆盖情况。
2. 标记 `douyin.js` 中商品卡相关方法范围。
3. 标记 `commerce-card-live-runner.js` 中商品卡养号状态机范围。
4. 新增或整理现有测试入口，不新增大规模测试框架。
5. 建立模块命名约定和 require 路径约定。

验收：

1. 无业务行为变化。
2. `node --check` 通过。
3. 现有商品卡 runner 测试通过。
4. 文档记录后续抽取顺序。

### 阶段 B：抽出纯判断逻辑

目标：先抽低风险函数。

优先抽出：

1. 商品卡文本信号判断。
2. 推荐区标题判断。
3. bounds 几何过滤。
4. 商品卡候选打分。
5. 商品详情签名生成。

建议模块：

```text
domain/commerce-card/recommendation-zone.js
domain/commerce-card/candidate-detector.js
domain/commerce-card/card-signature.js
```

验收：

1. 抽出前后日志语义不变。
2. 原函数调用路径仍能运行。
3. Node 单测覆盖输入输出。
4. 不引入 AutoX.js 全局 API 到 domain 模块。

### 阶段 C：抽出商品卡点击与推荐区动作

目标：把平台动作和业务识别分层。

任务：

1. 新增 `platforms/douyin-commerce-actions.js`。
2. 从 `douyin.js` 迁移搜索结果首卡点击动作。
3. 迁移详情页推荐卡扫描和点击动作。
4. 保留 `douyin.js` 对外接口，内部委托新模块，减少一次性改动面。

验收：

1. 对外 API 不变。
2. 首卡点击和推荐卡点击日志字段不变或只增不删。
3. 真机日志能看出命中策略：标题、推荐 tab、结构兜底或 OCR。

### 阶段 D：抽出单轮商品卡养号流程

目标：让 runner 不再直接写商品详情循环。

任务：

1. 新增 `domain/product-nurture/round-flow.js`。
2. 承接单轮 15 分钟商品卡浏览。
3. 统一返回本轮商品卡数量、跳转次数、异常原因。
4. 保留 PAUSE、STOP 和任务切换中断点。

验收：

1. 单轮流程可独立测试。
2. 暂停、停止、异常返回 reason 不丢失。
3. `commerce-card-live-runner.js` 行数明显下降。

### 阶段 E：抽出目标直播间门禁和三轮状态机

目标：修正“一轮结束后仍在商品详情页扫描直播间”的流程问题。

任务：

1. 新增 `domain/product-nurture/target-gate-flow.js`。
2. 一轮结束后强制执行退出抖音、重开抖音、进入直播板块。
3. 新增 `result-state.js` 区分养号成功、养号失败和异常中止。
4. runner 只负责把标准结果上报后台。

验收：

1. 3 轮未命中目标直播间时返回养号失败。
2. 页面异常、商城搜索失败、直播板块失败返回异常中止。
3. 手动暂停和停止不被误报为养号失败。

### 阶段 F：延迟加载 OCR 兜底

目标：避免 OCR 相关逻辑常驻增加启动和内存压力。

任务：

1. 新增 `domain/commerce-card/ocr-card-detector.js`。
2. 只在推荐区无障碍识别失败时加载。
3. OCR 返回候选和置信信息，不直接点击。
4. 点击仍由平台动作模块执行。

验收：

1. OCR 未触发时不加载 OCR 模块。
2. OCR 失败不影响无障碍主链路。
3. OCR 命中后仍做页面签名校验。

## 7. 回归验证矩阵

| 场景 | 必须验证 |
|---|---|
| 普通视频任务 | 不受商品卡模块拆分影响 |
| 普通直播任务 | 不加载商品卡内部流程 |
| 搜索直播评论 | 目标直播间搜索和评论链路不变 |
| 商品卡首卡 | 仍从“全部”板块进入 |
| 商品详情推荐区 | 能识别 `你可能还会喜欢` 下方商品卡 |
| 推荐 tab | 能识别 `推荐` tab 选中后的两列商品卡 |
| 三轮闭环 | 未命中目标时继续下一轮，三轮后失败 |
| 异常中止 | 搜索失败、权限异常、页面卡死不记为养号失败 |
| PAUSE/STOP | 暂停和停止语义不变 |
| APK 打包 | 拆分后所有新模块被打进 AutoX.js 包 |

基础命令：

```powershell
node --check mobile-agent/autojs/platforms/douyin.js
node --check mobile-agent/autojs/app/commerce-card-live-runner.js
node mobile-agent/autojs/tests/commerce-card-live-runner.test.js
node mobile-agent/autojs/tests/control-loop.test.js
```

如涉及 APK：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\package-autojs-apk.ps1
```

## 8. 风险与约束

| 风险 | 处理方式 |
|---|---|
| AutoX.js require 路径错误 | 所有新模块用 `files.join(config.runtime.scriptDir, "...")` 引入 |
| 循环依赖 | domain 不依赖 app/platform，platform 不反向 require runner |
| 拆分后行为漂移 | 每阶段先保持对外接口和日志字段稳定 |
| 模块漏打包 | 打包后检查 zip/APK 中新模块路径 |
| 性能未改善 | 引入懒加载，尤其 OCR 和商品卡专用模块 |
| 真机 API 差异 | domain 层只用普通对象，AutoX.js API 保留在 platform 层 |
| 回退困难 | 每阶段独立提交，避免一次性重构所有任务 |

## 9. 不变范围

1. 不改变后台任务类型 `commerce_card_live_comment`。
2. 不改变现有普通视频、普通直播、搜索直播评论业务入口。
3. 不改变真实评论安全门禁。
4. 不改变设备 token、心跳、日志上传和命令回执协议。
5. 不改变 AutoX.js/CommonJS 写法。
6. 不因为拆分而引入 Web 端构建链路或 TypeScript 编译要求。

## 10. 暂不处理内容

1. 不做全仓库格式化。
2. 不重写所有平台适配器。
3. 不把手机端改成 ESM 或 TypeScript。
4. 不一次性拆完 `control-loop.js`、`collector-app.js` 和 `uploader.js`。
5. 不在未完成测试前替换线上 APK。
6. 不把 OCR 作为默认主识别路径。

## 11. 建议下一步

建议先做阶段 B：

1. 从 `douyin.js` 抽出商品卡纯判断函数。
2. 保持对外函数名和日志不变。
3. 补最小 Node 测试覆盖推荐区标题、推荐 tab、商品卡结构和签名。
4. 通过后再进入平台动作和 runner 流程拆分。

这样能先降低 `douyin.js` 的复杂度，同时不触碰最容易出问题的页面点击和任务状态机。
