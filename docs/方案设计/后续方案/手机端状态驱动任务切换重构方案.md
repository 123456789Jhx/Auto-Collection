# 手机端状态驱动任务切换重构方案

## 1. 文档目标

本文记录手机端后续重构路线，目标是在保留当前可运行版本的基础上，增强脚本从不同抖音页面、弹窗和异常状态恢复到正常任务流程的能力。

当前可回退基线：

| 项目 | 内容 |
|---|---|
| 基线提交 | `9444593 feat: stabilize live comment control flow` |
| 本地回退标签 | `baseline-live-comment-1.0.9` |
| APK 版本 | `1.0.9` |
| 适用范围 | 当前已经可以执行直播评论、刷视频、刷直播的前后台与手机脚本版本 |

后续重构必须以该基线为兜底。任何重构改动如果导致主流程不可用，应能快速回退到该基线。

## 2. 当前判断

当前版本不是推倒重来的对象。后台、设备注册、心跳、日志、配置、任务调度、直播评论生成、执行记录上传和 APK 打包链路已经具备可用基础。

当前主要短板集中在手机端执行层：

1. 脚本仍偏线性流程，默认抖音会处于可预期页面。
2. 任务切换时，脚本知道后台想切换任务，但无法稳定识别当前抖音页面并恢复到新任务需要的上下文。
3. 直播评论从视频任务切换过来时，可能停在视频页、搜索页、评论面板、个人页、直播间或异常弹窗，当前恢复能力不足。
4. 搜索页旧关键词、网络空白、权限弹窗、键盘遮挡和未知浮层会导致任务失败。

因此后续采用渐进式重构：保留现有系统底座，重构手机端页面识别、恢复和任务切换接管能力。

## 3. 不变范围

以下能力不重写，只在必要时做小范围适配：

| 模块 | 处理方式 |
|---|---|
| 后台 Web 页面 | 保留现有页面，只补控制参数和状态展示 |
| API 与数据库 | 保留现有模型，必要时增加日志字段或状态字段 |
| 手机注册、设备 token、心跳 | 保留 |
| 远程命令轮询与 ACK | 保留 |
| `taskScheduler` 任务调度器 | 保留，作为任务切换核心 |
| 直播评论计划生成与安全判断 | 保留 |
| 执行记录上传 | 保留 |
| APK 打包与部署链路 | 保留 |

不做一次性大重写，不删除已验证可用的抖音控件识别、OCR、坐标兜底和日志上传逻辑。

## 4. 重构目标

目标不是让脚本每次都从首页开始，而是让脚本具备从任意常见页面恢复的能力。

目标流程：

```text
后台切换任务
-> 手机端发现 activeTask 改变
-> 当前动作安全中断
-> 识别当前抖音状态
-> 恢复到新任务需要的标准上下文
-> 执行新任务
-> 校验动作结果
-> 上报成功或失败原因
```

以视频任务切换到直播评论为例：

```text
当前正在刷视频
-> 后台启动直播评论
-> 视频采样/滑动循环检测到 activeTask 变为 live_comment
-> 停止当前视频动作
-> detectDouyinState()
-> recoverToTargetLiveRoom(targetRoom)
-> 进入目标直播间
-> 执行评论计划
```

## 5. 总体架构

手机端后续按五层组织：

| 层级 | 职责 |
|---|---|
| Task Scheduler | 管理 `video`、`live`、`live_comment` 当前活跃任务 |
| Page Detector | 识别当前抖音页面状态 |
| Recovery Router | 从当前状态恢复到目标上下文 |
| Task Flow | 视频、直播、直播评论的业务执行 |
| Action Verifier | 校验动作是否成功并上报失败原因 |

核心接口方向：

```text
detectDouyinState()
recoverTo(context, options)
verifyContext(context, options)
shouldInterruptForTaskSwitch(currentTaskType)
```

任务流不再直接假设页面位置，而是先调用恢复层。

## 6. 页面状态模型

新增统一页面状态模型，避免各个功能自己判断页面。

| 状态 | 含义 | 典型处理 |
|---|---|---|
| `not_douyin` | 当前不在抖音 | 拉起抖音 |
| `douyin_feed` | 推荐流或首页 | 可进入搜索或刷视频 |
| `video_playing` | 视频播放页 | 视频任务可继续，直播评论需进搜索 |
| `search_input` | 搜索输入页 | 清空旧词，输入新关键词 |
| `search_result` | 搜索结果页 | 校验关键词是否正确 |
| `search_empty` | 搜索无结果或空白 | 重试、刷新或重新搜索 |
| `network_error` | 网络异常、点击重试 | 点击重试，失败后重新进入上下文 |
| `live_room` | 直播间 | 校验是否目标直播间 |
| `wrong_live_room` | 错误直播间 | 退出并重新搜索目标 |
| `profile_page` | 用户主页 | 找直播入口或返回搜索页 |
| `comment_panel` | 评论面板打开 | 需要关闭或继续输入评论 |
| `share_panel` | 分享面板 | 关闭面板 |
| `product_panel` | 商品、小黄车、购物浮层 | 关闭浮层 |
| `permission_prompt` | 截图、权限等系统弹窗 | 按策略授权或停止 |
| `douyin_popup` | 抖音活动、提示、青少年等弹窗 | 关闭或返回 |
| `unknown_overlay` | 未知浮层 | 截图/日志，保守关闭 |
| `unknown` | 无法判断 | 尝试返回、重启抖音或暂停 |

每次识别结果需要记录：

```text
state
confidence
visibleTextSample
activityName
packageName
blockingReason
```

## 7. 标准上下文

恢复层不以“打开抖音首页”为唯一目标，而是根据任务恢复到标准上下文。

| 上下文 | 目标 |
|---|---|
| `feed_context` | 视频任务或普通直播发现可继续 |
| `search_input_context` | 可以输入新关键词 |
| `search_result_context(keyword)` | 已在指定关键词搜索结果页 |
| `target_live_room_context(targetRoom)` | 已进入并确认目标直播间 |
| `live_comment_ready_context` | 直播间内可打开评论或输入评论 |
| `video_playback_context` | 视频播放页可采集 |

直播评论任务应要求：

```text
recoverTo("target_live_room_context", { targetRoom })
```

视频任务应要求：

```text
recoverTo("video_playback_context", { keyword })
```

直播发现任务应要求：

```text
recoverTo("feed_context")
```

## 8. 任务切换机制

任务切换分两步处理。

第一步：调度层记录新任务。

```text
后台命令 START/RESUME/REFRESH_CONFIG
-> taskScheduler.requestTask(taskType)
-> activeTaskType 更新
```

第二步：执行层安全中断并交给新任务。

```text
当前任务循环每隔短时间检查 activeTaskType
如果 activeTaskType != currentTaskType
-> 设置 interruptReason = task_switched
-> 当前动作返回
-> 主循环启动新任务
```

需要检查任务切换的环节：

1. 视频滑动前后。
2. 视频评论采集前后。
3. 直播间采样间隔。
4. 直播评论计划发送前等待。
5. 搜索重试循环。
6. 长时间 sleep。
7. 网络异常重试循环。

## 9. 视频切直播评论流程

目标：后台从视频任务切到直播评论后，脚本能根据当前抖音页面自动接管。

流程：

```text
1. 后台下发 live_comment START/RESUME。
2. 手机端 taskScheduler 将 activeTaskType 设为 live_comment。
3. 视频任务循环检测到任务切换。
4. 视频任务停止当前动作并返回主循环。
5. live_comment 任务启动。
6. detectDouyinState() 识别当前页面。
7. recoverToTargetLiveRoom(targetRoom) 按状态恢复：
   - 视频页：打开搜索。
   - 搜索输入页：清空旧词，输入目标账号。
   - 搜索结果页：关键词不对则重搜，关键词正确则找直播入口。
   - 评论面板：关闭面板后继续。
   - 个人页：找直播入口或返回搜索页。
   - 直播间：校验是否目标直播间；不是则退出重搜。
   - 网络异常：点重试，失败后重搜。
   - 弹窗：关闭后继续。
8. 确认目标直播间后执行直播评论。
```

## 10. 直播评论搜索规则

指定直播间链路固定为：

```text
读取 targetRoom 配置
-> 搜索 anchorName 或目标关键词
-> 停留综合页
-> 在综合页识别用户直播中入口或直播卡片
-> 点击进入
-> 校验目标直播间
-> 执行评论计划
```

明确不做：

1. 不主动切到“视频”tab。
2. 不主动切到“直播”tab。
3. 不假设抖音刚打开就是首页。
4. 不假设搜索框一定可输入。
5. 不在未确认目标直播间时发送真实评论。

搜索页恢复规则：

| 当前状态 | 处理 |
|---|---|
| 已在搜索输入页 | 点清空或全选删除后重新输入 |
| 已在搜索结果页，关键词正确 | 复用结果 |
| 已在搜索结果页，关键词不正确 | 点击搜索框，清空旧词，重新搜索 |
| 停在“猜你想看”或建议页 | 输入后优先点顶部搜索按钮，失败再点建议 |
| 结果空白 | 先点重试，再下拉刷新，最后重新搜索 |
| 网络异常 | 点重试，失败后重新进入搜索 |

## 11. 异常恢复策略

恢复顺序必须保守：

```text
1. 关闭已知弹窗
2. 处理权限弹窗
3. 处理键盘和输入框
4. 处理网络异常
5. 返回上一层
6. 重新进入目标上下文
7. 最后才重启抖音
```

未知状态不能无限重试：

| 失败类型 | 最大重试 |
|---|---|
| 同一弹窗关闭失败 | 3 次 |
| 搜索关键词重置失败 | 3 次 |
| 目标直播间搜索失败 | 4 次 |
| 网络重试失败 | 3 次 |
| 连续启动流程失败 | 使用 `launchFailurePauseThreshold` |

达到上限后：

```text
暂停任务
上报 failureReason
保留当前页面截图或 visibleTextSample
等待后台或人工处理
```

## 12. 日志与后台可观测性

后续所有关键恢复动作都要上报结构化日志。

推荐字段：

```text
taskType
stateBefore
targetContext
actionName
attempt
stateAfter
success
failureReason
activityName
visibleTextSample
commandId
activeTaskType
```

失败原因应具体，不再只写“启动失败”。

示例：

| 失败原因 | 含义 |
|---|---|
| `search_keyword_reset_failed` | 搜索页旧关键词无法清空或新词未生效 |
| `search_network_retry_failed` | 搜索结果网络异常，多次重试失败 |
| `target_live_card_not_found` | 综合页未找到目标直播入口 |
| `target_live_room_not_matched` | 进入直播间后不是目标 |
| `comment_input_not_found` | 找不到评论输入框 |
| `task_switched` | 当前任务被后台切走 |
| `unknown_overlay_blocked` | 未知浮层阻断 |

## 13. 落地顺序

### 阶段一：只加识别，不改主流程

1. 新增 `detectDouyinState()`。
2. 在关键节点打日志。
3. 不改变当前操作路径。
4. 通过真实运行收集状态样本。

验收：

```text
后台日志能看到视频页、搜索页、直播间、弹窗、网络异常等状态识别结果。
```

### 阶段二：接入直播评论恢复层

1. 新增 `recoverToTargetLiveRoom(targetRoom)`。
2. 先只用于直播评论任务。
3. 重点解决旧搜索页、猜你想看、网络空白、错误直播间。

验收：

```text
从视频页、搜索页、直播间、个人页切入直播评论时，都能进入目标直播间或给出明确失败原因。
```

### 阶段三：任务切换中断

1. 在视频、直播、直播评论长循环中检查 `activeTaskType`。
2. 发现任务切换后安全返回。
3. 新任务通过恢复层接管。

验收：

```text
后台从 video 切 live_comment，不需要重启脚本即可进入直播评论链路。
```

### 阶段四：视频和直播任务接入恢复层

1. 视频任务接入 `video_playback_context`。
2. 直播任务接入 `feed_context` 或 `live_room_context`。
3. 清理重复的页面恢复逻辑。

验收：

```text
从直播评论切回视频，脚本能退出阻塞页面并恢复刷视频。
```

### 阶段五：清理旧线性流程

1. 删除重复兜底逻辑。
2. 将状态识别、恢复和校验集中管理。
3. 完善后台状态展示。

## 14. 回退措施

### 14.1 Git 回退基线

当前可用版本已经打本地标签：

```text
baseline-live-comment-1.0.9
```

查看基线：

```bash
git show baseline-live-comment-1.0.9 --stat
```

如果后续重构改坏，需要临时回到当前版本进行验证：

```bash
git switch -c rollback-live-comment-1.0.9 baseline-live-comment-1.0.9
```

如果明确要让当前分支回到基线，必须先确认不要保留后续改动，再执行：

```bash
git reset --hard baseline-live-comment-1.0.9
```

注意：`git reset --hard` 会丢弃当前分支未提交改动，只能在明确确认后使用。

### 14.2 安全开发方式

后续重构不要直接在基线提交上大块修改，建议：

```bash
git switch -c refactor-state-driven-task-switch
```

每完成一个阶段就单独提交：

```text
阶段一：状态识别日志
阶段二：直播评论恢复层
阶段三：任务切换中断
阶段四：视频/直播接入
阶段五：旧逻辑清理
```

每个阶段都保留可运行 APK。

### 14.3 功能开关回退

重构代码应增加开关，默认可控开启：

```text
runtime.stateDrivenRecoveryEnabled
runtime.taskSwitchInterruptEnabled
runtime.targetLiveRoomRecoveryEnabled
```

如果新恢复逻辑出问题，可以在配置层关闭，临时回到旧路径：

```text
stateDrivenRecoveryEnabled = false
```

### 14.4 APK 回退

当前 APK 版本为 `1.0.9`。后续每个重构版本建议递增：

```text
1.0.10 状态识别日志
1.0.11 直播评论恢复层
1.0.12 任务切换中断
```

如果手机测试失败，直接重新安装 `1.0.9` APK 回退。

### 14.5 服务器回退

后台如果只是新增状态展示和控制参数，应保持兼容旧 APK。

后续部署前要记录：

```text
部署前 commit
部署后 commit
docker compose 镜像时间
数据库迁移编号
```

如果后台改动影响当前手机脚本，应先回滚 Web/API 镜像或切回基线分支重新部署。

### 14.6 数据库回退

后续数据库迁移必须遵守：

1. 优先新增字段，不删除旧字段。
2. 新字段允许为空或有默认值。
3. 不改变旧接口必填字段。
4. 每个迁移写清楚是否可逆。

状态识别和恢复日志优先进入 `runtime_logs.context_json`，不急着新增复杂表。

## 15. 验收场景

后续重构完成后，至少验证以下场景：

| 场景 | 期望 |
|---|---|
| 视频任务运行中切到直播评论 | 自动停止视频动作，进入目标直播间 |
| 搜索页已有旧关键词 | 清空旧词，重新搜索目标账号 |
| 停在“猜你想看”页面 | 能提交新搜索或重新进入搜索输入 |
| 当前在错误直播间 | 退出并重新搜索目标直播间 |
| 当前在目标直播间 | 不重复搜索，直接执行评论 |
| 当前在评论面板 | 关闭或复用评论上下文 |
| 当前在个人主页 | 找直播入口或返回搜索结果 |
| 搜索结果网络异常 | 点重试，失败后重新搜索 |
| 出现权限弹窗 | 按策略处理并继续或暂停 |
| 出现未知弹窗 | 上报日志，尝试保守关闭 |
| 直播评论切回视频 | 退出直播阻塞页面，恢复视频播放上下文 |

## 16. 暂不处理内容

以下内容暂不放入本轮重构：

1. 不重新设计整个后台。
2. 不重写评论生成策略。
3. 不恢复脚本 zip 自动更新链路。
4. 不做多设备并行任务编排重构。
5. 不对抖音所有未知页面做一次性穷举。

本轮只解决一个核心问题：任务切换和异常页面下，手机脚本能识别当前状态并恢复到新任务需要的正常流程。
