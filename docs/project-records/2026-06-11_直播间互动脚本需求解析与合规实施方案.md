# 直播间互动脚本需求解析与合规实施方案

## 1. 背景与来源

本文来源于 2026-06 的《群控需求(1).md》录音笔记，讨论对象是四个手机自动化脚本中的“直播间互动”能力。

原始诉求包含：从直播推荐流自然刷到自家直播间、识别目标直播间、监听固定带头账号评论、触发一批账号发送 `1/2` 或其他预设话术、处理评论漏检、处理弹窗、直播结束后退出。

结合当前项目文档约束，本文把该需求整理为“直播间定位 + 评论监听 + 受控评论执行 + 日志审计”的实施方案。直播间评论是本功能的核心，但必须限定在自有或已授权直播间、自有或已授权账号、预设话术、频率限制、人工启动和全量审计范围内。

## 2. 核心结论

1. 当前核心业务目标：
   - 手机 Agent 能进入公开直播推荐流。
   - 手机 Agent 能识别是否到达目标直播间。
   - 手机 Agent 能观察直播间公开可见评论区。
   - 手机 Agent 能记录目标账号发出的触发消息。
   - 手机 Agent 能在命中触发条件后发送预设评论。
   - 后台能配置评论内容、执行节奏、设备范围、频率限制和停止条件。
   - 后台能展示直播间观察记录、评论执行记录、触发事件、异常和设备状态。

2. 需要改写的原始需求：
   - “批量账号无约束发评论”改为“授权范围内的受控评论执行”。
   - “监听后所有账号立刻回复 `1/2`”改为“按设备分组、冷却时间、单轮去重和全局上限执行”。
   - “漏检后用其他评论补触发”改为“多次采样、触发事件去重、低置信度标记和下一轮补偿”。
   - “弹窗擦掉继续操作”改为“关闭普通系统弹窗；遇到登录、验证码、风控、权限异常立即停机上报”。

3. 当前不建议进入开发的能力：
   - 非授权、非配置范围内的评论执行。
   - 在 M3 P0/P1/P2 中加入关注目标账号动作。
   - 自动关注、自动私信。
   - 模拟真人行为、反检测、绕过平台限制。
   - 根据直播间其他用户评论自动推断并跟评。

## 2.1.1 原始笔记中的点赞与关注边界

复核《群控需求(1).md》和《群控脚本系统需求文档》后，当前结论如下：

| 动作 | 原始笔记是否明确要求 | 当前归属 | 第一阶段处理 |
|---|---|---|---|
| 直播间评论 | 明确要求 | M3 直播间互动核心 | 必做 |
| 直播间点赞 | 笔记不是核心要求，但现有 `_3-抖音直播间互动(1).js` 已包含 | P3 待评估动作 | P0/P1/P2 不做 |
| 关注目标账号 | 原始笔记未明确要求 | P3 授权关注任务 | 不阻塞 M3 P0，后续单独做 |
| 普通视频点赞/关注 | 系统需求文档 M1 中有概率配置 | M1 刷视频养号 | 与 M3 分开配置 |

因此，M3 P0/P1/P2 不把“关注目标账号”作为必做项，避免直播间评论闭环被额外动作拖慢。后续如果员工账号需要关注公司账号，应作为 P3 授权关注任务单独配置，记录员工授权、账号、设备、执行时间和结果。

## 2.1 第一阶段必须先做到的 M3 闭环

根据《群控脚本系统需求文档》里的 M3 要求，第一阶段先不铺完整 M1、M2，也不先做复杂后台调度，优先把直播间评论闭环跑通。

这里的“第一阶段”只是实现顺序，不代表后续能力不做。M3 是必须持续推进的主线能力。当前分为 P0/P1/P2/P3：P0 单机评论闭环，P1 小批量稳定，P2 后台运营化，P3 扩展动作和技术栈评估。

第一阶段最小可用目标：

| 编号 | 能力 | 第一阶段要求 |
|---|---|---|
| M3-1 | 进入直播推荐流 | 按直播标签进入，例如 `健康`，不通过搜索账号进入 |
| M3-2 | 找目标直播间 | 从直播推荐流滑动，识别主播昵称、直播间标题或账号 ID |
| M3-3 | 进入目标直播间 | 识别成功后停留并进入评论监听状态 |
| M3-4 | 监听评论区 | 持续读取当前可见评论，并维护最近 200 条本地消息缓存 |
| M3-5 | 识别目标账号消息 | 只把固定目标账号的评论作为主触发信号 |
| M3-6 | 分组选择评论 | A 组发左选项，B 组发右选项，C 组可发话术型内容 |
| M3-7 | 延迟发送 | 目标账号消息出现后随机等待 `500ms-3000ms` |
| M3-8 | 发送预设评论 | 只能发送配置好的 `1/2`、`是/否`、短话术等内容 |
| M3-9 | 防重复触发 | 同一触发消息每台设备最多响应一次 |
| M3-10 | 日志记录 | 记录触发消息、发送内容、设备、时间、成功/失败原因 |
| M3-11 | 直播结束退出 | 检测到直播结束后退出直播间并结束任务 |
| M3-12 | 异常处理 | 普通弹窗可关闭；登录、验证码、风控、禁言直接停止并上报 |

第一阶段验收不要求先完成完整后台，只要求能用本地配置或后台下发配置跑通单台设备，再扩展到小批量设备分组。

## 2.2 M3 四阶段路线

| 阶段 | 目标 | 主要内容 | 明确不做 |
|---|---|---|---|
| P0 | 单机评论闭环 | 本地配置、进入直播间、监听目标账号、分组评论、本地日志、异常退出 | 后台、远程启停、点赞、关注 |
| P1 | 小批量稳定 | 多设备 A/B/C 分组、评论缓存、去重、冷却、失败停机、统一日志 | 点赞、关注、复杂后台 |
| P2 | 后台运营化 | 后台任务配置、设备心跳、远程启停、执行记录上传、日志看板 | 点赞、关注默认仍不做 |
| P3 | 扩展评估 | 点赞开关评估、授权关注任务、M1/M2 联动、技术栈替代验证 | 不影响 P0-P2 主链路 |

点赞开关不进入 P0/P1/P2，避免评论主链路尚未稳定时增加额外风险。P3 只做评估和独立开关，不和评论触发绑定。

### P0 单机评论闭环

| 任务 | 交付物 | 验收 |

| P0-4 评论区读取 | `comment-reader` 逻辑 | 能输出当前可见评论数组 |
| P0-5 评论缓存 | `comment-cache` 逻辑 | 能保留最近 200 条并去重 |
| P0-6 目标账号触发 | `trigger-detector` 逻辑 | 能识别固定目标账号消息 |
| P0-7 分组评论 | `comment-action-planner` 逻辑 | A/B/C 组选择不同评论 |

| P0-10 异常退出 | 停机原因枚举 | 登录、验证码、风控、禁言、直播结束可退出 |

### P1 小批量稳定

| 任务 | 交付物 | 验收 |
|---|---|---|
| P1-1 设备分组 | 每台设备配置 `groupName` | 不同设备发不同组内容 |
| P1-2 冷却控制 | 单设备冷却记录 | 两次评论间隔不小于配置 |
| P1-3 单触发去重 | `triggerEventId` 去重 | 同一触发只响应一次 |
| P1-4 失败停机 | 连续失败计数 | 超过阈值自动停止 |
| P1-5 日志规范 | 本地 JSON 日志 | 小批量设备日志可对齐分析 |

### P2 后台运营化

| 任务 | 交付物 | 验收 |

| P2-2 设备心跳 | 心跳字段扩展 | 后台可看到 live 状态 |
| P2-3 执行记录上传 | `live_comment_actions` | 后台可查评论结果 |
| P2-4 远程启停 | 命令轮询扩展 | 可暂停、停止、恢复 |
| P2-5 日志看板 | 运行日志筛选 | 可查异常和失败原因 |

### P3 扩展评估

| 任务 | 交付物 | 验收 |
|---|---|---|
| P3-1 点赞开关评估 | 评估结论 | 有是否做、何时做、怎么限流的结论 |
| P3-2 授权关注任务 | 独立任务设计 | 与评论闭环分开执行和记录 |
| P3-3 M1/M2 联动 | 联动流程图 | 明确直播互动和养号/发布的边界 |
| P3-4 技术栈对比 | Auto.js/Appium/uiautomator2/RPA 对比 | 给出主实现和备选方案 |

## 2.2.2 工程结构规范

M3 代码必须按模块拆分，避免把所有逻辑继续堆在单个脚本里。目录深度保持在现有 `mobile-agent/autojs/{app,core,domain,platforms,utils}` 范围内，不新增多层嵌套。

建议结构：

```text
mobile-agent/autojs/
  app/
    phase-runner.js              调度 live 阶段，不直接写评论细节
  core/
    logger.js                    复用
    storage.js                   复用，本地缓存和日志
  domain/
    live-comment-service.js      M3 主业务编排
    live-room-detector.js        目标直播间判断
    comment-cache.js             最近评论缓存和去重
    trigger-detector.js          目标账号触发判断
    comment-action-planner.js    分组评论选择、冷却、去重
  platforms/
    douyin.js                    只放抖音 UI 操作：进入直播、读评论、发评论、退出
  config.js                      增加 liveComment 配置段
```

设计原则：

1. `platforms/douyin.js` 只做平台 UI 操作，不写业务分组和触发策略。
2. `domain/*` 写业务规则，不直接写具体坐标点击。
3. `app/phase-runner.js` 只调度阶段，不塞入评论缓存、评论发送等细节。
4. `core/*` 只放通用能力，如日志、存储、权限、OCR、上传。
5. 不允许新增超过两层的功能目录，例如 `domain/live/comment/action/...`。
6. 能复用现有 `logger`、`storage`、`autojs-utils`、`douyin` 方法时优先复用。
7. 复用前必须确认职责一致；如果复用会让模块职责混乱，就新建同层小模块。
8. 不确定 Auto.js API、抖音控件结构、权限行为时，先列入“待查证问题”，不直接实现。

## 2.2.3 代码审查准则

开发前后都按下面检查：

| 检查项 | 要求 |
|---|---|
| 模块职责 | 一个模块只做一类事 |
| 嵌套深度 | 目录不超过现有层级，函数内避免多层 if/while 嵌套 |
| 配置管理 | 业务参数进入 `config.js`，不散落硬编码 |
| 日志 | 所有关键动作必须有结构化日志 |
| 失败退出 | 失败不能无限重试，必须有阈值 |
| 复用 | UI 点击、等待、日志、存储优先复用现有工具 |
| 文档不明 | 不确定的 API 或平台行为先记录，不写猜测实现 |
| 验收映射 | 每个 P 级任务必须能对应验收项 |

## 2.3 外部资料采纳边界与合理使用参数

参考资料：CSDN 文章《解放双手！我用冰狐智能辅助打造了全自动抖音脚本（附完整代码）》，发布时间为 2025-05-15。该文章包含全自动互动脚本示例，其中有部分内容不适合进入本项目，但可以提炼出运行配置、时长限制、弹窗处理和日志等工程化约束。

可采纳内容：

| 外部资料点 | 本项目采纳方式 |
|---|---|
| 配置化运行参数 | 所有直播间评论参数放入本地配置或后台任务配置，不写死在流程里 |
| 单次运行时长 | 第一阶段单次直播评论任务默认不超过 `120` 分钟 |
| 单日运行建议 | 单设备单日直播评论任务累计不超过 `240` 分钟 |
| 随机等待区间 | 评论触发后使用 `500ms-3000ms`，普通浏览停留另设区间 |
| App 启动等待 | 打开平台后等待首屏加载完成，再开始识别控件 |
| 弹窗处理 | 只关闭普通提示弹窗；登录、验证码、风控、禁言直接停机 |
| 调试与日志 | 保留本地控制台和文件日志，记录每次触发、发送、失败和退出 |

不采纳内容：

1. 非配置范围内的自动点赞。
2. 自动关注。
3. 普通视频流随机评论。
4. 所谓“防检测处理”或规避平台限制的实现。
5. 面向非目标直播间、非授权账号的自动互动。

第一阶段建议默认参数：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `maxRunMinutes` | `120` | 单次任务最长运行时间 |
| `dailyRunLimitMinutes` | `240` | 单设备单日累计运行上限 |
| `startupWaitMs` | `8000` | 打开 App 后等待加载 |
| `sendDelayMinMs` | `500` | 目标账号触发后的最短评论延迟 |
| `sendDelayMaxMs` | `3000` | 目标账号触发后的最长评论延迟 |
| `perDeviceCooldownSeconds` | `10` | 单设备两次评论最小间隔 |
| `localCommentCacheSize` | `200` | 本地评论缓存条数 |
| `maxConsecutiveSendFailures` | `3` | 连续发送失败后停机 |
| `maxPopupRecoveries` | `5` | 单次任务最多普通弹窗恢复次数 |

## 3. 变更范围

| 原始需求点 | 合规落地方式 | 说明 |
|---|---|---|
| 从健康类直播流刷到目标直播间 | 保留为“直播间评论入口” | 先定位直播间，再进入评论监听 |
| 识别自家直播间 | 保留 | 通过主播昵称、直播间标题、可见账号标识、截图 OCR 综合判断 |
| 监听带头账号评论 | 保留为“目标账号触发器” | 只响应后台配置的目标账号和触发词 |
| 根据带头账号自动发 `1/2` | 保留为“受控评论执行” | 按设备分组、冷却时间、单轮上限执行 |
| 评论刷新太快导致漏检 | 增加采样、去重和补偿机制 | 记录看到/未看到、截图证据和采样窗口 |
| 直播结束后退出 | 保留 | 直播结束后停止评论任务并返回推荐页 |
| 弹窗处理 | 部分保留 | 普通提示可关闭；登录、验证码、风控直接停止 |

## 4. 不变范围

1. 手机端仍然是采集执行器，不做复杂业务判断。
2. 后台仍然负责设备、任务、评论策略、记录、日志、待办的管理。
3. 外部采集结果仍作为运营观察材料，不替代原有视频生产生命周期。
4. 当前阶段优先支持抖音单平台，后续按平台适配器扩展。
5. 评论执行只能发生在后台明确授权的直播间、账号、设备和话术范围内。

## 5. 功能方案

### 5.1 直播评论任务配置

后台新增一种任务类型：`live_comment_control`。

第一阶段可以先使用手机端本地配置文件运行，字段与后台任务配置保持一致。后台暂未接入时，至少要支持以下本地配置：

```js
const LIVE_COMMENT_CONFIG = {
  platform: "douyin",
  entryMode: "live_feed",
  liveTagKeywords: ["健康"],
  targetRoomNames: ["天道直播"],
  targetAnchorIds: ["45782013369"],
  leaderAccountNames: ["运营号A"],
  leaderAccountIds: ["leader_001"],
  groupName: "A组-左选项",
  groupReplyRules: {
    "A组-左选项": ["1", "是"],
    "B组-右选项": ["2", "否"],
    "C组-话术": ["幸福安康", "说得对", "确实"]
  },
  sendDelayMinMs: 500,
  sendDelayMaxMs: 3000,
  perDeviceCooldownSeconds: 10,
  localCommentCacheSize: 200,
  maxRunMinutes: 120,
  dailyRunLimitMinutes: 240,
  startupWaitMs: 8000,
  maxConsecutiveSendFailures: 3,
  maxPopupRecoveries: 5
};
```

| 字段 | 示例 | 说明 |
|---|---|---|
| taskId | `live_20260611_001` | 任务 ID |
| platform | `douyin` | 平台 |
| entryMode | `live_feed` | 从直播推荐流进入 |
| liveTagKeywords | `["健康"]` | 直播推荐流标签或入口关键词 |
| targetRoomNames | `["天道直播"]` | 目标直播间名称候选 |
| targetAnchorIds | `["45782013369"]` | 可选，目标主播账号 ID |
| leaderAccountNames | `["运营号A"]` | 带头账号昵称候选 |
| leaderAccountIds | `["leader_001"]` | 可选，带头账号 ID |
| triggerKeywords | `["1", "2", "是", "否", "苹果", "橘子"]` | 触发词，只响应目标账号消息 |
| replyPool | `["1", "2", "是", "否", "幸福安康", "说得对", "确实"]` | 可发送评论池 |
| deviceGroups | `["A组-左选项", "B组-右选项", "C组-话术"]` | 参与任务的设备分组 |
| groupReplyRules | `{"A组-左选项":["1","是"],"B组-右选项":["2","否"],"C组-话术":["幸福安康","说得对"]}` | 分组对应评论池 |
| perTriggerMaxDevices | `20` | 单次触发最多参与设备数 |
| perDeviceCooldownSeconds | `10` | 单设备评论冷却时间，第一阶段按 M3 文档最低要求 |
| perTaskMaxComments | `200` | 单任务评论总上限 |
| sendDelayMinMs | `500` | 触发后最短延迟 |

### 5.3 目标直播间识别

识别目标直播间时，按置信度组合判断，不只依赖单一控件。

| 信号 | 来源 | 权重 |
|---|---|---|
| 主播昵称命中 | 控件文本/OCR | 高 |
| 账号 ID 命中 | 主播主页可见信息 | 高 |
| 直播间标题命中 | OCR/控件文本 | 中 |
| 直播标签命中 | OCR/入口上下文 | 中 |
| 头像或封面相似 | 暂不做 | 低，后续再考虑 |

建议规则：

1. 命中账号 ID 时可直接判定为目标直播间。
2. 只命中昵称时，需要结合直播间标题或其他可见信息。
3. 无法确认时不进入互动流程，只记录疑似直播间截图。

### 5.6 受控评论执行

评论执行是本需求的核心能力，但必须由后台策略约束，不允许设备自行决定无限发送。

执行规则：

| 规则 | 要求 |
|---|---|
| 授权直播间 | 只有目标直播间识别通过后才能评论 |
| 授权触发账号 | 只有目标账号发出的消息可以触发 |
| 授权话术 | 只能从 `replyPool` 中选择，不能自由生成 |
| 单轮去重 | 同一设备对同一 `triggerEventId` 最多发送一次 |
| 单设备冷却 | 未超过 `perDeviceCooldownSeconds` 不发送 |
| 单轮设备上限 | 超过 `perTriggerMaxDevices` 的设备跳过 |
| 单任务总上限 | 超过 `perTaskMaxComments` 后停止评论 |
| 失败停机 | 登录、验证码、风控、禁言、发送失败连续超限时停止 |
| 全量审计 | 每次计划、跳过、发送成功、发送失败都必须记录 |

评论动作字段：

| 字段 | 说明 |
|---|---|
| actionId | 评论动作 ID |
| triggerEventId | 关联触发事件 |
| taskId | 任务 ID |
| deviceId | 设备 ID |
| replyText | 实际发送文本 |
| plannedDelayMs | 计划延迟 |
| status | `planned` / `sent` / `failed` / `skipped` |
| skipReason | 跳过原因 |
| failureReason | 失败原因 |
| sentAt | 发送时间 |
| screenshotFileId | 发送后证据截图 |

### 5.7 漏检处理

原始需求担心评论刷新过快导致部分设备没看到带头账号消息。方案通过采样、去重和下一轮补偿降低漏判，而不是让设备无限跟评。

可做策略：

1. 高频短窗口采样：例如每 800ms 采样一次可见评论区。
2. 连续截图证据：触发前后保留 2 到 3 张截图。
3. 多设备记录去重：后台按 `leaderAccount + triggerText + 时间窗口` 合并事件。
4. 低置信度标记：只看到关键词但没识别到目标账号时，标记为 `suspected_trigger`。
5. 后台提醒人工复核：低置信度事件不直接评论，只进入待办。
6. 下一轮补偿：本轮未命中的设备可以在下一次有效触发中优先加入，但仍受冷却和总上限限制。

必须避免：

1. 根据普通观众或非目标账号开始刷 `1/2` 自动跟随。
2. 为了防漏检而无限刷新评论区。
3. 为了抢评论而提升发送频率。

### 5.8 人工待办

后台根据低置信度触发事件、未找到直播间、设备异常、评论失败等情况生成待办。正常命中的评论执行不需要逐条人工确认，但必须有人工启动任务和人工停止任务入口。

| 待办类型 | 来源 | 处理方式 |
|---|---|---|
| live_trigger_review | 低置信度目标账号触发事件 | 人工查看截图和文本 |
| suspected_trigger_review | 低置信度疑似事件 | 人工确认是否有效 |
| live_room_not_found | 未找到目标直播间 | 人工检查配置 |
| comment_send_failed | 评论发送失败 | 人工检查设备或账号状态 |
| live_exception | 登录、权限、风控、弹窗异常 | 人工处理设备 |

待办详情展示：

1. 直播间名称。
2. 设备 ID。
3. 目标账号名称。
4. 触发文本。
5. 建议回复选项。
6. 证据截图。
7. 采样前后评论文本。
8. 处理结果：已处理、忽略、配置错误、设备异常、重新执行。

## 6. 业务流程影响

```text
后台创建直播评论任务
  -> 手机 Agent 拉取任务
  -> 打开抖音并进入直播推荐流
  -> 自然滑动查找目标直播间
  -> 识别成功后进入评论监听状态
  -> 持续采样公开评论区
  -> 发现目标账号消息后上传触发事件
  -> 手机端按本地任务策略规划评论动作
  -> 满足频控和上限后发送预设评论

```

该流程解决“定位直播间、监听目标账号、发送预设评论、记录执行证据、异常停机”。评论能力是任务核心，其他互动动作不进入本阶段。

## 11. 后续落地顺序

1. 先基于现有 `docs/materials/_3-抖音直播间互动(1).js` 梳理可复用能力：打开抖音、进入直播 Tab、查找目标直播间、进入直播间、关闭弹窗、检测直播结束、发送评论。
2. 在手机端本地配置中补齐 M3 参数：直播标签、目标直播间、目标账号、分组、评论池、延迟、冷却、本地缓存大小。
3. 手机端先跑通单台设备闭环：直播推荐流 -> 目标直播间 -> 监听目标账号评论 -> 延迟发送本组评论 -> 写本地日志 -> 直播结束退出。
4. 增加本地最近 200 条评论缓存和单触发去重，降低评论区快速滚动导致的漏检。
5. 增加失败停机和异常日志：登录、验证码、风控、禁言、连续发送失败。
6. 单台设备稳定后，再接入小批量设备分组：A 组左选项、B 组右选项、C 组话术。
7. 小批量稳定后，再接后台任务模型 `live_comment_control`、评论执行记录上传和后台列表。
8. 最后再做后台可视化配置页和远程启停。

## 12. 验收标准

1. 手机端可以从本地配置读取直播标签、目标直播间、目标账号、分组和评论池。
2. 手机 Agent 可以进入直播推荐流，而不是通过搜索账号进入。
3. 手机 Agent 可以在限定滑动次数内查找目标直播间。
4. 找到目标直播间后，手机 Agent 可以进入直播间并持续扫描评论区。
5. 手机 Agent 可以维护最近 200 条本地评论缓存。
6. 目标账号发言出现在可见评论区或本地缓存中时，手机端可以生成触发事件。
7. 手机端按本机分组选择评论内容：A 组发左选项，B 组发右选项，C 组发话术。
8. 触发后评论发送延迟在 `500ms-3000ms` 之间。
9. 同一设备对同一触发消息最多发送一次。
10. 同一设备两次评论之间至少间隔 `10s`。
11. 评论发送成功或失败都必须写入本地日志。
12. 直播结束、任务超时或用户停止时，手机端可以退出直播间并结束任务。
13. 遇到登录、验证码、风控、权限异常时，手机端停止任务并记录原因。
14. 单次任务达到 `maxRunMinutes` 后必须自动退出。
15. 连续发送失败达到 `maxConsecutiveSendFailures` 后必须停机。
16. 普通弹窗恢复次数达到 `maxPopupRecoveries` 后必须停机。
17. P2 再验收后台任务配置、评论执行记录上传和远程启停。

## 13. 一句话开发原则

直播间能力以评论为核心，但评论只能在授权直播间、授权账号、预设话术、频控上限、全量审计和异常停机的约束下执行。

## 14. 当前代码审查结论

### 14.1 现有结构判断

已审查 `mobile-agent/autojs` 当前结构：

```text
mobile-agent/autojs/
  app/
  core/
  domain/
  platforms/
  utils/
  config.js
```
