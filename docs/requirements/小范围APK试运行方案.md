# 小范围 APK 试运行方案

## 文档目标

本方案用于把当前手机端 AutoJS 脚本封装成独立 APK，先支持 3-4 台手机小范围试运行。目标不是第一版就做完整移动端产品，而是验证“安装 APK 后傻瓜式启动、后台能稳定控制任务”这条链路。

## 核心结论

1. 第一阶段不重写采集自动化逻辑，继续复用 `mobile-agent/autojs`。
2. 第一阶段交付独立 APK，用户不需要安装 AutoXJS，不需要导入脚本。
3. 首次安装仍然需要手动开启无障碍、悬浮窗、电池优化等权限，因为普通 Android 不允许应用静默打开这些权限。
4. 小范围试运行以 3-4 台手机为目标，重点验证心跳、任务控制、日志、采集记录、脚本自动更新。
5. 如果 APK 封装链路稳定，再进入原生 Android 壳或完整产品化阶段。

## 第一阶段范围

### 必须实现

| 模块 | 目标 | 验收 |
| --- | --- | --- |
| APK 封装 | 把当前 AutoJS 项目封装为独立 APK | 手机可直接安装 APK |
| 权限引导 | 引导开启无障碍、悬浮窗、电池优化 | 权限状态可见，未授权时不能开始任务 |
| 脚本启动 | APK 启动 `watchdog.js` 或 `main.js` | 后台能看到设备上线 |
| 后台联动 | 复用现有 API | 心跳、日志、采集记录正常 |
| 任务控制 | 后台启动/暂停/关闭脚本 | 手机能按指令响应 |
| 配置刷新 | 后台保存脚本参数后自动下发刷新配置 | 手机下一轮轮询应用新配置 |
| 脚本更新 | 复用已部署版本接口 | 后台发布新脚本版本后手机自动下载校验 |

### 暂不处理

1. APK 自更新。
2. 原生 Android 重写采集逻辑。
3. 企业 MDM 静默授权。
4. 大规模批量设备运维。
5. 多品牌手机深度保活适配。

## 技术路线

### 路线选择

第一版采用“AutoJS 项目封装 APK”的方式。

```text
现有 AutoJS 脚本
  -> 项目包
  -> 独立 APK
  -> 3-4 台手机安装试运行
```

不采用第一版原生重写的原因：

1. 当前最复杂的业务逻辑已经在 JS 脚本中实现。
2. 原生重写需要重新实现抖音页面识别、点击、滑动、OCR、日志、心跳、任务控制。
3. 小范围验证阶段更需要快速验证运行链路，而不是重写技术栈。

## 运行结构

```text
农业采集助手.apk
├─ 内置 AutoJS 运行环境
├─ 内置脚本项目
│  ├─ project.json
│  ├─ watchdog.js
│  ├─ main.js
│  ├─ main.module.js
│  ├─ config.js
│  ├─ app/
│  ├─ core/
│  ├─ domain/
│  ├─ platforms/
│  └─ utils/
└─ Android 权限入口
```

启动链路：

```text
用户打开 APK
  -> 检查权限
  -> 用户点击启动
  -> watchdog.js 启动
  -> watchdog.js 拉起 main.js
  -> main.js 执行任务、心跳、日志、配置轮询
```

## 当前脚本准备状态

当前脚本已具备 APK 封装所需的主要能力：

1. `project.json` 已定义入口 `main.js`。
2. `config.js` 已指向生产后台 `http://106.54.41.106:18080/api/v1`。
3. `watchdog.js` 已支持自动更新脚本包。
4. 后台已发布 `0.1.1` 脚本包和 sha256。
5. 后台已支持设备 token 一机一设备映射。
6. 后台已支持保存配置后自动下发 `REFRESH_CONFIG`。

## 试运行设备要求

第一批建议 3-4 台 Android 手机，尽量包含不同网络环境：

1. 1 台常驻本地 Wi-Fi。
2. 1 台 4G/5G 移动网络。
3. 1 台弱网或不同运营商网络。
4. 可选 1 台不同品牌手机，用于观察后台保活差异。

手机需要预装：

1. 抖音。
2. 农业采集助手 APK。

首次配置需要人工打开：

1. 无障碍权限。
2. 悬浮窗权限。
3. 截图权限，如果当前脚本流程触发截图授权。
4. 忽略电池优化。
5. 后台运行权限，按手机品牌设置。

## 试运行验收流程

### 1. 安装验证

1. 安装 APK。
2. 打开 APK。
3. 检查权限入口是否可用。
4. 开启权限后返回 APK。
5. 启动脚本。

验收：

1. 后台设备页出现设备。
2. 设备名称和 token 映射正确。
3. 最近心跳在 1 分钟内更新。

### 2. 任务验证

1. 后台点击“启动/继续任务”。
2. 手机打开抖音并开始采集。
3. 后台观察当前状态变为运行中。
4. 后台点击“暂停任务”。
5. 后台点击“启动/继续任务”恢复。

验收：

1. 当前任务显示视频或直播。
2. 心跳持续上传。
3. 任务暂停后脚本不死亡。
4. 恢复后进度继续，不从 0 开始。

### 3. 数据验证

1. 观察采集记录。
2. 观察日志页。
3. 检查 9 号和 10 号日志是否按日期隔离。
4. 检查看板卡片是否固定顺序。

验收：

1. 采集记录有新增。
2. 运行日志有新增。
3. 设备列表和看板卡片不因心跳跳位置。

### 4. 配置验证

1. 后台打开某台设备脚本参数。
2. 修改视频/直播分钟数或评论数量。
3. 保存。
4. 等待手机下一轮轮询。

验收：

1. 后台自动下发刷新配置指令。
2. 手机日志出现配置已刷新。
3. 新配置生效。

### 5. 更新验证

1. 发布一个新脚本版本，例如 `0.1.2`。
2. 后台登记版本 URL 和 sha256。
3. 手机 watchdog 检测新版本。
4. 手机下载、校验、覆盖脚本。

验收：

1. 后台设备目标版本更新。
2. 更新事件有 `CHECKED`、`DOWNLOADED`、`VERIFIED`、`APPLIED`。
3. 更新后主脚本继续运行。

## 后台观察指标

试运行时重点看这些指标：

| 页面 | 指标 | 正常标准 |
| --- | --- | --- |
| 设备 | 最近心跳 | 1-3 分钟内持续更新 |
| 设备 | 当前状态 | 运行中、暂停、离线准确 |
| 看板 | 手机任务进度 | 不因重启或暂停丢失 |
| 日志 | 日期卡片 | 按自然日隔离 |
| 日志 | 异常数量 | 能定位脚本失败原因 |
| 采集记录 | 今日采集 | 有持续新增 |

## 交付物

第一阶段交付：

1. `AgriVideoCollector-0.1.1.apk`
2. APK 安装测试说明
3. 3-4 台手机试运行记录
4. 问题清单和下一版修复项

## 实施顺序

1. 更新脚本项目元信息，确保版本号和入口正确。
2. 使用 AutoJS/AutoX 打包能力生成独立 APK。
3. 在 1 台手机上做安装和启动链路验证。
4. 扩展到 3-4 台手机同时运行。
5. 观察 24 小时，记录心跳、日志、任务、保活问题。
6. 根据试运行结果决定是否进入原生 Android 壳开发。

## 风险与处理

### 权限无法静默开启

普通 Android 不允许应用静默开启无障碍。处理方式是做权限引导和现场一次性配置。

### 厂商后台杀进程

小米、OPPO、vivo、荣耀等手机可能限制后台。第一阶段通过前台运行、忽略电池优化和现场设置降低影响，第二阶段再做品牌化引导。

### APK 封装引擎兼容

不同 AutoJS 分支的打包能力不同。第一阶段优先用能最快产出 APK 的封装方式；如果封装 APK 对当前脚本兼容性差，再转向原生 Android 壳集成脚本运行环境。
