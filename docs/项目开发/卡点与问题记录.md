## 1.1 2026-07-01 直播评论执行层未彻底隔离

现象：

- 后台下发直播评论任务后，手机可能停留在上一轮搜索词页面。
- 直播评论任务可能复用普通直播流程，导致进入非目标直播间。
- 搜索阶段出现风控页时，日志可能继续记录为后续点击失败，而不是明确的 `risk_control`。

根因：

- `live_comment` 只有调度状态分离，执行流程仍可能复用普通 `live` runner。
- 搜索关键词设置后缺少二次校验，无法发现旧关键词残留。
- 风控检测没有覆盖搜索、点击、进房、评论前的全部阶段。

处理方案：

- 以 `docs/方案设计/功能方案/直播评论独立任务闭环修复方案.md` 为唯一修复口径。
- 先确认包含任务切换修复的代码基线。
- 新增或整理直播评论独立 runner。
- 禁止直播评论任务调用普通直播 runner。
- 搜索、目标直播入口、进房、评论、退出都做强校验。
- 三台手机用 ADB 观察完整链路，后台日志与手机画面必须一致。

已落地代码：

- `f073eed fix: stabilize backend task switching`：新增 `run-request-resolver.js`，将后台当前命令解析和旧任务中断前置，避免手机继续执行上一轮任务。
- `bb1e041 fix: improve target live entry fallback`：补充目标直播入口几何兜底识别，减少搜索页错点和非目标直播入口误入。
- `840959a fix: isolate live comment execution flow`：新增 `live-comment-runner.js`，直播评论独立执行搜索、目标入口、进房校验、评论发送和退出收尾，不再复用普通直播 runner。
- `mobile-agent/autojs/project.json` 已提升为 `1.0.21/57`，本地产物为 `dist/apk/燎原星火-1.0.21-inrt.apk`。

验证状态：

- 已补充 `run-request-resolver.test.js`、`live-card-geometry.test.js`、`live-comment-runner.test.js`。
- 2026-07-02 使用 `1.0.22/58` 三机从后台直播评论页下发 `START`：

### 1.1.1 2026-07-02 三机直播评论回归异常

现象：

- 后台下发直播评论 `START` 后，三个命令均被手机拉取并回执 `DONE`，回执内容为 `live comment command accepted; target room execution continues asynchronously`。
- `幸福安康` 成功进入 `爱番茄的蛋` 直播间，发送 1 条评论后记录 `直播评论任务完成`、`农业视频手机采集脚本结束`、`任务结束后退出抖音`。
- `勤能致富` 和 `大道至简2266` 没有进入目标直播间，后台运行日志记录 `直播评论任务失败，已停止`，结束上下文中的 `lastStopReason` 为 `search_keyword_set_failed`。
- 两台失败设备进入 MIUI 无障碍设置页；logcat 记录 `START u0 {act=android.settings.ACCESSIBILITY_SETTINGS ...} from uid ...`，该 UID 与 `com.agri.video.collector` 包 UID 一致。

当前判断：

- 幸福安康评论后立即退出不是正确行为；历史链路是按直播任务时长持续采样并多次评论。根因是独立 `live-comment-runner` 只调用一次 `sampleCurrentRoom()` 后返回，外层随即 `finishTask()` 并退出抖音。
- 两台失败的主因不是“没有直播间”或“进入了错误直播间”，而是搜索关键词输入阶段没有通过校验，直接以 `search_keyword_set_failed` 停止。
- 无障碍设置页是本 APK 拉起的，但本次日志没有打印到 `无障碍服务未开启，跳转设置页` 这条业务日志，说明还需要继续补调用阶段日志或检查 launcher/权限检查重入路径。

待修复方向：

1. `openSearch` 和 `enterSearchKeyword` 必须把每种输入策略的失败原因、当前 activity、焦点输入框、可见文本样本上报到运行日志。
2. 对直播评论任务，搜索关键词输入失败后应停在可解释状态并退出抖音或回 APP 待命，不允许再误跳系统设置页。
3. `permission.ensureAll()` 自动跳设置页只能发生在启动前权限检查阶段；任务执行中、任务失败收尾和后台待命循环不应自动拉起设置页。
4. 如果系统设置值已经包含 `com.agri.video.collector/org.autojs.autojs.core.accessibility.AccessibilityServiceUsher`，即使 `auto.service` 短暂不可用，也应先记录错误并待命，不应直接打开设置页。

2026-07-03 补充修复：

1. `live-comment-runner` 改为按 `durationMinutes` 多轮调用 `sampleCurrentRoom()`，汇总 `sampleCount`、`sentActionCount`、`plannedActionCount` 等结果，避免进房后只评论一轮就收尾。
2. 后台直播评论页保存指定直播间时不再强制写入 `liveCommentMode: "agri_chatbot"`，改为明确写入 `target_follow`，以便继续走 `liveComment.replyPools` 话术数组。
3. 新增回归测试 `testLiveCommentSamplesUntilDurationExpires()` 和 `live-comments-page.test.cjs`，分别覆盖持续采样和目标直播间保存不强制切模式。

### 1.1.2 2026-07-02 直播评论暂停、进房耗时与更新后无障碍弹窗排查

现象：
- 后台直播评论页点击 `PAUSE` 后，手机端可能仍继续搜索、进直播间或完成当前评论链路。
- 后台直播评论从打开抖音、搜索、搜索结果、直播间列表到目标直播间耗时偏长。
- 综合搜索页已出现目标账号且头像带“直播/直播中”标识时，页面可能没有下方大直播卡片；旧逻辑仍可能优先走通用直播卡片扫描或坐标兜底。
- 更新 APK 后立刻启动脚本并从后台下发任务，部分手机会跳到无障碍设置页；等待一段时间后再测，直播评论链路可正常执行且不再弹出设置页。
- 幸福安康曾出现 12 小时限制发言，需要确认是否已闭环。

排查证据：
- 后台命令记录显示，2026-07-02 15:18 左右三台设备的 `PAUSE` 命令被后续 `STOP` 覆盖，状态为 `IGNORED`，原因是 `superseded_by_new_state_command`；这类情况下手机根本不会收到暂停命令。
- 幸福安康 2026-07-02 15:20 的 `PAUSE` 命令被手机拉取并回执 `DONE`，回执结果为 `{ applied: true, taskType: "live_comment_control", commandType: "PAUSE" }`，说明直播评论页按钮本身能下发有效命令。
- 手机端 `live_comment_control` 的 `PAUSE` 只设置 `paused=true`、`liveCommentExecutionEnabled=false`，不设置 `stopRequested=true`；而 `live-comment-runner` 的搜索进房链路主要检查 `shouldStop()`，`shouldStop()` 只看 `exitRequested/stopRequested`，不看 `paused/liveCommentExecutionEnabled`。因此正在搜索或进房时，暂停不会立即中断。
- 成功链路耗时集中在两段：`task_start -> launch_route` 约 18-34 秒；`live_comment_start -> target_room_verified` 约 69-88 秒。三台成功进房记录的 `searchResult.source` 都是 `text_coordinate_fallback`，说明直接结构化识别没有命中，走了坐标/文本兜底路径。
- 用户截图显示，“爱番茄的蛋”在综合搜索页以用户行展示，头像圆环上有“直播”标识，用户行下方是普通视频卡片，不一定出现大直播卡片。这种形态应优先点击目标用户行/头像直播入口。
- `permission.ensureAll()` 只在初始化权限检查阶段主动打开 `android.settings.ACCESSIBILITY_SETTINGS`。更新后立即启动时，Android 设置里可能已显示无障碍已开启，但 AutoJS 服务对象或辅助服务绑定还没稳定可用，权限检查短时间误判后会拉起设置页；等待后再测不弹窗，符合启动竞态特征。
- 代码中已有对“访问被拒绝、操作过于频繁、预计 N 小时后正常访问”等风控文本的识别测试；但 2026-07-01 至 2026-07-02 的运行日志、评论执行记录和完整日志文件没有命中 `12小时/禁言/限制/访问被拒绝/操作过于频繁/risk_control` 等真实线上记录。

当前判断：
- 直播评论暂停问题不是单一前端按钮问题，而是两个问题叠加：后台会用新状态命令覆盖未拉取的旧 `PAUSE`；手机端收到 `PAUSE` 后，对直播评论搜索进房这种长链路没有即时中断能力。
- 慢链路主要卡在目标直播间搜索和进房识别，不是后台命令下发慢。截图场景的直接根因是“头像带直播标识的目标用户行”没有被当成最高优先级直播入口，导致脚本继续尝试通用直播卡片或 `text_coordinate_fallback`。
- 工作台和任务调度页的暂停存在同类风险：只要共用状态命令覆盖规则和手机端协作式暂停模型，就可能出现“页面已暂停、手机仍跑到下一个检查点才停”的现象；任务调度页还需要单独按 assignment 链路回归。
- 更新后误跳无障碍页当前更像启动竞态和权限检测误判，不应通过改业务搜索逻辑处理；应在权限检查层补充多次确认、冷启动等待和“已在系统配置中开启但服务暂不可用时不主动跳设置页”的保护。
- 12 小时限制发言目前不能判定已彻底解决，只能说代码有识别能力、今天没有线上复现。后续如再次出现，需要把风控文本、当前账号、直播间、动作状态和停止原因明确上报为 `risk_control`。

后续处理方向：
1. 后台命令层区分“状态切换”和“紧急控制”，避免 `PAUSE` 在手机拉取前被后续状态命令静默覆盖，或至少在页面明确显示“已被覆盖/未送达”。
2. 手机端直播评论 runner 在搜索、输入、点击直播卡片、进房校验、采样前后统一检查暂停状态；`PAUSE` 要能让长链路快速停在可解释状态。
3. 直播入口识别优先使用目标主播名、直播中标识、卡片区域和进房后主播/标题校验，减少 `text_coordinate_fallback` 的使用次数和固定等待。
4. 权限检查只允许在冷启动授权阶段拉起无障碍设置页；更新后首次启动增加服务绑定稳定等待和诊断日志，不在任务执行失败收尾阶段误跳设置页。
5. 12 小时限制按风控事件处理，不尝试绕过；命中后停止当前账号任务、上报 `risk_control`，并进入账号冷却/人工确认流程。

## 1.2 2026-07-02 AutoJS6 OOM 与线程高频创建

现象：

- 手机出现 `AutoJS6 应用崩溃` 页面。
- 崩溃信息为 `java.lang.OutOfMemoryError: OutOfMemoryError thrown while trying to throw an exception; no stack trace available`。
- 部分手机 APP 页面显示主脚本运行但守护脚本未运行，后台仍可收到心跳。
- 崩溃后再次启动时，可能出现无障碍设置页跳转或无障碍状态误判。

证据：

- ADB 可见手机曾持续出现 `/data/user/0/com.agri.video.collector/files/project/main.js` 的 `ScriptThread ... notifyThreadExit`。
- 频率与主脚本待命循环 `sleep(Math.min(config.runtime.agentIdleLoopMs || 1000, 300))` 对应，接近每 300ms 一次。
- 后台心跳由 `main.js` 的常驻循环上报，不依赖 `watchdog.js`，因此守护脚本未运行时仍可能在线。

当前判断：

- `collector-app.js` 的待命循环高频调用 `controlLoop.pollControlCommandsAsync(false)`。
- `pollControlCommandsAsync(false)` 在创建线程后才进入 `pollControlCommands` 判断是否达到 `commandPollIntervalSeconds`。
- 当未到轮询间隔时，新线程很快退出，但线程已经创建，长期待机会导致 AutoJS6 线程/脚本资源累计，最终触发 OOM。

处理方案：

1. 将后台命令轮询的间隔判断提前到创建线程之前。
2. 保留 `force=true` 的即时轮询能力。
3. 限制后台异步线程启动频率，避免待命循环每 300ms 创建线程。
4. 补充日志或诊断字段，区分主脚本运行、守护脚本运行、无障碍检测来源和后台心跳来源。

解决结果：

- 已在 `mobile-agent/autojs/app/control-loop.js` 增加 `shouldPollControlCommands`，在 `pollControlCommandsAsync(false)` 创建线程前先判断命令轮询间隔，未到间隔直接返回。
- 设备未注册时也会更新 `commandControl.lastPollAt`，避免未注册状态下每 300ms 创建一次后台线程。
- 已新增 `mobile-agent/autojs/tests/control-loop.test.js`，覆盖“未到轮询间隔不创建线程”和“未注册轮询受节流”两个场景。
- 已在 `mobile-agent/autojs/core/permission.js` 增加无障碍检测诊断日志，记录 `enabled`、`source`、`packageName`、`enabledServices`；不改变原有自动跳无障碍设置页行为。
- `mobile-agent/autojs/project.json` 已提升到 `1.0.22/58`，用于区分本次 OOM 修复和无障碍诊断日志版本。
- 1.0.22 已被 1.0.23 打包产物取代；当前应安装 `dist/apk/燎原星火-1.0.23-inrt.apk` 后真机回归，确认 AutoJS6 OOM 不再出现。

已执行验证：

- `node mobile-agent/autojs/tests/control-loop.test.js`
- `node mobile-agent/autojs/tests/live-comment-runner.test.js`
- `node mobile-agent/autojs/tests/run-request-resolver.test.js`
- `node mobile-agent/autojs/tests/live-card-geometry.test.js`

验证口径：

1. 真机待命至少 10 分钟，logcat 不再持续刷 `ScriptThread...main.js notifyThreadExit`。
2. 后台仍能按配置间隔收到心跳和控制命令。
3. APP 页面不再出现 AutoJS6 OOM 崩溃页。
4. 守护脚本未运行时，后台能明确展示或日志能解释心跳来源。
