## 1. 旧业务冻结方案

原则：**代码全留、入口全冻、随时可解冻、绝不影响发布业务**。

| 层 | 措施 | 细节 |
| --- | --- | --- |
| 后端 | 特性开关拦截 | `apps/api/.env` 增加 `LEGACY_BUSINESS_FROZEN=true`；命中开关时：`POST /admin/mobile-commands`（采集类 commandType：START/PAUSE/STOP/RESUME 等）与任务分配接口返回 `409 LEGACY_BUSINESS_FROZEN`。**放行**：PUBLISH_VIDEO_TASK、远程脚本配置/绑定、发布任务全部接口、设备注册心跳 |
| 前端 | 菜单隐藏 + 按钮移除 | 隐藏菜单「任务调度」「配置」；设备页移除 启动/暂停/关闭/启动-继续 按钮（设备列表、绑定操作保留）；「采集记录」「日志中心」保留只读（不影响发布，留作查数） |
| 手机端 | 零改动 | 收不到采集命令自然不会跑旧流程；APK 内旧代码保留无害 |
| 解冻 | 改回开关 | `LEGACY_BUSINESS_FROZEN=false` + 恢复菜单，即回到整理旧业务状态 |

## 3. 接口数据传输方案（确认版——链路已成型，无需重做）

```
① wecom-console → 后台（已测通，mock 契约）
   POST /api/v1/external/publish-tasks/claim  {platform, accountName?}
   ← 8 字段：taskId / platform / accountName / title / description(含5个#话题) / coverUrl(可null) / videoUrl / status

② 后台 → 手机（已实现，publish-command.service.ts:25-39）
   PUBLISH_VIDEO_TASK payload：
   taskId / title / description / coverUrl / videoUrl
   responseDelayMsMin~Max / actionWaitMsMin~Max（双闸口区间）
   expectedTopicCount / downloadDir（素材根目录覆盖值）

③ 手机 → 后台 → wecom-console（已实现）
   POST /mobile/publish-tasks/:id/result  {status, error?, publishedUrl?, platformContentId?}
   → PATCH /api/v1/external/publish-tasks/{taskId}/status  {platform, status, publishedUrl?, platformContentId?, error?}
```

缺口只有两个：前端按钮（孤儿接口）+ 手动测试接口 `POST /admin/publish-tasks/manual-test`（新增，复用 createPublishVideoTaskCommand 跳过外部 claim）。

## 4. 设备素材存储方案（用户拍板版）

### 4.1 核心规则

| 规则 | 内容 |
| --- | --- |
| 每任务独立文件夹 | 根目录下新建：`/sdcard/YYYYMMDD/`；同一天第 2、3…个任务：`/sdcard/YYYYMMDD（1）/`、`/sdcard/YYYYMMDD（2）/`… |
| 一文件夹只装一次任务 | 文件夹内容固定为本次任务的 `video.mp4` + `cover.jpg`（不再带任务名前缀——文件夹本身就是命名空间） |
| 序号持久化 | 当日序号存手机 storages（按日期键计数），删除文件夹或脚本崩溃重启后不撞名、不重号 |
| 下载前清残 | 每次任务开始前，扫描并删除**所有**匹配素材命名模式的残留文件夹（上次崩溃/失败的 leftover）→ 保证系统相册里只剩本次素材 |
| 下载即扫描 | 每个文件落盘后立即 `media.scanFile`（已有逻辑，保留） |
| 发布后删除 | 本次任务结束（成功或失败）→ 删除本次文件夹 |
| 缺料即报 | `coverUrl` 为 null → 不进入发布流程，直接失败上报「缺少封面素材：接口 coverUrl 为空」；视频缺失/下载失败同理，**缺什么报什么**（复用现有 MATERIAL_INVALID 通道，错误文案具体化） |

### 4.2 为什么这样不会选错素材（双保险）

1. **残留清零**：下载前清掉全部历史素材文件夹，相册里不存在旧素材；
2. **最新即第一**：发布动作前一刻才下载，本次视频是 MediaStore 里最新的视频 → 抖音/视频号素材选择器按时间倒序，第一个就是目标；封面图紧随其后（业务文档的"第一个视频+旁边图片"规则确定性成立）。

### 4.3 串行约束（逐条下载逐条发布）

- 手机端命令天然串行（逐条拉取→执行→ACK→下一条）；
- 加一道执行器锁：发布流程开始时置运行标志，期间到达的第二条 PUBLISH_VIDEO_TASK 立即失败回报 `PUBLISH_BUSY`（不并发下载、不排队 silently），由后台决定重试时机；
- 后台调度侧保持现状（按发布时间段触发 + 每日上限），单设备同时只有一条在飞任务。

### 4.4 配置项

publish_video 配置新增 `materialRootDir`（默认 `/sdcard/`），payload 的 `downloadDir` 字段语义改为"素材根目录覆盖值"（空=用默认）。手机端新建 `domain/素材目录管理.js`（≤400 行）承载：文件夹命名（含序号）、残留清理、下载、扫描、发布后删除。

## 修订记录 v1.1（2026-07-28 15:20，用户五条业务确认）

1. **双平台顺序**：同一设备同一时间段命中抖音+视频号两条任务 → **先发抖音，后发视频号**（调度器按平台顺序出队）。
2. **话题待补 = 断点续传，不是重走全流程**。三层设计：
   - 第一层（后台，主闸门）：claim 落库后、匹配前先校验描述话题（# 数量 = expectedTopicCount 且每个 # 后有文字）→ 不合格直接 TOPIC_PENDING，**不匹配、不下发、手机无感知**；后台补全后任务回到可调度状态。断点 = 未开始，继续 = 带补全内容下发。
   - 第二层（手机，收到命令时防御）：同一套校验，不合格 → 回传 TOPIC_PENDING，**不下载素材、不开 app**；补全后后台重发命令，手机正常执行。
   - 第三层（手机，发布前校验发现问题的交互场景）：**就地停车等待**——保持当前界面、保持亮屏，每 20 秒轮询后台任务是否已补全；拿到补全内容就地填入修正后的描述继续流程；超过 `topicResolveTimeoutMinutes`（配置项，默认 30 分钟）未补全 → 失败上报「话题补全超时」，finally 清理素材 + 释放执行器锁。
3. **发布成败判定**：执行器检测发布后界面特征（toast/跳转），特征清单在真机联调（N6）时校准。
4. **废除"账号每日上限"**：一个账号一天发几条**完全以接口返回为准**（可能只派 11 点一条，也可能 11+17 点两条；无视频号的账号只有抖音任务）。`dailyLimitPerAccount` 从配置 schema、业务配置 UI、调度器上限分支中全部移除；领取循环改为同 slot 内逐平台领空队列（接口返回 data:null 为止）。
5. **时间段语义**：到点后台才 claim+下发，手机收到**立即执行**；不做"提前领取、预发送等待"（避免工作量与状态管理成本）。
6. **视频号设备守卫**（新增，配合第 4 条）：视频号任务命中设备但绑定无 `wechatChannelsName` → 不下发，回填「未发布：该设备未绑定视频号」；accountName 为 null 的视频号任务 → UNMATCHED，原因「视频号任务必须指定账号并绑定视频号」。

> 实施落点：以上规则由手册增补节点 **N5B（业务规则对齐）** 承载，插在 N5 之后、N6 之前执行；N6 验收清单同步增加对应勾选项。
