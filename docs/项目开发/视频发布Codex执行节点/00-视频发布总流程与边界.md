# 00-视频发布总流程与边界

## 目标

把视频发布业务的全局规则先固定下来，后续节点只能在这个边界内修改，避免 Codex 一次性改爆后端、前端和 AutoJS 手机端。

本批节点的总目标是：

1. 外部接口任务明确给出平台，系统不再默认“一条任务双平台都发”。
2. 同一时间段内若有多个平台任务，后端固定按“抖音 → 视频号”的平台顺序处理。
3. 同一设备不在手机端排队；设备忙时由后端延迟重试，默认 **3 次 / 每次间隔 5 分钟**。
4. 同一素材缺视频、缺封面或 URL 无效时，该素材关联的双平台任务都失败，不允许某个平台先发。
5. 话题不足时，所有平台都等补全，不允许先发布其中一个平台。
6. 手机端只执行单条 `PUBLISH_VIDEO_TASK`，并继续负责下载、发布、清理、话题断点续传和验证弹窗标记。

## 当前问题

前序只读核对确认：

- 后端已有外部 claim、设备匹配、命令下发、结果回写、话题补全、outbox 重试等骨架。
- 前端已有视频发布 6 个入口、粘贴发布、接口定时、任务看板、设备账号绑定等骨架。
- AutoJS 已有抖音/视频号发布流程、素材目录、发布锁、动作闸口、话题断点续传和验证弹窗标记。

但仍有关键冲突：

- 视频号当前按 `wechatChannelsName` 路由，不是按抖音号路由到同设备。
- 后端会向同一设备连续创建多个 `PUBLISH_VIDEO_TASK`，形成手机端排队。
- 后端没有 `PUBLISH_BUSY` 延迟重试模型。
- 双平台顺序只依赖配置数组顺序，不是强约束。
- 封面必填没有全链路强制。
- 前端看板缺 `PUBLISH_BUSY` 状态和统计。
- 前端高级调试的手动发布配置来源被 `external_pull` 过滤空。

## 不要改什么

- 不要改真实外部接口 token、真实设备身份、真实生产配置。
- 不要恢复旧业务入口，不要修改采集/直播/商品卡旧流程。
- 不要让手机端处理“后台排队”；手机端只做本地发布锁防御。
- 不要把一条没有平台字段的外部任务默认为双平台任务。
- 不要一次性重构所有发布模块；按 01-10 节点逐个提交和测试。
- 不要把 `PUBLISH_BUSY` 设计成移动端常规上报状态；它主要是后端调度决策，移动端只保留防御上报。

## 验收口径

完成全部节点后，应满足：

1. 外部接口返回平台字段，系统按该平台保存和下发，不再隐式双发。
2. 同一 slot 多平台任务固定抖音先处理。
3. 视频号任务按抖音号命中同一设备，再检查该设备是否具备视频号绑定能力。
4. 同设备已有活跃发布时，不创建新的手机命令；后端按 5 分钟间隔重试，最多 3 次。
5. 重试耗尽后才回写外部 `PUBLISH_BUSY` / 未发布。
6. 缺视频、缺封面、URL 无效、话题不足都不会下发手机命令。
7. 话题补全后复用原任务继续，不重新 claim 外部任务。
8. 前端能看到 `PUBLISH_BUSY`、素材无效、话题待补、视频号验证待处理等状态。
9. AutoJS 单条任务执行后必定清理素材目录并释放本地发布锁。

## 风险提醒

- `PUBLISH_BUSY` 如果直接立即回写外部，会违背“3 次 / 5 分钟延迟重试”的确认结果。
- 如果 busy 检查不排除当前任务，会导致话题补全重下发被自己的旧命令拦住。
- 如果视频号直接用 `wechatChannelsName` 匹配，会把同一抖音账号的双平台任务拆到不同设备。
- 如果只在手机端防 `PUBLISH_BUSY`，后台仍会形成命令堆积，真机轮询会变成排队。
- 如果封面只在手机端下载时报错，外部任务会被不必要地下发，且双平台失败语义不清。
