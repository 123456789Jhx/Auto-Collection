# 06-发布设置时间闸口秒转毫秒

## 目标

明确发布设置中响应延迟、动作等待等时间闸口字段的 UI 单位和后端 payload 单位。

建议产品口径：

- 前端 UI 展示和编辑使用“秒”，便于用户理解。
- 保存到配置 payload 和下发给手机端时使用“毫秒”，保持现有 AutoJS 执行器字段语义。

需要转换的字段：

- `responseDelayMsMin`
- `responseDelayMsMax`
- `actionWaitMsMin`
- `actionWaitMsMax`

## 当前问题

前序只读核对发现：

- `RemoteScriptConfigModal.tsx` 默认值直接使用毫秒：700、1200、900、1500。
- 动态表单 `NumberField.tsx` 只是普通数字输入，不做单位转换。
- 后端 schema 描述为毫秒。
- 当前没有“UI 秒 ↔ payload 毫秒”的适配层。

如果用户期望 UI 填“1.2 秒”，当前实际会保存为 `1.2` 毫秒或要求用户填 `1200`，体验和业务口径都容易错。

## 不要改什么

- 不要改变手机端字段名；AutoJS 仍读取 `*MsMin` / `*MsMax`。
- 不要把后端、数据库和命令 payload 全部改成秒。
- 不要让高级 JSON 与动态表单显示的单位混乱。
- 不要对 `publishTimeSlots` 做秒/毫秒转换；它是 `HH:mm` 时间窗。

## 实施步骤

1. 确认 UI 单位策略。
   - 推荐：UI 秒，payload 毫秒。
   - 表单 label 应显示：
     - 响应延迟最小值（秒）
     - 响应延迟最大值（秒）
     - 动作等待最小值（秒）
     - 动作等待最大值（秒）

2. 实现适配层。
   - 方案 A：业务层适配。
     - 在 `RemoteScriptConfigModal.tsx` 打开弹窗时，把 payload 中毫秒除以 1000，填入表单显示值。
     - 保存时，把表单中的秒乘以 1000，再写入 `configPayload`。
   - 方案 B：动态表单扩展。
     - 在 schema 中支持 `uiUnit: "seconds"` 或类似扩展。
     - `NumberField` 根据配置自动转换。
   - 推荐先用方案 A，改动范围小。

3. 处理小数。
   - UI 秒字段允许 0.1 或 0.5 秒。
   - 保存时使用 `Math.round(seconds * 1000)`。
   - 最小值不能小于 0。
   - 最大值不能小于最小值。

4. 保持 JSON 高级编辑一致。
   - 直接素材配置目前隐藏高级 JSON。
   - 如果接口定时配置仍允许 JSON 高级编辑，需要明确 JSON 中仍是毫秒。
   - 表单切换到 JSON 时，不要把秒值误写进 payload。

5. 更新后端描述。
   - 后端 schema 可继续叫毫秒。
   - 前端 label 可单独显示秒。
   - 文档提示：前端显示秒，保存后 payload 仍为毫秒。

6. 手机端无需修改。
   - `action-timing-gates.js` 继续按毫秒 sleep。
   - 发布命令 payload 继续传毫秒字段。

## 测试要求

前端测试：

- 打开配置弹窗时：
  - payload `responseDelayMsMin: 700` 显示为 `0.7`。
  - payload `responseDelayMsMax: 1200` 显示为 `1.2`。

- 保存配置时：
  - UI 输入 `0.8` 保存为 `800`。
  - UI 输入 `1.5` 保存为 `1500`。

- 校验：
  - 最大值小于最小值时报错。
  - 负数时报错。
  - 空值按默认值或必填规则处理。

建议测试文件：

- `account-data-platform/apps/web/tests/publish-execution-settings.test.js`
- `account-data-platform/apps/web/tests/dynamic-form-schema.test.js`

后端/手机端测试：

- 不需要修改 AutoJS 逻辑测试，但建议保留 `action-timing-gates` 现有毫秒语义测试。

## 验收口径

- 用户在发布设置页看到的是秒。
- 保存到 API 的配置 payload 仍是毫秒。
- 下发给手机端的命令 payload 仍是毫秒。
- 旧配置毫秒值打开后能正确转换显示。
- 再次保存不会产生二次乘 1000 的错误。

## 风险提醒

- 最容易出现的 bug 是打开时除以 1000，保存时又对已经是毫秒的 JSON 值乘 1000。
- 如果动态表单和 JSON 编辑同时存在，必须明确两者单位，否则会出现配置漂移。
- 如果后端也改成秒，会导致手机端 sleep 时间缩短 1000 倍，不能这么做。
