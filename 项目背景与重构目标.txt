1. 项目背景与重构目标
本节将详细说明需要重构的现有系统架构，以及本次重构要实现的业务与技术目标。
1.1 现有架构约束
根据前期的项目梳理结果，现有 Auto-Collection-main 系统的架构存在以下硬性约束，任何重构方案都必须严格遵循这些约束，不能以任何理由突破：
命令通道约束：Mobile Agent 端与后端控制平面的通信协议，采用的是已在生产环境稳定运行的 REST 轮询机制，而非性能更高但业务不兼容的 WebSocket 协议。因此在重构过程中，不能对整个通信层进行替换式修改，新业务的命令交互必须完全兼容现有的 REST 轮询逻辑。
老业务基线约束：系统当前的养号、发布视频和 legacy 评论抓取业务，是支撑线上流量的核心稳定链路。任何重构操作都不能修改这些老业务目录下的文件，也不能影响它们的现有行为逻辑 —— 即使是修复已知问题，也必须在独立的技术债优化任务中单独处理，不能混入本次重构流程。
共享文件行数约束：项目中负责传输报文的核心文件mobile-agent/autojs/core/uploader.js，是一个已经超过 400 行的共享逻辑文件。根据团队的代码合并约束，除非是紧急的线上热修复，否则不允许进一步增大这类文件的行数。这意味着新业务的报文透传逻辑，必须采用最小化的兼容修改方案，或者在现有的报文 envelope 结构内扩展字段，不能直接在该文件中添加大量新代码。
打包自动处理约束：项目的打包构建脚本scripts/bundle-autojs.ps1，已经设计为递归遍历并打包features目录下所有业务子目录的逻辑。因此在重构过程中，不需要为新业务模块单独修改打包脚本，只要将新业务代码放在features目录下的合规子目录中，就可以被自动打包进业务包，这一机制已经在多个现有业务中验证过，是稳定可靠的。
1.2 重构目标
本次重构需要在严格遵循上述现有架构约束的前提下，实现以下四个核心目标：
业务目录物理隔离：在 Mobile Agent 端的features目录下，为新评论抓取业务创建独立的隔离目录。通过工程级的目录结构约束，彻底避免新业务的逻辑被老业务代码反向引用，防止两个业务的实现逻辑在运行时产生类加载冲突或资源抢占冲突。
路由契约逻辑隔离：为新评论抓取业务设计独立的路由契约白名单机制。控制平面在下发任务时，会通过白名单校验请求中的路由相关字段；如果字段不符合新业务的契约规则，将直接在网关层返回标准错误响应，根本不会触达新业务的实际执行逻辑 —— 这意味着老业务的请求链路完全不受新路由逻辑的影响。
报文逻辑隔离：在不修改共享uploader.js文件核心逻辑的前提下，利用现有报文 envelope 结构的扩展能力，将新业务的命名空间字段透传到控制平面。同时保证新旧业务的报文字段完全兼容，不会影响现有日志、心跳和回执报文的解析逻辑，也不需要对控制平面的报文解析链路进行升级。
错误路由防护：在 Mobile Agent 端的路由入口增加强制校验逻辑。所有不符合新评论抓取业务完整路由契约规则的请求，都会被路由防护逻辑直接拦截，并且返回标准化的错误响应 —— 这一机制可以彻底避免非法请求被老业务的注册表逻辑处理，防止出现未定义的交叉业务行为。
1.3 非目标（不修改范围）
为了将重构的风险和工作量控制在可接受的范围内，本次重构将不包含以下范围的修改或优化：
任何涉及老业务目录mobile-agent/autojs/features/account-warmup/下的文件修改，包括调整现有文件的代码格式、修改老业务的配置常量、甚至修复已知的老业务逻辑 bug。
对共享文件mobile-agent/autojs/core/uploader.js的非兼容逻辑修改，比如修改现有报文的 envelope 结构、调整 REST 请求的底层封装逻辑、或者将新业务的报文透传逻辑实现为单独的上层拦截器。
将 Mobile Agent 端与控制平面的通信机制，从当前的 REST 轮询方式替换为 WebSocket 方式。这一通信层的整体替换方案，需要留到后续的专属技术架构升级任务中处理，不在本次重构的覆盖范围内。
对现有业务的打包脚本scripts/bundle-autojs.ps1进行任何修改，比如调整业务包的生成规则、新增新业务的特殊打包配置、或者修改业务包的输出路径。
任何与评论抓取业务本身无关的逻辑修改，比如优化评论抓取的控件选择器逻辑、增加评论内容的实时去重逻辑、或者调整评论分页读取的策略。

2.3 共享文件修改边界

任务路由管理器修改规则：仅在该文件的现有路由判断逻辑中，新增一个独立的 else if 分支用于识别新业务的路由字段；完全不修改老业务的路由分支、路由优先级逻辑，以及任务调度的核心逻辑。同时，新分支的实现代码必须采用独立的工具函数封装，避免直接在该文件中写入大量冗余代码，进一步增加文件行数。
核心原子层适配规则：新业务的原子层适配逻辑，将采用独立的文件实现，放在新业务的隔离目录features/new-comment/下；完全不修改老业务的原子层适配文件，也不共享老业务的原子层实例。这一方案可以保证新老业务的原子层资源完全隔离，不会在运行时出现资源抢占或冲突的情况。
3. 实施阶段一：物理隔离与基础适配
本阶段将创建隔离的新业务目录、核心原子层适配代码和路由守卫逻辑，保证所有新业务的逻辑完全不与老业务的逻辑交叉引用。
3.1 安全准备工作（必须先执行）
在开始任何代码修改之前，必须执行以下操作流程，保证所有修改的风险被完全隔离，并且可以快速回退到稳定状态；这是后续所有重构操作的前置校验流程，必须在操作完毕后验证结果，才能进行下一步操作。具体的操作流程如下：
校验本地仓库的工作区状态：执行git status命令，确认当前工作区的文件状态干净，没有未 tracked 的文件，也没有未提交的修改记录。如果存在未提交的修改，需要先执行git add .和git commit -m "chore: 暂存本地未提交改动，准备评论隔离重构"命令，将所有本地改动提交到本地仓库，避免后续代码合并时出现冲突。
切换到主分支并拉取最新代码：执行git switch main命令，切换到本地仓库的主分支；然后执行git pull origin main命令，拉取远程仓库中主分支的最新代码，保证本地仓库的基础代码与远程仓库的最新版本完全一致，避免后续开发时出现基于旧版本代码进行修改的情况。
创建并切换到重构专属分支：执行git switch -c refactor/comment-capture-isolation-20260826命令，创建一个新的专属重构分支，并自动切换到该分支。后续所有的代码修改和提交操作，都将在这个独立的分支上进行；这一机制可以将重构操作的风险完全隔离在该分支内，不会影响到主分支的代码稳定性。
备份核心共享文件：在本地磁盘的安全位置创建备份目录，如C:\temp\autojs-backup\；然后复制以下两个核心共享文件到该备份目录：
mobile-agent/autojs/core/uploader.js
mobile-agent/autojs/app/account-warmup-command-bridge.js
这一操作是为了在共享文件出现兼容问题时，可以快速将文件恢复到修改前的状态，降低故障回退的成本。
验证环境变量的配置状态：确认 Mobile Agent 端的开发环境变量，与生产环境的配置完全一致，包括控制平面的接口地址、设备 ID 的配置信息、以及 REST 轮询的间隔时间等核心配置参数，避免后续重构时出现因环境变量不一致导致的调试偏差或意外行为。
3.2 原子层适配
在新业务的隔离目录下，创建封装 AutoJS 基础操作的原子层适配代码；这一逻辑将完全独立于老业务的原子层适配逻辑，保证新老业务的操作资源被完全隔离。需要在新业务目录下创建的原子层适配文件路径为mobile-agent/autojs/features/new-comment/device-atoms.js；该文件的实现逻辑，需要遵循以下约束：
以模块化方式提供兼容老业务原子层的能力封装，包括安全点击、安全滑动、控件元素等待、文本获取和随机延时等基础操作；所有这些操作的底层实现，都将复用项目中已有的utils/autojs-utils.js和core/accessibility.js工具函数，不会重新实现相关逻辑。
所有的操作函数都采用同步调用模型，完全兼容 AutoJS 的现有运行机制，不将其修改为 Promise 异步调用模型；这一设计可以避免破坏现有业务的子线程管理和停止信号处理逻辑，保证新业务的线程行为与老业务完全一致。
在该文件的顶部，集中保存抖音平台的控件选择器、页面区域和坐标配置常量，比如直播评论区的控件 ID、分页按钮的坐标等；这一设计可以将平台相关的配置逻辑与业务的执行逻辑完全隔离，后续如果需要修改控件选择器，只需要修改该文件顶部的配置常量即可。
该文件的总行数必须控制在 400 行以内，优先采用已有工具函数的包装逻辑，不添加任何额外的抽象逻辑或重复代码。
该文件的所有导出函数，都必须包含足够的异常处理逻辑，比如控件元素找不到、点击操作超时等异常情况的捕获和处理；并且在异常发生时，将错误信息结构化记录到日志中心，保证问题的可追溯性。

3.4 路由接入与路由守卫
修改共享的任务路由管理器文件，增加新业务的路由识别逻辑；同时新增独立的路由守卫文件，实现新业务的四层路由契约校验逻辑。具体的文件修改和创建规则如下：
修改任务路由管理器文件：打开文件mobile-agent/autojs/app/account-warmup-command-bridge.js，在现有的路由判断逻辑中，新增一个独立的 else if 分支，用于识别新业务的路由字段；该分支的校验逻辑，将完全调用新路由守卫文件中的校验函数。这一修改必须采用最小兼容方案，不能修改老业务的任何路由分支；并且新分支的代码行数必须控制在 10 行以内，避免进一步增加该文件的代码行数。

6.1 硬性约束（不能突破的规则）
本次重构必须遵循以下规则，不能以任何理由突破；这些规则是保证重构过程可控、不会影响现有业务稳定性的核心底线：
老业务目录只读约束：mobile-agent/autojs/features/account-warmup/目录下的所有文件，都不能被修改；包括老业务的配置文件、入口文件、原子层适配文件、清理逻辑和注册表逻辑，都不能进行任何修改。
共享文件行数约束：mobile-agent/autojs/core/uploader.js文件的修改，只能添加最小化的namespace字段透传逻辑；修改后该文件的总行数，不能超过 400 行的约束。
新路由隔离约束：所有新业务的逻辑，必须放在mobile-agent/autojs/features/new-comment/目录下；新业务的所有文件，都不能引用老业务的任何代码或配置常量；两个业务的资源必须完全隔离，不能共享任何原子层实例。
报文兼容约束：新业务的namespace字段，必须在现有报文 envelope 结构的顶层扩展字段中透传；不能修改现有报文的结构、字段名或编码方式，以保证新旧业务的报文在传输层上完全兼容。
打包逻辑兼容约束：不能修改项目的打包脚本scripts/bundle-autojs.ps1；新业务的目录结构，必须与现有养号、发布视频等业务的目录结构完全一致，以保证打包脚本可以自动识别并打包新业务的逻辑。
REST 轮询兼容约束：不能将 Mobile Agent 端与后端控制平面的通信协议，从现有的 REST 轮询方式替换为 WebSocket 方式；新业务的命令交互，必须完全兼容现有的 REST 轮询逻辑，不能修改通信层的核心逻辑。
错误路由防护约束：所有不匹配新业务完整路由契约规则的请求，必须在路由层直接拦截，返回标准化的错误响应；不能回落到老业务的默认路由分支，也不能执行老业务的任何逻辑。
二元修改约束：修改共享文件时，必须采用兼容修改的方式，不能将新的路由逻辑耦合到老业务的代码中；保证新老业务的逻辑在运行时完全解耦，不会出现交叉引用的情况。
